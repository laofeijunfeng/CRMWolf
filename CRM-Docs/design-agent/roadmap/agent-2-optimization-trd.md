# Agent 2.0 优化 TRD（审阅草案）

- **版本：**2026-09-28 草案；待产品与技术审阅，**不是现行已冻结合同，也不是实施完成证明**。
- **适用入口：**销售助手 Web `/assistant` 与后端 `/v1/assistant`。旧 Web Agent、飞书 IM、页面表单不在此次切换范围。
- **定位：**实施和验收的单一草案清单。每一项须以本文件的验收矩阵关闭，不能用阶段名称代替验收。
- **既有权威：**`CONTEXT.md:15-44`、Accepted `docs/adr/0001-customer-activity-workflow-parity.md:14-45`、[客户活动 Workflow 实施规格](customer-activity-workflow-parity-spec.md)。冲突须先批准版本/入口边界；本草案不自行推翻既有合同。

## 1. 目标与非目标

**总验收红线：Agent 2.0 的同步请求、持久后台任务及重试/恢复入口均不依赖 LangChain、LangGraph 或旧 `app.services.agent.langchain_runtime`。** 检查运行时传递依赖，不以移除显眼的 import 作为合格证明。旧入口暂留，整个后端不必立即卸载这些依赖。

本期交付一条完整业务纵切：接收活动 → 区分跟进/会议 → 绑定有权限的客户 → 类型化整理和最终评分 → 单缺口补充 → 冻结确认 → 幂等写入活动 → 商机、阶段、**每条**任务、客户事实逐笔提案/确认/执行。活动写入后冻结，后续原子失败不回滚已写活动。模型只能提名候选，不能直接写权威状态或调用 CRM。

**默认禁止：**因 2.0 活动自动完成历史任务、未经逐笔确认写客户事实、发布受该活动影响的用户可见档案。任何例外均须另行产品批准并定义来源、安全及无框架执行链。创建客户、联系人、线索等旧 Agent 能力及旧入口下线不属于本期。

## 2. 设计依据、已知阻断及冲突裁决

下表说明为何必须优化，**不是声称修复已经实现**。

| 编号 | 现状依据 | 必须达到的边界 |
| --- | --- | --- |
| R1 | `assistant/confirmation.py:102-149` 先调用 writer 再记助手提交；`customer_activity_write_service.py:536-597` 自行提交 | CRM 活动事实和助手回执同事务，或由持久命令账本对账；重放仅一笔。 |
| R2 | `app/api/assistant.py:314-327` 在 SSE `accepted` 后才启动进程内 runner | turn 必须先持久化，断流/重启由独立 Session 与租约恢复。 |
| R3 | `assistant/task_state.py:109-113` 以 ORM 快照及 `with_for_update()` 比较版本 | 数据库条件 `UPDATE ... WHERE version=:expected AND status=ACTIVE`，检查影响行数。 |
| R4 | `assistant/llm.py`、`chooser.py` 引用旧 Agent runtime，质量门禁及 writer 依赖旧评分 | 2.0 传递调用链和由其创建的持久任务都不进旧 Agent runtime/图。 |
| R5 | `real_writer.py` 在确认时重评分、只保存简化正文；会议字段与原文可能丢失 | 完整类型化稿、原始输入和最终评分冻结；确认零模型调用、零改稿。 |
| R6 | `app/api/assistant.py:75-88` 没有生产提案执行器；`assistant/proposals.py:116-155` 无执行器亦记成功 | 无真实候选或执行器不展示可确认成功的卡片；成功以 CRM 回执为准。 |
| R7 | `create_final_from_agent():277-328` 固定创建旧后台工作；全局客户智能对账读取活动水位 | 2.0 来源必须跨入队、扫描、证据、上下文和发布全链隔离。 |
| R8 | 现有等待只含 `FIELD/CONFIRMATION/ACTIVITY_KIND`，业务又要求多客户选择 | 明确增加封闭的 `OBJECT_SELECTION` 等待。 |

**五篇原设计的内部张力及本草案裁决：**

1. “等待中回复零模型调用”与“补字段后重跑整理/评分”冲突：准确规则是**等待回复不调用 chooser**；服务端可按字段依赖调用整理及评分模型。确认/取消仍为零模型调用。
2. “补充不翻案”与最终稿变化后评分有效性冲突：保留未受影响的已接受事实，但实质变更使旧评分失效，对完整最终稿重新评分。已有客户绑定、未受影响字段不因补一句话被模型随意改写；**最终分数可以变化**。
3. Accepted 旧合同要求补充后重新解析完整语义；2.0 要求局部重算。本草案以**局部字段合并、完整原文校验、最终整稿评分**为候选合同，须在现行 ADR/领域文档中明确适用 2.0 入口后才成为正式规则；旧 Web Agent/表单仍守现行合同。
4. 多客户无法靠“无匹配”回退实现：增加 `OBJECT_SELECTION`，候选来自服务端；无匹配、歧义、无权和解析故障必须区分。
5. “只读档案刷新”不能覆盖现有事实持久化与档案发布：未经批准时过滤 2.0 输入；无法隔离的刷新失败关闭、保留原发布版本。
6. 五篇原设计既要求复用 CRM 底座又禁止旧控制核依赖：共享的是中性领域合同和应用写入语义，**不是**旧 `agent` 包、旧图或旧后处理 worker。

## 3. 运行模块与依赖约束

```text
/v1/assistant：鉴权、请求幂等、任务投影、SSE/补读
  → 协调器：唯一状态转换入口、合法动作集合、候选裁决
     ├─ 中性模型传输：Chooser / 跟进或会议整理 / 对应 Rubric 评分
     ├─ 只读对象解析端口：团队、客户/商机/任务、权限、对象现状
     └─ CRM 应用命令端口：权限复核、幂等、canonical 写入、来源策略
  → 助手持久 turn / lease / 恢复 worker：自有 Session
```

- 中性模型传输可沿用项目已有 `app/services/ai_service.py:18-125` 的 OpenAI 兼容 `httpx` 方式及现有 AI 配置，输出经 Pydantic 结构化校验。它不得引入 LangChain/LangGraph；缺配置、超时、空输出、非法输出为技术失败，不作为 `end` 或业务低分。
- 跟进/会议 schema 与两套 canonical rubric 是领域合同，使用中性模块供表单和 2.0 共同引用；2.0 不运行时 import `app.services.agent.*` 的模型、控制或评分。静态 import 不足以证明安全：动态工具注册、延迟 import、任务队列与恢复扫描也必须检查。
- 工具只经中性 CRM 应用端口调用，不直接 import 业务 ORM/CRUD。应用端口可在进程内，不强制新建 HTTP 往返；须保留活动写入附带的旅程事件、操作日志、证据等 canonical 同命令语义（`app/crud/customer_activity.py:181-281`），且其来源可追踪。不能绕过应用服务直接插活动表。
- 2.0 的任务是交互真相；只追加动作日志供审计；命令账本仅管理冻结写入与回执，不容模型修改，也不是另一份可写草稿。旧 Web/IM 继续使用旧路径至单独 cutover。

## 4. 状态、模型输出及前端协议

### 4.1 单任务状态

任务保存 `goal`、`activity_kind`、接受/候选字段、逐段原始用户输入、观察、唯一 `waiting_on`、权威对象 ID、冻结命令、`committed` 回执、版本和预算。只有服务端状态转换函数可改这些字段；动作日志只追加。服务端按状态计算合法动作白名单；模型一次只提名**一个**封闭动作名和候选参数，不能连续规划、生成确认凭证、改已接受字段或调用 Tool。同一用户 turn 最多执行一次 chooser；类型确定、整理、评分是提名被允许后的受控子步骤，活动后的下一提案由独立持久 turn 继续。`end` 仅在服务端完成条件成立时生效。

预算明确定义为**已消费的 chooser 提名次数**，在调用前原子检查上限；幂等重放、取消、字段处理和确认不计次数。耗尽时停在可解释的错误/人工处理状态，不能标为成功完成。现有 `budget_max_steps` 不是已生效的强约束。

### 4.2 四类封闭等待

| `waiting_on` | 允许回复 | 拒绝的输入 |
| --- | --- | --- |
| `ACTIVITY_KIND` | 签发选项之一；取消 | 任意类型自由文本、过期选项。 |
| `OBJECT_SELECTION` | 选一个服务端签发的有权候选对象 ID；取消 | 模型自造 ID、过期候选、无权对象。 |
| `FIELD` | 当前字段文本、适用字段的 `EXPLICITLY_NONE`、取消 | 把“算了/不要了”存入字段，回答其他字段。 |
| `CONFIRMATION` | 当前这一笔的确认、明确拒绝/取消 | 普通文本、仅凭 `choice=confirm` 不带动作身份。 |

每个等待包含服务器签发的 `action_id`、任务版本、类型、候选/冻结载荷指纹与可选字段或对象列表。请求包含 `client_request_id`，回复等待还包含 `action_id`、`expected_version` 和明确选择。同一请求 ID 与同一哈希重复投递返回原结果，即使任务已进入**下一张**卡；同键不同载荷报冲突。动作 ID、等待、版本、指纹或用户权限不符时返回 `STATE_CONFLICT` 与最新投影，不改状态。候选客户/商机于选择和写入时再验团队、权限和现状。

用户在 `FIELD` 等待时明确说“算了、不要了”，服务端将其作为取消动作关闭当前任务；前端按钮应直接发取消。改变目标必须另开任务。只接受显式的类型化“这条没有”，不可借任意文本或占位字符串伪造明确无下一步。

### 4.3 业务草稿、整理及最终评分

- 允许类型：`FOLLOW_UP`、`ONLINE_MEETING`、`OFFLINE_MEETING`；持久 canonical 字段为 `activity_kind`，不恢复旧 `method`。用户明确指定优先；普通沟通暂按跟进，会议主题/参会角色/行动项提示会议；线上线下或信号冲突只问一次。
- 跟进载荷含完整正文、客户反馈、进展、风险、下一步动作、时间原话与可解析时间。会议载荷对齐 `customer_activity_ai/schemas.py:10-64`：主题、背景、我方/客户方角色、关键纪要、问答、需求/异议/风险、承诺、**所有**行动项及下一步摘要。行动项各有稳定项 ID、负责人、动作、时间原话；不能缩成一条主行动。
- `source_content` 只按顺序收录用户首句及用户补充原文；不写入系统问题、模型推理、评分理由或整理稿。整理可去重调序，不能遗漏客户反馈、进展、风险、承诺、下一步和时间。正文补充要合并进完整事实而非覆盖全文，行动项按稳定 ID 合并；未受影响的已接受字段保持不变。
- 跟进/会议分别使用 `customer_activity_ai/rules.py:15-44` 的 rubric。评分对象与最终落库的 `content_json`/摘要/下一步一致。服务端强制 `score >= 60` 且独立执行下一步行动门禁；低分只问一个最关键缺口，补前低分不得入业务评分历史。模型评分失败或非法输出是技术失败，不向用户假问“客户反馈缺失”。
- 下一步缺失或“继续跟进”等模糊表达要追问；明确动作无时间可保存，不猜日期；时间不能解析只问该时间。明确暂无行动可保存 `EXPLICITLY_NONE`，同时记录原因或复查条件，不生成空洞任务；会议明确无行动项亦保留依据。
- 按字段依赖补充时不运行 chooser，但可调用受影响的整理/评分模型；**最终整稿**有实质变化就重评分，旧结果作废。落库只存最终评分，不存补充评分历史。确认时不再评分。
- 活动确认前显式改类型：清除旧类型整理及评分，保留用户原文与待复核客户绑定，撤销旧确认卡；活动提交后在中央状态转换与路由同时禁止更换类型/改稿/再次建活动。当前 `/change-kind` 仅检查 `ACTIVE`，不满足此要求。

客户解析需区分 `NOT_FOUND`、`AMBIGUOUS`、`PERMISSION_DENIED`、`DEPENDENCY_FAILURE`。候选只暴露用户有权查看/操作的对象；未找到客户不自动创建客户/线索，本次活动提案停止，建客户另开任务。

### 4.4 冻结命令与前端

确认卡出现前持久化活动冻结命令：团队/用户/客户权威 ID，类型，所有用户原文段，完整类型化 `content_json`、标题/摘要/下次时间/下一步，最终评分/原因/明细与 rubric 版本、模型元数据、草稿版本、载荷规范化指纹、稳定非空 `submission_id`、命令执行状态。卡片显示实际待写的客户、稿件、评分、锁定字段及可展开原文。确认只授权这一指纹，不授权下一张卡。

页面、侧栏、消息和卡片均从服务端任务投影渲染，不解析自然语言、不本地组装 CRM 对象。一次只呈现当前等待及一张提案；“这条没有”发类型化 `EXPLICITLY_NONE`（不是当前 `SalesAssistantChat.vue:402-407` 的占位文本）。“算了”发取消。断流后先查询 turn/任务权威状态，显示**结果待核对**；当前 `SalesAssistantChat.vue:340-342` 直接称“没有提交”不可沿用。前端行为和视觉须遵守现有设计系统。

## 5. 业务时序、事务与恢复

| 阶段 | 行为与持久边界 | 失败/中断结果 |
| --- | --- | --- |
| 1. 接收 | `create`/`submit` 在 `(team,user,client_request_id)` 下存请求哈希及任务/turn；**提交之后**才发送 SSE `accepted(turn_id)`。worker 独立 Session、租约领取，SSE 只投影可补读事件。 | 接收前断流可同请求 ID 重试；接收后断流不取消 turn；重启后回收超时租约。 |
| 2. 无等待提名 | 加载最新状态、预算及合法动作；一次结构化 chooser 提名，服务端检验名称、参数和顺序。 | 缺配置、超时、非法/空输出记持久技术错误与观察，不当作 `end`、不宣称完成。 |
| 3. 类型/客户 | 服务端按规则决定类型，冲突进 `ACTIVITY_KIND`；按团队/活动权限解析客户，多候选进 `OBJECT_SELECTION`。 | 无匹配说明不能记录，不能自动建客户；无权不降级为按名字重找。 |
| 4. 整理、评分、补缺 | 按类型整理整稿，选择正确 rubric 评分及下一步门禁；只问一个缺口。字段回复合并原文并重算受影响结构及最终评分，不调用 chooser。 | 技术失败保留草稿进入可恢复错误；取消不入 CRM；不合规不入活动表或旧后台队列。 |
| 5. 冻结、确认 | 合规后同事务持久冻结命令、版本、确认动作；只接受当前卡的明确决策。 | 编辑产生新草稿/评分/动作 ID；旧确认失效；取消不调用 CRM。 |
| 6. 活动写入 | **零模型调用**。按冻结客户 ID 复核当前权限与状态；条件更新消费动作；同库事务内写 canonical 活动事实、同命令审计/证据、命令成功回执、任务 `committed`、下一 turn/动作日志；写入服务不得自行 `commit()`。 | DB 唯一键 `(team_id,submission_id)` 防重；重试查询同键并核对指纹，一致返回同一活动与回执，不一致拒绝；回滚不能留半笔。不可重试业务拒绝退役此确认凭证。 |
| 7. 后续事项 | 活动成功后另一个持久 turn 只形成一条真实候选，绑定对象、权限要求、原状态、载荷/指纹及稳定命令键；逐笔确认再复核并执行 CRM 命令。 | 拒绝/失败只记观察，已成功活动保持不变；无候选跳过，缺执行器是配置错误而非成功。 |

中央状态迁移采用 `UPDATE crm_assistant_tasks SET ..., version=version+1 WHERE id=:id AND version=:expected AND status=:expected_status`，必须检查更新行数为 1；状态、等待、只追加动作及可同事务的回执一起提交。已提交活动的 ID 和类型不可再变；`committed` 只增不减。以 ORM identity-map 的旧对象快照比较不是原子 CAS。

活动写入优先采用**同一数据库事务**：冻结命令的 `submission_id` 非空、`submission_fingerprint` 与活动记录一致，2.0 来源强制有键。当前 `(team_id, submission_id)` 唯一约束允许 `NULL`，而现有 writer 未传有效 ID，须以 Alembic 迁移和应用校验补足。不得仅依赖 `committed_json` 或客户端防双击。若某项 CRM 命令实际跨数据库/远程接口无法共享事务，先持久登记命令账本并在目标 CRM 按同键幂等执行；模糊超时**先对账**，对账不明停在 `UNKNOWN`、告警，不能盲发、报成功或永久占用原确认卡。

旧卡重放必须首先根据客户端请求 ID 查原命令结果，再决定是否产生冲突；不能把它交给当前最新等待路由，否则旧活动确认会误确认商机。并发相同命令仅一个执行者；权限被撤回时不写活动；技术故障不伪装成内容缺口。任务只在活动已成功，所有已生成提案已成功/明确拒绝/明确跳过后 `COMPLETED`。成功活动不因后续命令失败回滚。

## 6. 后续事项：一次只处理一笔

| 提案/命令 | 候选与确认时的规则 |
| --- | --- |
| 创建商机 | 有本活动可追溯的商机信号且无高置信度现有商机才提案；展示字段摘要，确认后执行真实创建 API，不凭“接受”就记成功。 |
| 推进阶段 | 绑定具体商机；阶段只取当前采购流程允许列表；确认时重验权限、当前阶段及目标可达性。与创建商机分开幂等命令。 |
| 历史跟进任务 | 每条任务独立展示适用候选（完成、延期、取消或无关）、分别确认/执行；未确认任务不变。2.0 的该提案类型不改变旧 ADR 对现有历史待办确认卡的文案/行为边界。 |
| 客户事实 | 只提本次活动原文可定位证据的具体事实，逐条确认后写该事实；确认事实**不等于**批准刷新并发布整份客户档案。 |

实际成功以 CRM 的持久结果/可对账回执为准。取消或执行失败留下观察，再决定下一笔/结束；不会撤销已成功活动。无候选不提示虚构提案；无执行器不得展示可成功的确认卡。

## 7. 来源隔离与旧后台共存

**不能只关 `kick()`，也不能只拦截即时入队。** `CustomerActivityWriteService.create_final_from_agent():277-328` 固定启用旧 PostCommit、客户智能、商机建议；`_write():536-597` 入队并自提交，持久 worker 会恢复。旧 PostCommit 可能自动完成历史任务；全局对账还会绕过直接入队的门禁。

1. **来源和迁移**：新增持久 `ASSISTANT_2` 提交来源，Alembic 修改 `crm_customer_activities` 的来源检查约束与 2.0 幂等非空规则；现有 `AGENT` 不重定义为 2.0。旅程事件、操作日志、证据、向量文档、候选事实及确认后的命令必须能沿来源字段或稳定 `source_activity_id` 追踪到该活动；来源不明的派生数据不得被旧档案管线采用。
2. **源头门禁**：2.0 只做 canonical 活动事实、同命令审计和有来源的证据，不创建旧 PostCommitJob、旧客户智能请求或旧商机建议任务，也不创建可间接恢复这些工作的 outbox。若需要索引，先证明其消费者、写入和恢复入口安全且无框架。停用 `kick()` 不足以实现此项。
3. **领取/恢复门禁**：现有旧队列及未来重试、恢复、手工触发入口在领取与执行前均核对来源和 revision；误排入 2.0 工作记录审计并标 `SKIPPED`，不可触发旧图或自动任务转移。删除 2.0 活动及 tombstone 的清理也要按来源处理，遵守既有删除事实语义，不误触发旧刷新。
4. **全局水位门禁**：`customer_intelligence_reconciliation_service.py:91-246` 扫全体客户并根据 source watermark 排 full refresh；水位与刷新读取的输入必须使用**同一份允许来源视图**。活动、旅程事件、任务、事实、向量/证据及删除事件各自按来源过滤；过滤在排序/`LIMIT` 之前。仅有 2.0 活动变化不得使旧档案标记 stale、入队或发布。
5. **其他来源的合法刷新**：旧来源仍可启动刷新，但当前 `customer_intelligence_context_service.py:472-478` 读取最近 50 条**所有来源**活动，`:848-901` 水位未隔离，旧档案图还能写事实并发布档案（`agent/customer_profile_projection_graph.py:440-535,606-635`）。输入构建、证据注册、事实候选入库和发布前都须排除未逐笔批准的 2.0 活动及其旅程/向量/派生证据，并复核来源水位。若共享对象无法还原合格来源视图，本次客户的旧档案发布失败关闭、原版本保持可见并记录阻断原因，其他合法旧刷新继续运行。

保守边界不是“客户档案永不变”：旧来源的合法刷新仍可变更它；禁止的是让未获批准的 **2.0 证据**参与事实写入/档案发布。2.0 活动即使获准写入，也不自动授权事实写入、历史任务完成或用户可见档案发布。任何例外须产品单独批准，并同时更新来源过滤和恢复合同。

## 8. 错误分类、呈现与运维观察

- 区分 `BUSINESS_GAP`、`NOT_FOUND`、`AMBIGUOUS`、`PERMISSION_DENIED`、`VALIDATION_REJECTED`、`RETRYABLE_DEPENDENCY_FAILURE`、`UNKNOWN_COMMIT_RESULT`、`STATE_CONFLICT`、`CONFIGURATION_ERROR`。只有业务缺口进入 `FIELD`；CRM 原 code/message 经脱敏上界处理后进观察和失败卡，不把权限错误说成“稍后重试”。
- 失败/澄清卡说明：这笔是否写入、原因、1–2 个真实可行动作。未知提交状态必须显示待核对而不是否认提交。SSE `accepted` 与每个阶段/等待都有持久序号可补读；请求级 session 不能传给后台 runner。
- 运维按来源、turn、command、action、activity ID 关联审计；可查询当前租约、重试、不明结果、来源被拒的旧 job、被隔离的对账/发布。审计记录不得含模型推理或不必要的客户明文。
- 故障恢复从任务表/命令账本/持久事件继续，不重新解释全部对话；服务端业务结果始终以权威数据库或目标 CRM 可对账回执为准。
