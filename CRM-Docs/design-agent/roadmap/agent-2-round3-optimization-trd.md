- **版本：**2026-09-28 草案；基于第三轮黑盒测试，待产品与技术审阅，不是实施完成证明。
- **证据：**`outputs/agent2-ui-test-report-round3/report.md`、同目录 `findings/` 与 `screenshots/`。
- **环境：**本地前端 `http://localhost:5173`、后端 `http://localhost:8000`；测试开始时 Alembic `143 → 145_assistant_turns`；账号 `eddie@apifox.com`。
- **范围：**只处理本轮已观察的缺陷、证据不足项和验收口径。既有 `agent-2-optimization-trd.md` 的 MySQL 并发、崩溃恢复、来源隔离和旧入口退役门禁继续有效。
- **权威边界：**销售助手 2.0 的补充规则已由 ADR 0001 第 7 条批准；本文件不改变旧 Web Agent、飞书 IM 和页面表单。

## 1. 本轮结论

16 项中报告标记 8 项 pass、6 项 gap、2 项 blocked。对照截图后，不能按这个总表直接关闭验收：

| 观察 | 证据 | 处理 |
| --- | --- | --- |
| 最近任务整块消失 | `o4`：旧回执 `{"kind":"refused:opportunity"}` 使 50 条任务的严格 Zod 数组解析失败，异常被静默吞掉 | P0，先修 |
| 分类经常超过 180 秒 | `s2/s3/o1` 截图停在“判断活动类型”，实测约 182–197 秒；报告记录混合文本可达 200 秒以上 | P0，先定预算和模型路由 |
| 客户未找到有两套文案和两套卡片 | `s8`：确认失败说“没有找到客户”并显示动作；缺口轮说“未找到对应客户”且不显示失败动作 | P1 |
| 跟进确认、缺口卡、提案卡本轮没有到达可判定画面 | `s3/s5/s6` 的截图仍是处理中或文件缺失；不能把超时记成组件缺失 | 重测，不先改组件 |
| 幂等、恢复、状态冲突的 JSON 结论弱于正文 | `o3` 只记录两次 409；`o5` 最终是 `ACTIVE/waiting=none`；`o7` 的不同载荷场景只做了代码核对 | 补测试，不记为关闭 |

已观察到且本轮无需返工的行为：会议确认卡完整渲染；无别名主导的双候选进入 `OBJECT_SELECTION` 并写入正确客户；明确无下一步按 `EXPLICITLY_NONE` 与原因提交，并触发整稿重评分；过期 `action_id` 返回 409 和最新任务投影。

## 2. 优化项

### O1 · 历史回执兼容，恢复最近任务（P0）

**现状**

`CRM-Client/src/schemas/assistant-contracts/index.ts` 的拒绝回执只接受新枚举，并强制 `proposal_key`。`loadRecentTasks` 对整组任务做 `z.array(...).parse`，一条旧数据失败后静默得到空列表。结果是所有历史回放入口消失，而不只是那一条旧任务不可开。

**合同**

- 新写入继续使用新枚举和稳定 `proposal_key`，不恢复旧值作为新写入格式。
- 读取必须兼容已落库的 `refused:opportunity`，且 `proposal_key` 可缺。
- 一条不可识别的历史回执只降级该任务或该回执，不能清空其余最近任务。
- 列表解析失败必须可见，不能静默显示“没有历史任务”。
- 不在本项做破坏性数据改写。若后续要统一旧数据，单独写可重跑迁移，并保留原始审计证据。

**验收**

1. 构造含 `{"kind":"refused:opportunity"}` 的任务列表：侧栏仍显示其他任务。
2. 打开该历史任务不抛页面级异常；旧拒绝回执以只读历史状态展示。
3. 新拒绝回执仍要求新枚举和 `proposal_key`，服务端契约测试继续拒绝新写入的旧形状。

### O2 · 活动分类预算与可恢复等待（P0）

**现状**

分类、整理、评分串行发生在同一次处理中。分类本身实测 90–200 秒以上，`model_transport timeout=120s` 仍让页面在 180 秒截图时看不到类型卡、跟进确认卡或改类型入口。阶段清单和“已 N 秒”提示已显示，但用户无法判断是仍在运行、已超时，还是应该刷新。

**合同**

- 分类使用低延迟模型或独立更短预算，不能占用完整整理模型的 120 秒以上预算。
- 每个模型调用有独立超时、持久错误码和当前阶段；超时是 `RETRYABLE_DEPENDENCY_FAILURE`，不是业务缺口，不生成假的字段问题。
- 180 秒内必须到达下列三者之一：类型卡、确认卡、可见的技术失败卡。超过该时限仍无持久事件即判定失败。
- 超时后任务保持可恢复，显示“结果待核对/重试”；刷新读取同一 turn，不创建另一任务。
- 已有 `activity_kind` 的改类型后重描述不得再次分类。此项本轮被超时阻断，修复后单独复测。

**验收**

同一组第三轮混合文本各跑一次：无信号文本到达类型卡；明确跟进文本到达跟进确认卡；明确会议文本到达会议卡。三次均记录模型名、分类耗时、首个可操作事件时间。任一模型超时必须出现失败卡和原任务重试入口。

### O3 · 统一客户不存在的失败语义（P1）

**现状**

确认阶段消息“没有找到客户”命中 `FailureCard`，提供“换个名称重试 / 结束本次记录”。缺口阶段服务端消息“未找到对应客户，请核对并提供客户准确名称。”被当成普通字段缺口，失败动作不出现。`isFailureMessage` 和 `isCustomerNotFound` 都只匹配前一种文案。

**合同**

- 两种时机都持久记录 `NOT_FOUND`，不依赖前端关键字猜测。
- 页面都明确“尚未写入”。
- 都提供“修改客户名称”和“结束本次记录”。
- 输入框可以改名，但不能只剩自由输入而没有结束动作。
- 权限不足、系统故障和多个候选不得复用这张未找到卡。

**验收**

同一不存在名称分别在客户缺口轮和确认写轮触发：错误码都是 `NOT_FOUND`，活动数不增加，两张卡都有上述两个动作。另用 `AMBIGUOUS`、`PERMISSION_DENIED`、依赖超时各一条，确认卡片类型不串。

### O4 · 别名主导客户的产品边界（P1，先确认）

**现状**

“睿狐有限公司”正确进入双候选选择；别名事实主导的“睿狐”以 0.94 分自动选择 top-1。后者符合当前解析阈值，但报告已指出两个同名公司场景可能需要用户确认。

**待产品选择**

- 方案 A：保持现状。别名事实达到现有自动选择阈值就绑定，用户仍可在确认卡看到客户并取消。
- 方案 B：同一规范化简称命中两个及以上有权客户时强制 `OBJECT_SELECTION`，即使某个别名分数更高。

未选择前不改解析阈值。两种方案都必须保留无权限候选不可见、确认时按冻结客户 ID 重验权限。

### O5 · 补齐被超时掩盖的界面验收（P1）

以下项目本轮没有足够证据，不进入实现修复：

| 项 | 本轮证据 | 重测必须看到 |

### O6 · 校正第三轮过宽的通过结论（P1）

| 原结论 | 实际可确认范围 | 仍需补测 |
| --- | --- | --- |
| `o3` 幂等 pass | 正文称一次冻结、一个 `submission_id/fingerprint`、一次 `confirm_write`、activities 928–931 各自唯一 | JSON 实际只记录两次 409。须保留首个 turn、重放 turn、活动 ID 和回执，并证明同键不同载荷返回 409 且无第二笔活动 |
| `o5` 刷新 pass | 刷新后原任务还在 | 最终 `ACTIVE` 且 `waiting=none` 没有证明处理卡或等待卡恢复。须在持久 `RUNNING` 或某种等待态刷新，并看到同一状态和可继续动作 |
| `o7` 冲突 pass | 过期 `action_id` 返回 409 和最新投影 | 同请求 ID、不同载荷仍需真实双请求，不能只引用 `accept_submit` 代码路径 |
| `s1` 最近任务 pass | 空闲布局、空态、输入和“新任务”可见 | 截图没有“客户 · 类型”历史行；O1 修复后再验 |

## 3. 实施顺序

1. 先做 O1。它是确定回归，且阻断所有历史任务验收。
2. 做 O2 的分类预算、超时错误和 180 秒验收探针。
3. 用 O2 的可完成链路重跑 O5、O6，只修复重新观察到的确定偏差。
4. 做 O3 的稳定错误码和卡片动作。
5. O4 等产品在方案 A/B 中选择后再改。

O1 可以独立发布。O2 未达到 180 秒判定标准前，不进行新一轮完整 UI 验收，避免再次把模型等待记录成组件故障。

## 4. 不纳入本轮

- 不宣告 A1–D2 或 X1–X2 已通过。第三轮没有覆盖 MySQL 双会话并发、进程崩溃后的命令对账、混合来源档案发布和 20–50 条样本。
- 不把活动 928–931 的 API 成功扩大解释为提案执行、失败回滚或“已写入”徽标已验证。
- 不因本轮修改旧入口，不自动完成历史任务，不自动发布客户档案。
- 不把模型低分继续追问改成放宽 60 分门槛；低分仍只问一个真实缺口。
