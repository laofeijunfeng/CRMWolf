# 交互编排策略

适用于销售助手 `/assistant` 的澄清、选择、补字段、写入确认、结果反馈和下一步建议。相关规范：[Agent UI 平台边界](agent-ui-platform.md) · [结构化输出](structured-output.md) · [销售助手命令契约](assistant-command-contract.md)。

## 一个需要回应的交互

同一轮的最终回复最多包含一个需要用户响应的主交互。只读 facts、既有权威回执及同一交互的确认、取消或次要编辑动作不另算交互。不得同时要求确认、补字段、选择对象或决定另一条建议。

## 优先级与顺序

1. 语义澄清；涉及现有等待归属不明时先厘清，不擅自切换任务。
2. 客户或业务对象选择；多候选或无可靠证据先选择或澄清，不以模型输出当作授权。
3. 必填字段补充；质量低于 60 分只问一个关键缺口，达到 60 分即停止质量补问，但仍需独立通过下一步行动门禁。
4. 业务写入确认；客户与必填字段未确定时不确认。确认前不得声称已完成；确认后也仅以持久结果为准。
5. 权威结果反馈；确定失败不在同一回复混入另一张可提交确认卡，结果待核对不提供写入重试。
6. 下一步建议决策；跟进是本次主产物时，先确认并提交活动，再独立处理商机创建、推进等建议。
7. 普通总结。

活动提交后，跟进后资料提议（联系人、开票抬头、部署信息）排在商机与后续任务建议之前。实体表单打开时，用户打字只算补充字段，不写入；「待补充」是导航入口，不算第二个主交互。

低优先级动作不能抢占当前交互；已成功的活动回执可以作为只读事实与一个后续交互共存。

## 服务端权威

模型输出候选意图、证据、字段和建议；服务端确定当前任务、唯一等待、签发动作及允许的提交。回复文案不是恢复状态或授权写入的依据。继续操作绑定当前任务、动作和版本，不从历史卡片或含糊的“是”中猜测命令。等待卡打开时不插入查询；低置信、状态冲突、目标不明时不自动推进。

本规范不要求特定编排框架或 LangGraph 映射。任务、轮次和冻结命令的持久状态用于恢复；界面不依赖模型复述状态。
