# 系统设置页面化优化方案

- **日期：**2026-08-31
- **状态：**方案评审稿
- **范围：**账户设置、系统配置入口、系统配置下的管理 Sheet 页面化
- **目标：**在不改变现有 CRMWolf 视觉语言和业务权限边界的前提下，将账户与团队级配置统一收拢到“系统设置”入口，并将长期管理型 Sheet 改造成可独立访问的页面。

## 1. 结论摘要

建议采用“统一入口 + 设置专用侧栏 + 独立子路由 + 页面内保留短任务弹窗”的结构：

1. 用户菜单只保留一个“系统设置”入口，所有已登录用户均可进入；个人用户至少可以访问“账户设置”。
2. 进入系统设置后，复用现有应用左侧 Sidebar 的外壳和样式，但将 `NavMain` 切换为设置导航；顶部增加“返回系统”，固定返回 `/agent`，不依赖浏览器历史。
3. 当前 `/settings` 作为新的规范入口，`/account`、`/system-config` 以及已有旧管理路径保留兼容重定向，避免历史书签和外部链接失效。
4. 角色、成员、审批、采购方式、获客来源、AI、通知、第三方集成等当前一级 Sheet 改为页面；其中新建、编辑、分配角色、修改密码等短时操作可继续使用 Dialog，不能把长期管理容器继续放在 Sheet 中。
5. “不用搜索”理解为设置导航不新增搜索框；角色、成员、审批流程、采购方式、获客来源等业务列表已有的搜索/筛选仍应保留，否则会损失管理效率。

## 2. 当前实现与主要问题

### 2.1 当前入口

- `NavUser.vue` 中同时提供“账户设置”和“系统配置”两个入口。
- `/account` 是独立的账户信息页面，包含：个人信息、账户详情、安全设置、飞书登录授权。
- `/system-config` 是配置卡片网格，点击卡片后打开 Sheet。
- `/roles`、`/approval-flows`、`/procurement-methods`、`/ai-config`、`/notification-config`、`/team-members` 等路径目前主要重定向回 `/system-config`，没有真正的独立管理页面。

### 2.2 当前系统配置 Sheet

| 当前模块 | 当前承载 | 现有业务能力 | 建议页面名称 |
| --- | --- | --- | --- |
| 角色管理 | `RoleSheet` | 角色搜索、创建/编辑、权限配置、删除 | 角色管理 |
| 审批流程管理 | `ApprovalFlowSheet` | 流程搜索、状态/授权类型/单据类型筛选、详情、启停、手工创建、AI 创建 | 审批流程管理 |
| 获客来源 | `AcquisitionSourceSheet` | 名称搜索、启用状态筛选、新建/改名/排序、启停 | 获客来源 |
| 采购方式管理 | `ProcurementSheet` | 方式搜索、状态筛选、新建/编辑/删除、阶段模板、AI 创建 | 采购方式管理 |
| AI 配置 | `AIConfigSheet` | 供应商、接口地址、密钥、模型、连接测试、说明 | AI 配置 |
| 通知配置 | `NotificationSheet` | 飞书群 Webhook、群名称、通知测试、说明 | 通知配置 |
| 团队成员 | `TeamMemberSheet` | 成员搜索、邀请、角色分配、改名、重置密码、移除、邀请码 | 团队成员 |
| 第三方集成 | `LoginIntegrationSheet` | 飞书应用配置、事件订阅、机器人相关配置 | 第三方集成 |

### 2.3 业务与交互问题

1. **入口分裂：**个人账户设置和团队/系统配置分别位于用户菜单，用户难以判断“我应该去哪里改设置”。
2. **管理容器使用了临时承载：**角色、成员、审批流程、采购方式等具有列表、筛选、分页/排序、编辑和权限控制，属于长期管理任务，不符合抽屉“保留当前页面上下文的补充任务”边界。
3. **缺少可定位 URL：**Sheet 没有稳定的子路由，无法直接收藏、刷新后恢复、使用浏览器前进/后退，也不利于权限审计和问题定位。
4. **页面级权限不完整：**当前系统配置入口有统一访问判断，但各卡片采用组件内 `v-if`；路由本身没有按具体模块声明权限。页面化后需要把“能看到菜单”和“能访问页面”统一为同一份配置。
5. **信息层级不清：**当前卡片网格把个人信息、成员管理、流程规则、基础资料、AI 和集成混在同一层，随着模块增加会继续膨胀。
6. **移动端容易失去上下文：**大 Sheet 叠加 Dialog 的方式在窄屏下滚动、关闭和返回路径不清晰。

## 3. 目标信息架构

### 3.1 用户感知的入口

用户菜单改为：

- 系统设置
- 退出登录

“系统设置”不应只对管理员显示，因为普通用户仍需要查看和维护自己的账户信息。进入后再按权限显示团队/系统级菜单。

移动端底部导航中的“账户设置”也改为“系统设置”，目标路径统一为 `/settings`。

### 3.2 设置侧栏

桌面端进入 `/settings/**` 后，现有应用 Sidebar 的主导航区切换为设置导航：

```text
系统设置
├── 返回系统
├── 账户与成员
│   ├── 账户设置
│   ├── 团队信息与安全 （团队信息查看/管理能力）
│   ├── 团队成员       （成员查看/管理能力）
│   └── 角色管理       （角色查看/管理能力）
├── 流程与业务配置
│   ├── 审批流程管理   （流程查看/管理能力）
│   ├── 获客来源       （获客来源查看/管理能力）
│   └── 采购方式管理   （采购方式查看/管理能力）
└── 智能与集成
    ├── AI 配置        （AI 配置查看/管理能力）
    ├── 通知配置        （通知查看/管理能力）
    └── 第三方集成      （集成查看/管理能力）
```

设计约束：

- “系统设置”是侧栏顶部的上下文标题，不作为普通列表项重复占用空间。
- “返回系统”是确定性导航，返回应用默认工作台 `/agent`；不使用 `router.back()`，避免用户从新标签页或深链接进入时返回失效。
- 侧栏菜单使用现有 `SidebarMenuButton`、活动态、折叠和无障碍语义，不引入另一套导航样式。
- 不新增设置导航搜索框。模块少且有稳定分组，直接浏览比再增加一层搜索更清晰。
- 无权限的模块不显示；如果用户直接访问无权限 URL，显示统一 403 状态并提供“返回系统设置”操作，而不是将其静默重定向到不相关页面。

### 3.3 路由建议

以 `/settings` 为规范入口：

```text
/settings                  -> 重定向到 /settings/account
/settings/account          -> 账户设置
/settings/team            -> 团队信息与安全
/settings/members          -> 团队成员
/settings/roles            -> 角色管理
/settings/approval-flows   -> 审批流程管理
/settings/acquisition-sources -> 获客来源
/settings/procurement-methods -> 采购方式管理
/settings/ai               -> AI 配置
/settings/notifications    -> 通知配置
/settings/integrations     -> 第三方集成
```

兼容策略：

- `/account` -> `/settings/account`
- `/system-config` -> `/settings/account` 或 `/settings`（建议 `/settings`，由设置壳再进入默认页）
- `/roles` -> `/settings/roles`
- `/approval-flows` 及其 create/edit 深链 -> 对应设置页面和查询参数/子路由
- `/procurement-methods` 及 stages 深链 -> `/settings/procurement-methods`
- `/ai-config`、`/notification-config`、`/team-members` -> 对应设置子路由

旧路径只做兼容，不继续作为新代码的跳转目标。

## 4. 页面化方案

### 4.1 页面统一骨架

所有设置子页面统一采用现有 V2 页面结构：

1. TopBar 显示当前页面标题；设置壳负责左侧上下文导航。
2. 页面主体沿用 `$wolf-page-padding-v2`、`$wolf-bg-page-v2`、现有 Card、ListCard、Button、Dialog 和状态组件。
3. 页面标题下可有一句简短说明，不新增装饰性大 Banner。
4. 管理型页面使用“工具栏 + 内容列表 + 加载/空态/错误态”；需要跨页处理时使用现有 DataTable/分页契约。
5. 新建、编辑、确认、分配角色等短时操作继续用 Dialog；复杂、多阶段、需要复制链接或浏览器定位的任务使用页面。

页面化不是简单把 `<SheetContent>` 换成 `<div>`，每个页面应补齐独立路由、刷新恢复、权限、错误态和可分享 URL。

### 4.2 各页面建议

#### 账户设置（P0）

直接迁移现有 `AccountSettings.vue` 的内容，保留：

- 个人信息
- 账户详情
- 安全设置与修改密码 Dialog
- 飞书登录授权

这是所有登录用户的默认设置页，不依赖管理员权限。

#### 团队成员（P0）

将 `TeamMemberSheet` 的成员列表提升为页面。保留现有成员搜索、邀请、角色分配、改名、重置密码、移除成员和邀请码能力。邀请/分配/重置等操作仍可用 Dialog，页面承担列表上下文和刷新。

按成员查看/管理能力控制可见和访问。成员列表应明确区分当前团队，切换团队后刷新页面数据。

#### 角色管理（P0）

将 `RoleSheet` 提升为页面。角色列表是长期管理对象，支持搜索、创建/编辑、权限配置和删除。权限配置可先保留 Dialog/Sheet 作为局部编辑器，但角色列表本身必须有独立 URL。

角色页面的查看、编辑、删除和权限配置应按拆分后的角色管理能力控制，页面迁移不改变现有授权含义。

#### 审批流程管理（P0）

将 `ApprovalFlowSheet` 提升为列表页，保留流程名称/编码搜索、状态、授权类型、单据类型筛选、启停和详情能力。

审批流程创建/编辑包含基本信息、适用条件和节点配置，复杂度高，建议第二阶段改为独立表单页：

```text
/settings/approval-flows/new
/settings/approval-flows/:flowId/edit
```

AI 创建可以先保留为对话框入口，但创建成功后应跳转或打开对应编辑页，避免在对话框内承载完整流程维护。

#### 获客来源（P1）

将 `AcquisitionSourceSheet` 提升为页面。保留搜索、启用状态筛选、新增、改名、排序和启停。由于获客来源同时服务线索和客户，是共享基础资料，应在说明中明确“影响线索与客户表单选项”。

#### 采购方式管理（P1）

将 `ProcurementSheet` 提升为页面。采购方式及阶段模板属于商机推进规则，不应继续隐藏在抽屉中。建议增加独立阶段模板路由或页面内明确的详情入口：

```text
/settings/procurement-methods/:methodId/stages
```

删除、启停和阶段模板批量保存继续使用现有确认和表单反馈。

#### AI 配置（P1）

将 `AIConfigSheet` 提升为表单页。保留供应商、接口地址、密钥、模型、连接测试和配置说明。密钥字段不回显明文，保存/测试过程需有 loading、错误和成功反馈。

AI 配置属于团队级高敏感设置，菜单、路由、页面操作和后端接口应统一使用独立的 AI 配置查看/管理能力控制。

#### 通知配置（P1）

将 `NotificationSheet` 提升为表单页。保留飞书群 Webhook、群名称、通知测试和配置说明。页面中明确通知触发范围和失败后的处理方式。

通知配置和审批流程有业务关联，但不建议塞进审批流程页面；它是跨流程的通道设置，应保持独立页面。

#### 第三方集成（P1）

将 `LoginIntegrationSheet` 提升为页面。飞书应用、事件订阅和机器人配置按 Card 分组，复用现有表单样式。保存后显示当前配置状态，敏感配置只显示“已配置”状态。

#### 团队信息与安全（P0，当前方案遗漏项）

当前团队名称、邀请码和团队成员操作实际共同构成团队管理能力，不应全部隐藏在“团队成员”页面中。建议增加“团队信息与安全”设置页或在“账户与成员”下增加独立分组，至少覆盖：

- 团队名称等基础信息维护；
- 当前团队邀请码查看、重新生成、复制和失效提示；
- 团队所有者展示、所有权转移和转移后的权限重算；
- 成员邀请的有效期、重复邀请、撤销邀请和已加入状态；
- 团队停用/删除的产品边界（若本期不做，也要明确为后续能力，不能在页面化时遗漏）；
- 所有者、最后一个管理员和当前操作者的保护规则。

团队切换、无团队和邀请链接进入是独立的生命周期场景：用户没有当前团队时仍可进入账户设置，但不能看到团队级数据；切换团队后设置菜单、页面数据和权限必须整体重新计算，不能沿用上一个团队的缓存。

## 5. 权限设计

建议建立一份设置导航注册表，同时驱动菜单可见性、路由 meta 和页面空/禁用状态，避免继续维护多套 `v-if` 判断：

```ts
interface SettingsNavItem {
  key: string
  label: string
  path: string
  requiredPermissions?: readonly string[]
}
```

权限规则：

- `/settings/account`：登录用户可访问。
- 其他页面：统一按权限码判断，不因页面化扩大权限；角色仅作为权限集合来源。
- 菜单隐藏是体验层控制；后端接口仍是最终授权边界。
- 路由守卫只负责提前拦截明显无权限访问，页面仍需处理接口返回的 401/403。
- `canAccessSystemConfig` 可以保留为“是否存在任何团队级设置权限”的辅助判断，但不应再作为整个设置页面唯一权限开关。

## 6. 统一权限模型

建议将系统设置相关入口统一改为以权限码作为最终授权依据，避免当前“权限码 + TEAM_ADMIN 角色硬编码”并存，导致菜单显示、路由访问和实际操作权限不一致。

### 6.1 权限模型原则

- 角色是权限集合或权限模板，权限码是菜单、路由、页面和操作按钮的统一判断依据。
- `TEAM_ADMIN` 继续保留为系统内置团队管理员角色，但应通过角色权限映射获得全部系统设置能力，前端和普通后端接口不再直接把 `TEAM_ADMIN` 作为唯一显隐条件。
- 团队所有者是团队权限体系的兜底主体：在当前团队内默认拥有全部团队级权限码（包括后续新增的团队设置权限），避免出现“没有权限进入角色管理，因而无法给自己或他人授权”的死胡同。该能力应自动反映到有效权限集合中，菜单、路由、按钮和普通后端接口仍统一按权限码判断。
- 账户设置属于登录用户的个人能力，登录用户默认可访问；团队级设置按当前团队的权限集合判断。
- 查看、管理和特殊操作权限需要拆分，避免出现“入口可见但保存/编辑时被拒绝”的情况。
- 当前团队切换后，所有设置菜单和页面权限必须重新按新团队权限计算；权限变更后应及时刷新或失效缓存。

### 6.2 设置模块权限能力

| 设置模块 | 查看/进入 | 管理或特殊操作 |
| --- | --- | --- |
| 账户设置 | 登录用户默认可访问 | 修改个人资料、密码和个人授权，遵循个人账户规则 |
| 系统设置入口 | 系统设置访问能力，或至少拥有一个已授权的团队设置模块 | 不直接赋予子模块管理能力 |
| 团队成员 | 成员查看能力 | 邀请、移除、分配角色、重置密码等成员管理能力 |
| 角色管理 | 角色查看能力 | 创建、编辑、删除角色及配置角色权限 |
| 审批流程 | 流程查看能力 | 创建、编辑、启停和配置审批节点 |
| 获客来源 | 获客来源查看能力 | 新增、编辑、排序和启停 |
| 采购方式 | 采购方式查看能力 | 新增、编辑、删除和维护阶段模板 |
| AI 配置 | AI 配置查看能力 | 修改配置、连接测试和敏感配置维护 |
| 通知配置 | 通知配置查看能力 | 修改配置和发送测试通知 |
| 第三方集成 | 集成查看能力 | 修改飞书应用、事件订阅和机器人配置 |
| 团队信息与安全 | 团队信息查看能力 | 修改团队信息、邀请码、所有权转移和团队生命周期操作 |

上述为产品能力划分，具体权限码命名在技术方案中统一定义；不得为同一能力同时维护角色硬编码和权限码两套判断。成员列表查看、邀请、角色分配、移除、改名、重置密码、邀请码管理和所有权转移不能共用一个过大的“团队管理”权限。

### 6.3 角色判断的保留边界

角色不作为常规入口和操作权限的第二套机制，但以下属于领域安全规则，可以继续使用角色语义：

- 防止移除团队最后一个管理员、转移团队所有权等团队安全约束。
- 审批节点配置的审批人身份匹配，例如销售总监、财务人员或团队管理员。
- 团队创建、所有权转让等只属于团队所有者的高风险操作。

这些例外必须在产品规则中明确标注，不能混用于普通菜单显隐。

### 6.4 权限一致性与迁移要求

- 设置导航、页面直接访问、页面内操作按钮和后端接口必须遵循同一套权限语义。
- 用户能看到某个入口时，至少应具备该页面的查看能力；用户能执行保存、编辑、删除或测试时，必须具备对应操作权限。
- 迁移期间由 `TEAM_ADMIN` 角色继承全部新的权限能力，确保现有管理员不丢权；已有自定义角色需要完成权限映射补齐后再切换。
- 团队创建时，创建者自动成为团队所有者并获得全部团队级权限码；转移所有权后，新所有者自动获得完整权限，原所有者按新的角色权限重新计算，避免权限长期无条件保留。
- 团队所有者不可被移除、禁用或降权为无法管理团队的状态；转移所有权必须经过明确确认，并保留审计记录。
- 迁移完成后，重点验证通知配置、团队成员、第三方集成等目前存在角色硬编码或权限复用的模块，避免入口可见但接口操作失败。

## 6.5 业务边界与配置生效规则（本轮业务审查补充）

页面化只调整设置的组织方式，不应把所有“看起来像配置”的能力都塞入系统设置。结合当前客户、商机、合同、回款、发票、License 和审批链路，补充以下边界：

### 6.5.1 设置管理与业务操作分离

- **审批流程管理**维护流程模板、适用单据类型、节点和启停；**审批中心**维护正在运行的审批实例、待办和已处理记录，两者不能合并为一个页面。
- 合同、回款计划、回款记录、发票申请、发票重开、License 申请属于业务操作页面，不因其存在审批权限而迁入系统设置。
- 发票抬头是客户级业务资料，不是团队级系统配置。它应继续在客户/发票业务上下文中维护；删除或修改抬头不能破坏已有发票申请中的抬头快照，历史记录应保留原始开票信息。
- 销售看板、业务旅程看板、客户、线索和商机列表属于业务工作区，不应为了“页面统一”迁入设置侧栏；其筛选、数据权限和操作入口继续遵循各自业务权限。

### 6.5.2 采购方式、阶段与获客来源的引用保护

- 采购方式会影响客户默认值、商机创建和阶段推进。修改默认值只对后续新建业务生效，已有客户、商机及阶段快照不得被静默改写。
- 已被客户或商机引用的采购方式、阶段模板不能直接物理删除；应优先停用，并展示使用量、影响范围和替代方案。删除/停用阶段前要检查进行中的商机。
- 阶段模板的编码、排序、默认起始阶段和版本变更需要校验；涉及在途商机的调整应提供影响评估、迁移确认和失败回滚/重试路径。
- 获客来源同时被线索和客户使用。已被引用的来源不得物理删除；停用后不出现在新建表单，但历史数据仍显示原值，排序只影响后续选项和展示。
- 系统初始化来源与自定义来源的可编辑、可停用和可删除边界要明确，并在列表中展示线索数、客户数等使用量。
- AI 生成采购方式或阶段模板只能生成草稿/预览，必须由有权限的用户确认后才写入正式配置。

### 6.5.3 审批配置的运行影响

- 审批流程模板与审批实例解耦。停用流程不影响已发起实例，但新提交业务不能再匹配该流程；页面必须明确“对新提交生效/不影响存量”的提示。
- 修改流程节点前检查流程是否已被合同、回款、发票或 License 等业务类型使用，并提示对新实例和存量实例的影响。
- 审批节点引用的角色必须是当前团队有效角色；删除、停用或修改角色前检查其是否被流程引用，避免形成无人审批节点。
- 流程创建、编辑、启停、节点配置、查看运行实例和通知配置应分别定义能力；不能用角色管理权限或审批流程编辑权限覆盖其他模块。
- 通知是跨业务流程的通道配置，应使用独立通知权限。测试通知属于有外部副作用的操作，需单独授权或二次确认，并展示发送目标、消息类型、结果和失败原因。

### 6.5.4 AI、飞书集成与个人绑定的影响边界

- AI 配置可能同时影响 Agent、审批 AI、采购方式 AI 等多个入口；保存或切换供应商前要展示影响范围，连接测试不得修改正式配置。
- 个人飞书绑定属于个人账户设置；团队飞书应用、登录、事件订阅和机器人属于团队级集成设置，二者必须在产品上明确区分。
- 替换或禁用团队飞书应用前要说明对飞书登录、机器人、事件订阅和已绑定用户的影响；敏感字段只展示已配置状态，不回显明文。
- 集成保存、测试失败、回调异常和重试结果需要可见；对外发送或回调相关操作应留下审计记录。

### 6.5.5 团队、权限与平台边界

- 团队所有者的“全部权限”仅指当前团队范围内的有效业务和设置权限，不自动扩展为跨团队或平台运维权限；权限定义需要标明团队级/平台级作用域。
- 团队所有权转移、团队删除/停用、邀请码重置、批量成员移除、角色权限大范围修改等属于高风险操作，必须二次确认、明确影响范围并记录审计日志。
- 成员角色、权限和团队状态变化后，当前会话、其他已登录会话和权限缓存的生效时点要明确；至少保证下一次操作不会继续使用已撤销权限。
- 无当前团队、团队被停用、用户被移除或权限刚被撤销时，设置页需要给出可理解的状态和下一步，不得展示上一个团队的数据。

### 6.5.6 页面状态与数据安全补充

- 表单离开前存在未保存修改时要提示，重复点击保存要幂等；保存成功后刷新页面仍应显示服务端最终值。
- 密钥、Webhook、飞书 App Secret 等敏感字段采用“已配置/未配置”状态和显式替换流程；空值提交不能误清空已有密钥，除非用户明确确认。
- 页面加载、无数据、无权限、接口失败、部分保存失败、权限变化和配置冲突都要有明确反馈；失败不能静默回退到旧 Sheet 或错误模块。

## 7. 设计系统与组件复用要求

本次页面化改造必须以 CRMWolf 现有样式架构、交互模式和组件体系为基准，优先参考系统中已经上线且稳定使用的页面，确保系统设置各页面与现有业务页面在布局、视觉、操作和反馈上保持统一，不进行脱离现有产品语言的单独设计。

### 7.1 样式与交互统一原则

- 页面布局优先复用现有 Sidebar、TopBar、页面标题区、Card、ListCard、DataTable、Dialog、表单区域、分页、筛选栏和状态反馈模式。
- 页面间统一使用现有的颜色、字体、间距、圆角、边框、阴影、按钮层级、图标和响应式规则；不得因页面化重新引入一套视觉规范。
- 列表页统一延续现有 DataTable 的搜索、筛选、排序、分页、批量操作、空状态和错误反馈行为；表单页统一延续现有字段布局、校验、保存中、保存成功和保存失败反馈。
- 原 Sheet 中已有的业务能力和操作顺序应在页面化后保持一致；仅调整长期管理内容的承载层级，不随意改变业务规则和用户心智。
- 桌面端、窄屏和移动端需要沿用系统已有的布局适配方式，避免新增横向滚动、操作按钮溢出或弹窗层级混乱。

### 7.2 组件选型与复用约束

组件选型遵循以下优先级：

1. **优先使用 CRMWolf 已封装的业务组件和基础组件。**如果系统中已经存在满足需求的组件、页面模式或交互封装，必须统一复用，不得重复实现同类组件。
2. **系统没有对应封装时，使用 shadcn-vue 官方组件。**组件能力和交互细节参考官方文档：https://www.shadcn-vue.com/docs/components
3. **使用 shadcn-vue 组件前必须先在项目组件层完成封装。**页面不得直接大面积拼装或散落使用 shadcn-vue 原始组件；应结合 CRMWolf 的设计 Token、业务状态、权限、校验和反馈约定，形成项目内可复用的统一组件后再使用。
4. **禁止自行造轮子或引入新的 UI 组件库。**对于已有组件能覆盖的场景，不新增平行实现；对于 shadcn-vue 能覆盖的场景，不自行开发同类基础组件。

### 7.3 页面化落地要求

- 角色、成员、审批流程、获客来源和采购方式等列表页面，统一复用项目已有的表格、筛选、分页、操作菜单和确认反馈组件；如现有能力不足，再基于 shadcn-vue 封装项目级组件补齐。
- AI 配置、通知配置和第三方集成等表单页面，统一复用项目已有的输入框、选择器、密码/敏感字段、按钮、提示、校验和结果反馈组件；敏感信息继续遵循脱敏展示规则。
- Dialog、Sheet、Popover 等浮层只承载新建、编辑、确认、分配等短时任务；浮层样式和关闭、返回、保存反馈必须复用现有封装或项目级封装组件。
- 新增的项目级组件需要具备明确的使用边界、统一的参数和事件约定，并在至少两个相关页面中优先复用，避免为单个页面定制一次性组件。
- 页面验收不仅检查功能是否可用，还要检查组件来源、视觉一致性、交互一致性、响应式表现和可访问性。

## 8. 分阶段实施

### Phase 0：壳与入口（P0）

- 新增 `/settings` 设置父级路由和设置布局状态。
- 用户菜单、移动端溢出菜单统一改为“系统设置”。
- `NavMain` 在设置路由下切换为设置导航。
- 增加“返回系统”，默认返回 `/agent`。
- 保留所有旧路由重定向。

### Phase 1：高频管理页面（P0）

- 账户设置页面迁移至 `/settings/account`。
- 团队信息与安全、团队成员、角色管理、审批流程管理页面化。
- 保留内部 Dialog 作为短任务承载。
- 建立页面级权限、加载态、空态、错误态和直接 URL 测试。

### Phase 2：基础资料与团队配置（P1）

- 获客来源、采购方式管理页面化。
- 补齐采购阶段模板深链。
- 统一列表工具栏和分页/筛选行为。

### Phase 3：智能与集成（P1）

- AI 配置、通知配置、第三方集成页面化。
- 梳理敏感字段脱敏、保存反馈、连接测试和失败重试。

### Phase 4：清理与验证（P1）

- 删除设置入口对旧 Sheet 容器的依赖（保留兼容组件或逐步移除）。
- 检查所有旧深链、刷新、浏览器前进/后退、权限切换和移动端布局。
- 更新导航与页面组件测试、路由测试和权限契约测试。

## 9. 验收标准

### 入口和导航

- 用户菜单不再同时出现“账户设置”和“系统配置”，只出现“系统设置”。
- 普通用户进入系统设置后能看到并访问账户设置。
- 有权限的管理员只看到自己有权访问的设置模块；所有者在当前团队内不会因角色配置缺失而失去进入设置和修复权限的能力。
- 设置侧栏顶部有“返回系统”，点击后稳定进入 `/agent`。
- 桌面端复用现有 Sidebar；移动端不出现横向滚动，设置导航仍可达。

### 路由和页面

- 每个管理模块都有独立 URL，可刷新、收藏和直接打开。
- 旧路径仍能正确重定向，不产生循环重定向。
- 管理型一级内容不再依赖打开 Sheet 才能访问。
- 新建/编辑等短任务关闭后返回原列表，并保留列表筛选和分页状态。

### 业务和权限

- 页面化前后 API、团队隔离和权限含义不变。
- 无权限直接访问页面时显示明确 403，不泄露数据。
- 设置导航、页面访问、操作按钮和后端接口使用统一的权限码授权语义；常规权限不再同时依赖权限码和 `TEAM_ADMIN` 硬编码。
- `TEAM_ADMIN` 在迁移后通过角色权限映射获得完整设置能力；最后一个管理员保护、所有权转移、团队生命周期和审批人身份匹配等领域安全规则仍按产品规则生效。
- 团队所有者进入当前团队后默认拥有全部团队级权限码，但不包含跨团队/平台级权限；转移所有权后，新所有者自动获得同等能力，原所有者按新权限集合生效。
- 列表原有搜索/筛选继续有效；设置导航本身不增加搜索框。
- 页面实现优先使用 CRMWolf 已封装组件；缺少对应能力时使用 shadcn-vue，并先封装为项目级组件后再在页面中复用，不得自行造轮子或引入新的 UI 组件库。
- 加载、空数据、无筛选结果、接口失败和保存失败均有明确反馈。

## 10. 风险与取舍

1. **一次性全量迁移风险高：**建议按 Phase 0–3 逐步迁移，先建立壳和路由，再搬运页面内容。
2. **Sheet 与页面并存期间可能重复维护：**每个模块页面上线后，设置卡片立即改为路由入口，不再保留同一业务的两套入口。
3. **权限不一致风险：**菜单权限、路由权限和 API 权限必须共用模块注册表和后端权限契约，不能只依赖前端隐藏。
4. **“不用搜索”的理解风险：**本方案不做设置导航搜索，但保留管理列表内部已有搜索/筛选；如果产品意图是连业务列表搜索也取消，需要另行评估效率和数据规模，不建议默认删除。
5. **页面化不等于视觉重做：**优先复用现有 V2 Token、Card、ListCard、DataTable、Dialog、Sidebar 和 TopBar，避免同时引入新视觉体系。

## 11. 推荐决策

建议确认以下决策后进入实施：

- 规范入口采用 `/settings`，默认页为 `/settings/account`。
- “系统设置”作为所有用户可进入的统一入口，团队级菜单按权限显示。
- 设置导航使用现有应用 Sidebar，顶部固定“返回系统”。
- 一级管理 Sheet 全部页面化，内部短时编辑 Dialog 暂时保留。
- 不新增设置导航搜索框，但不删除角色、成员、审批流程、采购方式、获客来源等列表原有搜索/筛选。
- 统一使用权限码控制菜单、页面和操作；角色作为权限集合，仅保留明确的团队安全规则例外。
