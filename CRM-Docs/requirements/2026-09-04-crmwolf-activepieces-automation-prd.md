## 一、摘要

CRMWolf 当前已经具备客户、商机、合同、回款、发票、License、审批和 Agent 等核心能力，但系统的自动化能力仍主要散落在业务代码和固定页面流程中。随着产品继续发展，用户会提出越来越多的需求：

- 客户或商机发生变化后，自动通知相关人员；
- 某个销售阶段超过若干天没有跟进时，自动提醒；
- 合同、回款等审批规则由业务管理员自行配置；
- 审批通过后自动通知财务、同步 ERP 或创建任务；
- 按天、按周或按业务日期执行提醒；
- 将 CRMWolf 与飞书、ERP、财务、项目管理、邮件等系统打通；
- 在自动化流程中调用 Agent，生成摘要、建议或草稿。

如果每个需求都由 CRMWolf 自己开发页面、定时器、流程引擎、重试机制和连接器，会持续重复建设基础设施，也会使系统越来越难以扩展。因此，本项目引入 Activepieces 作为独立的自动化编排运行时，CRMWolf 提供 CRM 领域 API、事件、权限、审批、业务状态和审计能力。

本项目不是把 CRMWolf 做成另一个通用 Zapier，也不是把 CRM 的业务规则外包给第三方工作流平台，而是形成清晰的职责分工：

> **Activepieces 决定“什么时候做、按什么顺序做、条件是什么、失败如何重试”；CRMWolf 决定“业务是否允许做、谁可以做、最终业务状态是什么”。**

第一阶段优先采用飞书式的轻量产品体验：

```text
当……
如果……
那么……
```

底层不自研工作流画布、Scheduler、Worker、Retry Engine 或执行引擎，而是直接使用 Activepieces；CRMWolf 只建设必要的控制面和集成边界，保证租户、权限、幂等、审计与业务一致性。

## 二、问题定义

### 2.1 用户问题

1. **提醒依赖人工记忆**：销售需要自行记住商机阶段、回款日期和跟进节奏，容易漏跟进。
2. **审批规则变更成本高**：审批流程固化在系统配置或代码中，金额、团队、业务类型变化时需要产品或研发介入。
3. **跨系统协作断裂**：CRM 内部状态发生变化后，财务、ERP、项目或即时通讯系统不会自动同步。
4. **自动化需求碎片化**：不同客户需要不同的通知对象、延迟时间、条件和外部动作，固定功能难以覆盖。
5. **Agent 缺少可组合的落点**：Agent 可以生成内容，但缺少标准化的触发、审批、发送和回写流程。
6. **现有审批与自动化边界不清**：如果让外部工作流直接修改 CRM 数据，可能绕过权限、审批和审计；如果所有流程都由 CRM 内部实现，又会持续扩大自研范围。

### 2.2 产品问题

CRMWolf 缺少一个面向业务管理员的、低门槛的自动化配置能力，同时缺少一个稳定、受控、可演进的外部编排集成边界。

### 2.3 非目标

本项目不追求：

- 自研一个通用工作流平台；
- 复制 Activepieces 的画布、连接器市场和执行引擎；
- 让 Activepieces 成为 CRM 核心业务状态的最终事实来源；
- 用自动化替代 Agent 对话、确认和高风险写入门禁；
- 一次性迁移所有历史审批实例和所有固定业务流程。

## 三、产品目标与成功标准

### 3.1 产品目标

#### 目标 G1：让用户可以自行配置轻量自动化

管理员或销售运营无需研发介入，即可基于 CRM 事件、业务日期或定时器配置通知、任务、字段更新、Webhook 和审批动作。

#### 目标 G2：以 Activepieces 为运行时，避免重复造轮子

CRMWolf 不自研通用流程执行层，优先复用 Activepieces 已有的 Flow Builder、Trigger、Condition、Schedule、Delay、Retry、Run History 和连接器能力。

#### 目标 G3：保证 CRM 业务安全边界

所有 CRM 业务读取和写入均经过 CRMWolf 受控 API/Piece；外部 Flow 不能直连数据库、绕过权限或直接改变合同、回款、发票、License 等核心状态。

#### 目标 G4：先解决审批，再扩展提醒和跨系统自动化

第一批验证以新合同审批为主，同时验证一个主动提醒和一个外部 Webhook 场景，建立从事件触发到结果回写的完整闭环。

#### 目标 G5：为未来嵌入式体验和多连接器生态保留架构空间

先支持独立 Activepieces 服务与 CRMWolf 关联；在权限、租户、凭据和运行历史边界稳定后，再评估 Embed Builder、单点登录和更深度的白标体验。

### 3.2 成功标准

| 维度 | 第一阶段目标 |
|---|---|
| 配置效率 | 管理员可在 10 分钟内配置一个“商机阶段变化后提醒”自动化 |
| 可靠性 | 同一事件重复投递不会重复创建业务任务或重复产生不可逆副作用 |
| 安全性 | Activepieces 无法绕过 CRMWolf API 权限写入 CRM 数据库；越权写入目标为 0 |
| 审批闭环 | 新合同两级审批可完成提交、审批、驳回、回调、最终状态更新 |
| 可观察性 | 用户可以知道自动化是否启用、最近一次运行结果和失败原因 |
| 可恢复性 | 可对失败 Flow 进行重试或人工处理，且不重复成功的副作用 |
| 隔离性 | 不同团队的 Flow、连接、业务事件和运行上下文互不可见 |
| 可演进性 | 新增一个 CRM 业务动作不需要修改 Activepieces 执行引擎 |

## 四、产品定位与核心原则

### 4.1 产品定位

> **CRMWolf 是一个以 CRM 业务对象和业务事件为中心，提供主动提醒、审批编排、跨系统同步与受控 Agent 动作的 CRM-native Automation 平台。**

底层使用 Activepieces，产品价值不在于重新实现通用编排能力，而在于：

- 把 CRM 业务对象和事件做成可理解、可组合的能力；
- 把权限、审批、幂等和审计做成可靠边界；
- 用模板和领域化动作降低配置门槛；
- 让用户可以逐步从简单提醒扩展到跨系统流程。

### 4.2 核心原则

1. **不自研通用执行引擎**：Activepieces 是第一阶段的一等运行时。
2. **CRM 是业务事实来源**：客户、商机、合同、回款、发票、License 和审批决定最终以 CRMWolf 为准。
3. **Flow 通过 API/Piece 访问 CRM**：禁止直连 CRM 数据库和自由 SQL。
4. **业务动作要深，不要暴露内部表结构**：提供“创建跟进任务”“发起合同审批”等业务动作，而不是暴露通用 CRUD。
5. **轻量优先**：产品体验优先围绕“当—如果—那么”，不一开始把用户暴露给复杂画布。
6. **高风险动作必须受控**：核心状态变更、对外发送和批量写入需要权限、幂等，必要时需要审批或人工确认。
7. **单一状态机原则**：Activepieces 负责自动化 Flow 状态；CRMWolf 负责审批决定和业务状态，不维护两套相互竞争的审批状态机。
8. **可观测、可重试、可审计**：自动化不是黑盒后台任务。
9. **按阶段开放能力**：先管理员和销售运营，后续再扩大普通用户和外部租户范围。
10. **底层可替换，产品契约稳定**：CRMWolf 的事件、动作、身份和审计契约不能绑定到 Activepieces 的内部数据库模型。

## 五、用户与使用角色

### 5.1 系统管理员

- 配置团队级自动化；
- 管理 Flow 启停、连接凭据和发布权限；
- 查看运行失败和审计记录；
- 管理哪些用户可以创建、编辑、发布自动化。

### 5.2 销售运营 / 业务负责人

- 配置销售阶段提醒、回款提醒和审批规则；
- 复用模板并调整条件、时间和通知对象；
- 查看自动化对业务过程的影响。

### 5.3 销售人员

- 接收自动提醒和待办任务；
- 查看与自己负责客户、商机相关的自动化结果；
- 在审批中心处理自己有权限处理的审批。

### 5.4 审批人

- 在 CRMWolf 审批中心查看单据上下文；
- 批准、驳回、撤回或补充意见；
- 不需要为了处理 CRM 审批而进入 Activepieces Builder。

### 5.5 运维 / 客服

- 查看 Flow Run、错误、重试和死信；
- 帮助客户定位连接器、权限、回调或业务校验问题；
- 无权替代业务用户做审批决定。

## 六、用户故事

1. 作为系统管理员，我希望查看团队内所有自动化，以便了解当前有哪些业务规则正在自动运行。
2. 作为系统管理员，我希望控制谁可以创建、编辑、发布和停用自动化，以便避免未经授权的业务副作用。
3. 作为销售运营，我希望从模板创建“商机阶段变化后提醒”，以便无需研发即可落地销售跟进节奏。
4. 作为销售运营，我希望按金额、负责人、团队和业务状态配置条件，以便不同业务场景走不同路径。
5. 作为销售人员，我希望在商机长期没有跟进时收到提醒并自动生成任务，以便减少漏跟进。
6. 作为销售负责人，我希望每周收到团队销售风险摘要，以便及时发现停滞商机和逾期回款。
7. 作为财务人员，我希望合同审批通过后自动收到通知或同步信息，以便减少跨系统手工传递。
8. 作为合同发起人，我希望提交合同后能看到审批是否已启动，以便避免业务单据已保存但审批未生效的误解。
9. 作为审批人，我希望继续在 CRMWolf 审批中心处理审批，以便在熟悉的业务上下文中做出决定。
10. 作为审批人，我希望看到合同金额、客户、商机和审批路径，以便基于完整上下文审批。
11. 作为系统管理员，我希望配置不同金额区间的审批路径，以便满足团队实际的授权制度。
12. 作为系统管理员，我希望审批驳回、撤回和回调失败有明确状态，以便能够定位和恢复异常。
13. 作为集成管理员，我希望客户创建后调用外部系统 Webhook，以便减少重复录入。
14. 作为集成管理员，我希望外部系统返回关联 ID 后回写 CRMWolf，以便后续同步能够关联同一条记录。
15. 作为集成管理员，我希望外部接口临时失败时自动重试，以便不因短暂网络问题导致数据不同步。
16. 作为运维人员，我希望查看某次自动化运行的触发事件、步骤、错误和重试记录，以便快速排查问题。
17. 作为运维人员，我希望手动重试失败运行，并知道该重试可能产生哪些副作用，以便安全恢复流程。
18. 作为业务管理员，我希望自动化只读取和修改我有权限访问的 CRM 数据，以便满足团队隔离和权限要求。
19. 作为业务负责人，我希望调用 Agent 生成跟进摘要或沟通草稿，以便提升销售效率而不直接放开高风险自动发送。
20. 作为业务负责人，我希望自动化的每次发布、停用、运行和业务写入都有审计记录，以便满足追责和复盘要求。
21. 作为产品管理员，我希望未来可以在 CRMWolf 内嵌或统一跳转到 Flow Builder，以便用户不必理解多个系统的关系。
22. 作为平台开发者，我希望新增 CRM 动作时只需增加稳定的 API/Piece 契约，而不需要修改自动化执行引擎。
23. 作为平台开发者，我希望未来可以替换底层自动化引擎而不改变 CRM 业务模型，以便降低长期技术锁定风险。

## 七、产品范围

### 6.1 第一阶段 MVP 范围

#### 触发器

1. 客户创建；
2. 客户更新；
3. 商机创建；
4. 商机阶段变化；
5. 跟进任务逾期；
6. 回款计划到期或逾期；
7. 合同提交审批；
8. 定时触发（按团队时区）；
9. Webhook 触发；
10. 手动测试/手动运行。

1. 业务对象字段匹配；
2. 数值区间（如合同金额）；
3. 枚举/状态匹配；
4. 团队、负责人、客户类型匹配；
5. 是否存在最近跟进；
6. 时间窗口判断；
7. AND/OR 基础组合；
8. 审批结果判断。

#### 动作

1. 发送站内通知；
2. 发送飞书/邮件通知（第一阶段可先支持已有通知能力或 Webhook）；
3. 创建跟进任务；
4. 更新白名单 CRM 字段；
5. 添加或移除标签；
6. 调用 HTTP/Webhook；
7. 发起 CRM 审批；
8. 查询 CRM 业务上下文；
9. 在审批完成后更新受控业务状态；
10. 调用 Agent 生成摘要、建议或草稿；
11. 记录自动化结果和关联业务对象。

#### 运行能力

- Flow 草稿、发布、暂停、恢复、复制、归档；
- Activepieces Flow 与 CRMWolf 团队、业务对象的关联；
- 流程版本绑定；
- Flow Run 状态投影；
- 失败原因和重试入口；
- 业务对象详情页展示关联自动化；
- 审批中心展示关联 Flow 信息；
- 审计日志和 trace_id 关联。

### 6.2 后续范围

- CRMWolf 内嵌 Activepieces Builder；
- 模板中心和行业模板；
- 更多中国区 SaaS 连接器；
- OAuth 连接和连接健康检查；
- 批量同步、游标、冲突解决；
- 复杂循环、子流程和并行分支；
- Agent 辅助生成 Flow 草稿；
- 面向外部客户的开放 API 和开发者文档；
- 运行成本、配额和高级治理。

## 八、典型用户场景

### 场景 A：商机阶段变化后的主动提醒

```text
当：商机进入“报价”阶段
如果：最近 3 个工作日没有跟进
那么：给负责人发送飞书提醒，并创建一个跟进任务
```

预期价值：销售不需要人工记忆跟进节奏，管理者可以通过模板统一销售动作。

### 场景 B：合同两级审批

```text
当：新合同提交审批
如果：合同金额 ≤ 10 万
那么：销售总监审批 → 财务审批 → 更新合同为已通过 → 通知发起人
```

```text
当：新合同提交审批
如果：合同金额 > 10 万
那么：销售总监审批 → 财务负责人审批 → 总经理审批 → 更新合同为已通过
```

审批人在 CRMWolf 审批中心处理任务，Activepieces 负责条件、顺序、等待和审批完成后的后续动作。

### 场景 C：客户创建后的外部同步

```text
当：客户创建
如果：客户类型为正式客户
那么：调用外部 ERP/项目系统 API 创建客户，并回写外部系统 ID
```

外部系统调用失败时由 Activepieces 重试，最终失败在 CRMWolf 中可见；重复事件不能重复创建外部客户。

### 场景 D：回款逾期后的 Agent 辅助跟进

```text
当：回款计划逾期
那么：获取客户与商机上下文 → Agent 生成催收建议和沟通草稿
      → 发送给负责人确认 → 通过后再发送给客户
```

Agent 只生成建议或草稿，不直接拥有任意外部发送权限；对外发送属于高风险动作，需要用户确认或审批。

### 场景 E：周期性销售摘要

```text
每周一 09:00
→ 汇总本团队本周到期回款、逾期跟进和阶段停留商机
→ 调用 Agent 生成摘要
→ 发送给销售负责人
```

## 九、用户体验设计

### 8.1 配置入口

第一阶段不在 CRMWolf 自己实现通用画布。提供以下入口：

1. **自动化列表**：查看当前团队的 Flow、状态、负责人、最近运行结果；
2. **从模板创建**：直接进入 Activepieces Flow 配置；
3. **编辑自动化**：跳转或嵌入 Activepieces Builder；
4. **业务对象详情页**：查看该客户、商机、合同关联的自动化和最近运行；
5. **审批中心**：查看审批对应的 Flow、版本和运行状态。

### 8.2 配置体验

用户看到的业务抽象应尽可能接近：

```text
当 [选择对象和事件]
如果 [添加条件]
延迟/定时 [可选]
那么 [选择动作]
```

技术上可由 Activepieces 画布承载，但 CRMWolf 应通过模板、命名、说明和动作目录隐藏不必要的技术复杂度。

### 8.3 模板

第一阶段提供至少以下模板：

1. 商机进入报价阶段后 3 个工作日未跟进提醒；
2. 回款到期前 7 天提醒负责人；
3. 回款逾期后通知负责人和销售负责人；
4. 客户创建后调用 Webhook 同步外部系统；
5. 新合同两级审批；
6. 合同审批通过后通知财务；
7. Agent 生成客户跟进摘要草稿；
8. 每周销售风险摘要。

模板必须带有：

- 适用对象；
- 所需字段；
- 所需权限；
- 会产生哪些副作用；
- 使用哪个连接；
- 如何测试；
- 如何暂停或恢复。

### 8.4 状态展示

Flow 状态至少包括：

- 草稿；
- 已发布/运行中；
- 已暂停；
- 运行成功；
- 运行失败；
- 等待审批；
- 等待外部回调；
- 需要人工处理；
- 已归档。

CRMWolf 不复制 Activepieces 的全部节点详情，但应展示对业务有价值的信息：

- 关联 Flow 名称和版本；
- 触发业务对象；
- 最近运行时间和结果；
- 当前是否等待审批；
- 失败原因摘要；
- 重试/跳转到 Flow Run 的入口；
- 关联的审批实例和审计记录。

## 十、审批改造方案

### 9.1 核心决策

第一阶段将“审批流程的配置和编排”交给 Activepieces，但不会把审批业务事实交给 Activepieces。

| 能力 | Activepieces | CRMWolf |
|---|---|---|
| 流程配置、条件和节点顺序 | 负责 | 提供模板和业务动作 |
| 等待、延迟、重试、运行历史 | 负责 | 展示业务投影 |
| 审批人解析 | 不负责 | 负责 |
| 审批任务和审批中心 | 不负责 | 负责 |
| approve/reject 决定 | 不负责 | 负责 |
| 审批记录和审计 | 不负责 | 负责 |
| 合同/回款/发票最终状态 | 不负责 | 负责 |
| 审批后通知和外部动作 | 编排 | 通过受控 API/Piece 执行 |

### 9.2 推荐流程

```text
业务单据创建/提交
  → CRMWolf 以业务事务保存单据
  → 启动对应 Activepieces Flow
  → Flow 根据金额、类型、团队等条件分支
  → 调用 CRMWolf Action 创建审批任务
  → CRMWolf 解析审批人并写入 Approval / ApprovalRecord
  → 审批人在 CRMWolf 审批中心 approve/reject
  → CRMWolf 记录最终决定并发送签名回调
  → Activepieces 恢复 Flow
  → Flow 执行审批后动作
  → CRMWolf 通过受控 API 最终更新业务状态
```

### 9.3 状态归属

- **Activepieces Flow Run**：自动化编排、等待、重试和节点执行的事实来源；
- **CRMWolf Approval**：业务审批实例和当前业务审批上下文；
- **CRMWolf ApprovalRecord**：审批人、动作、意见、时间和审计事实；
- **业务对象状态**：合同、回款、发票、License 等最终业务状态的唯一事实来源。

不能让 Activepieces 和 CRMWolf 同时维护同一套“当前审批节点/审批是否完成”的最终状态并互相同步。

### 9.4 迁移策略

1. 旧审批流程和存量审批实例继续按现有逻辑运行；
2. 第一阶段只让“新合同审批”走 Activepieces；
3. 保留现有审批中心作为审批人的统一入口；
4. 先实现线性两级审批，再加入条件分支、超时提醒、驳回重提和撤回；
5. 验证稳定后，再迁移回款、发票、License、商机等业务类型；
6. 最后再决定是否废弃旧的 `ApprovalFlow` 配置页和旧流程写入接口。

### 9.5 事务一致性

Activepieces 不参与 CRMWolf 数据库事务。业务提交与 Flow 启动必须设计可恢复机制：

- 业务单据提交成功后生成自动化启动记录；
- 由可靠投递机制触发 Activepieces，而不是在业务请求中直接依赖同步调用成功；
- 启动请求携带幂等键；
- Activepieces 启动失败进入重试/待处理状态；
- Flow 启动成功后回写 Flow ID、Flow Version、Run ID；
- 用户可看到“业务已保存但自动化尚未启动”的明确状态；
- 不能因为第三方暂时不可用而回滚已经成功提交的 CRM 业务事实，除非该业务明确要求强一致并由专门接口处理。

## 十一、系统架构

### 10.1 目标架构

```text
┌──────────────────────────────────────────┐
│ CRMWolf                                  │
│ CRM 业务对象 / 权限 / 审批 / Agent       │
│ API / Domain Events / Outbox / Audit     │
└──────────────┬───────────────────────────┘
               │ Signed Webhook / API / Piece
               ▼
┌──────────────────────────────────────────┐
│ Activepieces                             │
│ Builder / Trigger / Condition / Delay    │
│ Schedule / Retry / Run History / Connect │
└───────┬───────────────┬──────────────────┘
        │               │
        ▼               ▼
   飞书/邮件/ERP     Agent API / 外部系统
```

### 10.2 CRMWolf 需要建设的控制面

CRMWolf 不建设执行引擎，但需要建设薄的 Automation Control Plane：

1. **租户映射**：CRMWolf `team_id` 与 Activepieces project/workspace 的映射；
2. **Flow 映射**：保存 Activepieces Flow ID、版本、用途、创建者和状态；
3. **事件目录**：定义哪些 CRM 事件可被触发，字段和权限是什么；
4. **动作目录**：定义可被 Flow 调用的业务动作及其输入输出；
5. **连接管理**：记录连接用途、所属团队、状态和授权范围，不保存不必要的明文凭据；
6. **身份映射**：区分 Flow 配置者、事件触发者、审批人和外部连接账户；
7. **运行投影**：把 Flow Run 与客户、商机、合同、审批实例关联；
8. **回调管理**：校验签名、幂等消费、记录回调结果；
9. **审计**：记录发布、启停、修改、运行、回调和高风险动作；
10. **能力白名单**：按团队、角色和业务动作控制可用范围。

### 10.3 集成方式

#### POC 阶段

- Activepieces 作为独立服务部署；
- CRMWolf 通过 Webhook 和 REST API 接入；
- 使用私有/自维护 `CRMWolf Piece` 或 HTTP 动作；
- 先通过外部入口打开 Activepieces Builder；
- 不依赖深度修改 Activepieces 内部源码。

#### 产品化阶段

- 评估 Activepieces Embed Builder/Embed SDK；
- 增加 CRMWolf 内部单点登录或短期授权跳转；
- 将模板、CRM 业务动作和运行投影集成到 CRMWolf；
- 明确 Community Edition、Enterprise 和 Embed 能力的许可边界；
- 保持 CRMWolf 与 Activepieces 数据模型解耦，避免未来替换引擎时重写 CRM 业务层。

## 十二、事件与动作契约

### 11.1 事件契约

每个可触发事件都必须定义稳定的业务契约，而不是把数据库变更直接暴露给 Flow。

事件至少包含：

- `event_id`：全局唯一事件 ID；
- `event_type`：如 `opportunity.stage_changed`；
- `occurred_at`：事件发生时间；
- `team_id`：租户/团队边界；
- `actor_id`：触发事件的用户或系统身份；
- `entity_type` / `entity_id`：业务对象引用；
- `entity_version`：业务对象版本或更新时间；
- `payload`：经过筛选的业务字段；
- `trace_id`：跨 CRM、Flow、外部系统的追踪 ID；
- `schema_version`：事件契约版本。

第一批事件：

- `customer.created`；
- `customer.updated`；
- `opportunity.created`；
- `opportunity.stage_changed`；
- `follow_up.overdue`；
- `payment_plan.due`；
- `payment_plan.overdue`；
- `contract.submitted_for_approval`；
- `approval.approved`；
- `approval.rejected`；
- `approval.cancelled`。

### 11.2 动作契约

第一批动作应是有业务语义的深模块接口：

- `get_customer_context`；
- `get_opportunity_context`；
- `create_follow_up_task`；
- `send_internal_notification`；
- `send_feishu_notification`；
- `update_opportunity_fields`；
- `add_customer_tag`；
- `start_crm_approval`；
- `get_approval_context`；
- `finalize_approved_business_object`；
- `call_external_webhook`；
- `request_agent_summary`；
- `create_agent_draft`。

每个动作必须定义：

- 输入字段和输出 schema；
- 读取/写入的业务对象；
- 所需权限；
- 是否产生外部副作用；
- 幂等键规则；
- 可重试错误与不可重试错误；
- 是否要求审批或人工确认；
- 审计字段；
- 关联的 `team_id`、actor 和业务对象。

禁止提供一个无边界的“任意 CRM API”“任意数据库写入”或“任意 SQL”动作。

### 11.3 身份模型

必须区分四类身份：

1. **Flow 配置者**：创建、编辑和发布 Flow 的人；
2. **事件触发者**：导致事件发生的用户或系统；
3. **动作执行身份**：Flow 调用 CRM API 时使用的服务身份和原始 actor 上下文；
4. **外部连接账户**：调用飞书、ERP、邮件等系统时使用的授权连接。

默认规则：

- Flow 创建者不自动拥有所有执行权限；
- CRM 动作必须由 CRM 重新校验团队和业务权限；
- 审批动作必须使用真实审批人身份；
- 外部连接按团队、用途和 scope 隔离；
- 日志中不得输出凭据、token 和敏感业务数据。

### 11.4 幂等

所有可能产生副作用的动作都必须接受幂等键。建议组合：

```text
idempotency_key = team_id + event_id + flow_id + flow_version + action_key
```

对于按日期执行的提醒，幂等键还要包含业务日期；对于外部同步，需要保存外部系统关联 ID 和同步状态。

## 十三、权限、安全与合规

### 12.1 权限

新增权限建议至少包括：

- `automation:read`：查看自动化；
- `automation:create`：创建草稿；
- `automation:edit`：修改草稿；
- `automation:publish`：发布/启停；
- `automation:run`：手动运行和重放；
- `automation:connections:manage`：管理连接；
- `automation:runs:read`：查看运行历史；
- `automation:audit:read`：查看审计。

CRM 业务动作继续使用现有业务权限，不因为 Flow 调用而放宽。

### 12.2 安全边界

- Activepieces 不直连 CRMWolf MySQL；
- 所有 Webhook 校验签名、时间戳和重放窗口；
- 回调使用一次性或短期 token，并绑定 team、flow、run 和业务对象；
- 外部请求限制目标域名、超时、请求体大小和敏感字段；
- Agent 不默认拥有对外发送和核心状态写入权限；
- 高风险动作提供审批/HITL 门禁；
- Flow 版本发布后不可静默改变历史运行语义；
- 运行日志脱敏，凭据由 Activepieces 或专用密钥存储管理；
- 记录 Flow 配置变更、发布人、发布版本、连接变更和业务副作用。

### 12.3 数据隔离

每个团队至少需要隔离：

- Flow；
- 模板实例；
- 连接和凭据；
- 事件；
- 运行历史；
- 审批关联；
- Agent 上下文；
- 日志和审计。

## 十四、可靠性与可观察性

### 13.1 失败分类

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 临时外部失败 | 429、503、网络超时 | 按策略重试，必要时退避 |
| 永久业务失败 | 权限不足、字段无效、业务状态不允许 | 不盲目重试，提示用户处理 |
| 配置失败 | Flow 未发布、连接失效、字段被删除 | 阻止运行或标记为需要修复 |
| 回调失败 | 签名错误、重复回调、Flow Run 不存在 | 记录审计，幂等处理，进入人工排查 |
| CRM 暂时不可用 | API/数据库短暂故障 | 重试并保留关联上下文 |

### 13.2 运行可观察性

CRMWolf 侧至少可查询：

- Flow ID、版本、Run ID；
- 触发事件和业务对象；
- 当前步骤和等待原因；
- 开始/结束时间；
- 重试次数和下一次重试时间；
- 错误分类和错误摘要；
- 关联审批 ID；
- 外部系统关联 ID；
- 最终业务结果；
- trace_id。

### 13.3 副作用保护

- 先完成查询和条件判断，再执行不可逆动作；
- 外部发送前尽量生成草稿；
- 核心业务写入由 CRMWolf API 事务完成；
- 重试必须能够识别已经成功的副作用；
- 手动重放时明确提示可能产生外部影响；
- 对外发送、批量写入和状态变更支持 allowlist 和审批门禁。

## 十六、分阶段路线图

### Phase 0：技术 POC（2–4 周）

目标：证明 Activepieces 能够作为 CRMWolf 的外部自动化运行时可靠工作。

交付：

1. 独立部署 Activepieces；
2. CRMWolf 与 Activepieces 的团队/项目映射；
3. 最小 CRMWolf Piece 或 HTTP API；
4. 一个 CRM 事件触发器；
5. 一个定时触发器；
6. 一个飞书/邮件/HTTP 动作；
7. 一个合同两级审批 Flow；
8. 签名回调、幂等和运行投影；
9. 失败、重复事件和服务重启测试。

通过标准：

- 可以创建、发布和运行 Flow；
- 可以完成新合同两级审批；
- 审批人仍在 CRMWolf 审批中心操作；
- Flow 恢复后不会重复创建审批任务；
- Activepieces 不访问 CRM 数据库；
- 运行失败可定位和恢复。

### Phase 1：轻量自动化 MVP

目标：面向管理员/销售运营提供可实际使用的自动化能力。

交付：

- 自动化列表和模板入口；
- CRM 事件目录；
- 受控 CRM 动作目录；
- 商机阶段提醒；
- 回款提醒；
- 合同审批模板；
- Webhook/HTTP 集成；
- Flow 状态和运行投影；
- 权限、审计、幂等和失败处理。

### Phase 2：产品化与嵌入体验

目标：降低用户进入 Activepieces 的门槛，让自动化成为 CRMWolf 的自然能力。

交付：

- Embed Builder 或统一单点登录；
- CRMWolf 内的模板中心；
- 自动化与业务对象详情页关联；
- 连接管理和 OAuth；
- 运行历史、重放和死信处理；
- 更多飞书、ERP、财务和项目系统适配；
- 完善租户、配额和数据保留策略。

### Phase 3：生态与复杂编排

仅在真实需求验证后考虑：

- 对外开放事件订阅和 API；
- 第三方开发者 Piece/Connector；
- 多租户集成市场；
- 长周期、多信号、补偿型业务流程；
- Activepieces 与其他 durable execution 方案的边界评估。

## 十七、验收标准

### 16.1 Flow 管理

- 管理员可以从模板创建 Flow；
- Flow 草稿和已发布版本有明确区分；
- 只有具备发布权限的用户可以启用 Flow；
- Flow 暂停后不再接收新的触发；
- 历史 Run 仍能关联到执行时的 Flow 版本；
- CRMWolf 可查询 Flow 与团队的关联关系。

### 16.2 事件触发

- CRM 业务事件包含稳定事件 ID、团队、对象和版本信息；
- 重复事件不会产生重复业务副作用；
- 事件触发失败可重试并可观测；
- 不同团队之间不能消费彼此事件；
- 业务对象删除、权限变化和版本过期时有明确处理结果。

### 16.3 审批

- 新合同可启动 Activepieces 审批 Flow；
- 条件分支能根据合同金额选择审批路径；
- CRMWolf 正确解析审批人并创建审批任务；
- 审批人在现有审批中心可以 approve/reject；
- 审批结果能可靠回调 Flow；
- 审批通过后由 CRMWolf 事务性更新合同状态；
- 驳回、撤回、重复回调、Flow 重试不会破坏审批记录；
- 旧审批实例不受影响。

### 16.4 外部动作

- HTTP/Webhook 动作支持超时、重试和失败分类；
- 外部系统成功后保存关联 ID；
- 重试不会重复创建外部对象；
- 凭据不会出现在日志和前端响应中；
- 外部动作使用正确的团队和连接身份。

### 16.5 Agent 动作

- Agent 可作为可选动作被 Flow 调用；
- Agent 失败不会直接改变核心业务状态；
- 对外发送和高风险写入有人工确认或审批门禁；
- Agent 输入上下文经过权限过滤和数据脱敏；
- Agent 生成结果可被后续节点消费并可追踪。

## 十八、测试策略

测试应优先通过公开业务边界验证外部行为，不测试 Activepieces 内部实现细节。

### 17.1 契约测试

- 事件 schema 和版本兼容；
- CRMWolf Piece 输入输出；
- 签名 Webhook 和回调协议；
- 错误码、重试语义和幂等键。

### 17.2 业务集成测试

- 商机阶段变化触发提醒；
- 合同提交启动审批 Flow；
- 两级审批完整通过；
- 驳回、撤回、重提；
- 回调丢失后重试；
- Activepieces 重启后恢复；
- 外部 429/503、超时和重复事件。

### 17.3 权限和隔离测试

- 非管理员不能发布 Flow；
- Flow 不能读取其他团队客户；
- Flow 不能绕过业务权限写入 CRM；
- 连接不能跨团队使用；
- 审批人不能被 Flow 配置者任意冒充；
- 高风险动作必须经过门禁。

### 17.4 回归测试

- 现有审批中心行为不变；
- 旧审批流程和存量审批实例继续可用；
- 合同、回款、发票、License 的原有状态联动不受影响；
- Agent 既有对话、确认和业务写入门禁不受影响。

## 十九、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| Activepieces 嵌入或白标许可不满足预期 | 产品化受阻 | 先采用独立服务；尽早核实 Community/Enterprise/Embed 授权 |
| Activepieces 与 CRM 同时维护审批状态 | 重复审批、状态不一致 | 明确状态归属，CRM 掌握审批决定，单向回调 |
| Flow 绕过 CRM 权限 | 数据泄露或错误写入 | 禁止直连 DB，所有动作走受控 API/Piece |
| 业务事务成功但 Flow 未启动 | 用户误以为审批已开始 | 建立启动记录、可靠投递、可见状态和重试 |
| 重试导致重复外部副作用 | 重复客户、重复通知 | 幂等键、外部关联 ID、动作级去重 |
| 用户面对通用画布过于复杂 | 使用率低 | 模板优先、领域化命名、分阶段开放节点 |
| 连接器能力不完整 | 集成体验不稳定 | 连接器能力矩阵、沙盒测试、优先支持 HTTP/Webhook |
| 运行历史跨系统分散 | 排查困难 | 在 CRMWolf 投影 Flow Run、审批和业务对象关联 |
| 用户自由配置高风险动作 | 误发、误改、越权 | allowlist、权限、审批/HITL、发布前校验 |
| 过早迁移所有旧审批 | 迁移成本和回滚风险高 | 仅新合同 POC，旧实例保留原路径 |

## 二十、待确认决策

以下事项不阻塞技术 POC，但必须在产品化前确认：

1. Activepieces 采用独立服务、嵌入 Builder，还是两者并存；
2. Activepieces 的租户隔离采用 project、workspace 还是独立实例；
3. 第一阶段是否直接支持用户自定义 Flow，还是仅允许模板复制和有限修改；
4. 飞书通知是复用 CRMWolf 当前团队配置，还是允许每个 Flow 使用独立连接；
5. 审批人是否始终在 CRMWolf 审批中心操作，还是后续支持 Activepieces Human Input；
6. Agent 动作第一阶段是只生成摘要/草稿，还是允许低风险字段自动回写；
7. 外部系统同步采用单向推送还是支持双向同步；
8. 是否需要把 Flow Run 全量同步到 CRMWolf，还是只投影与 CRM 业务对象相关的运行；
9. Community Edition 与 Enterprise/Embed 能力的商业许可边界；
10. 未来是否需要支持 n8n、Make、Zapier 等其他自动化引擎的互操作。

---

## 二十一、最终决策建议

1. **引入 Activepieces，不自研通用工作流引擎。**
2. **产品上先做飞书式轻量自动化，底层直接使用 Activepieces。**
3. **先以“新合同审批 + 商机提醒 + Webhook 同步”验证闭环。**
4. **Activepieces 负责编排，CRMWolf 负责业务事实、权限、审批决定、审计和最终写入。**
5. **现有审批中心保留为审批人的统一入口，先不把审批人迁移到 Activepieces UI。**
6. **不允许 Activepieces 直连数据库或绕过 CRM API。**
7. **先独立接入，后评估 Embed；不要因为技术上可嵌入就一开始绑定企业授权能力。**
8. **先建设稳定的事件、动作、身份、幂等和回调契约，再扩展连接器和 UI。**
9. **MCP 不属于本 PRD 范围。Agent 如需接入，先通过受控 Agent API/Piece 作为一个动作节点。**

最终产品路径为：

```text
CRMWolf 业务内核
  + Activepieces 自动化运行时
  + CRM 原生事件与动作
  + 审批/权限/审计控制面
  + 可选 Agent 节点
  = 面向 CRM 的开放自动化能力
```
