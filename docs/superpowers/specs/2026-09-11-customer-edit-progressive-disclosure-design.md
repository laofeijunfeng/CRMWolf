# 客户创建与编辑弹窗轻量化统一保存设计

- 日期：2026-09-14
- 状态：轻量化修订草案（用户已确认方向，待书面审阅）
- 范围：客户创建与编辑 Dialog、客户资料维护、客户状态资料字段、客户授权汇总字段
- 上游决定：更多客户信息继续保留；区内字段平铺；创建和编辑共用低频字段；底部只保留一个保存按钮；不提供清除授权日期操作；不增加保存前业务确认弹窗
- 相关规范：`CRM-Docs/design-system/patterns/form-page.md`、`CRM-Docs/design-system/patterns/detail-page.md`、`CRM-Docs/design-system/components/modal-sheet.md`、`CRM-Docs/design-system/components/input.md`

## 1. 背景与目标

客户记录中的行业、客户状态、授权类型和授权到期日都属于客户资料或客户授权汇总信息。当前弹窗把这些低频字段拆成多个业务卡片，并为状态、授权分别提供独立保存按钮，造成了不必要的认知负担。

重新核对现有业务链路后的结论：

- `跟进中`、`已成交`是客户状态值，不是审批流程；弹窗中的资料维护不应强制弹出“确认赢单”一类二次确认；
- 列表中的“赢单”“输单”“失效”等显式动作仍是既有操作入口，可能带有通知、原因记录或专用状态处理；它们不被本设计删除或改写；
- 客户授权类型和到期日是客户表中的授权汇总快照。直接补录只维护客户展示数据，不创建 License 申请、不进入审批、不修改正式 License 记录；后续重新申请 License 仍走现有 License 流程；
- 客户表已经具备行业、状态、授权类型和授权到期字段，不需要数据库 migration。

本设计目标：

1. 创建和编辑都能在“更多客户信息”中补充行业、客户状态、授权类型和授权到期日；
2. 更多区域默认收起，展开后字段与基础信息使用相同的平铺表单视觉；
3. 创建和编辑各自只保留一个底部保存按钮；
4. 一次客户资料保存请求原子写入本次修改的客户字段，避免前端串行调用多个接口；
5. 未填写的可选字段保持空值或后端默认值，不产生 License 或审批动作；
6. 保留显式赢单/输单/失效、公海和正式 License 流程的既有入口与语义；
7. 保持桌面、窄屏、键盘和读屏场景下的可恢复性。

## 2. 非目标与业务边界

本设计不做以下事情：

- 不在客户创建或编辑弹窗中创建 License 申请、提交审批、审批或发放 License；
- 不修改 `crm_license_applications` 中的申请、审批、授权码、部署、合同或授权人数；
- 不把客户授权汇总快照当作正式 License 事实；后续正式申请和发放仍走 License 流程；
- 不在弹窗中直接设置 `status=2`（输单）、`status=3`（失效）或公海状态；弹窗状态选择只允许 `0` 跟进中和 `1` 已成交；
- 不删除或改变列表“赢单”“输单”“失效”、退回公海、领取、移交等显式操作；
- 不删除现有专用状态/授权 API，它们可继续服务既有操作或外部调用；本弹窗使用统一客户资料写入契约；
- 不提供“清除授权到期日”按钮；弹窗只允许新增或改选日期，不能主动清空已有日期；
- 不增加保存前的业务确认弹窗；关闭时的未保存更改保护仍保留；
- 不引入新的通用字典或通用级联表单框架。

## 3. 方案选择

采用“基础信息首屏 + 更多客户信息默认收起 + 区内字段平铺 + 单一客户资料保存”的方案。

### 3.1 交互层级

```text
客户创建/编辑 Dialog
├── 基础信息（默认显示）
│   ├── 客户名称
│   ├── 所在城市
│   ├── 客户来源
│   ├── 公司规模
│   ├── 默认采购方式
│   └── 详细地址
├── 更多客户信息（默认收起，创建和编辑都可用）
│   ├── 行业
│   ├── 客户状态（只允许跟进中 / 已成交）
│   ├── 授权类型
│   ├── 授权到期日
│   └── 授权状态（只读派生展示）
├── 创建模式专属：联系人信息
└── Dialog Footer
    ├── 取消
    └── 保存客户 / 保存客户资料
```

“更多客户信息”仍使用有文字的按钮，不使用只有图标的入口。已有低频值显示“已填写 N 项”；创建模式中未填写的可选字段不计数。

### 3.2 为什么保留“更多”但取消内部业务卡片

低频字段需要可发现，但不需要让用户先理解三个业务模块。一次折叠控制首屏密度；展开后将行业、状态和授权字段作为同一客户表单中的连续字段展示，减少视觉分割和操作路径。

字段仍可以有轻量辅助说明：

- 状态字段下方说明只允许跟进中与已成交；输单和失效使用原有专用操作；
- 授权字段下方用一行说明告知“这里只维护客户授权汇总，不会创建 License 申请或修改正式 License 记录”；
- 不使用独立警示卡片、独立确认按钮或独立保存按钮强化流程感。

### 3.3 为什么采用一个普通资料保存契约

这次调整不是单纯兼容前端接口，而是按实际业务语义收敛交互：弹窗中的字段都是客户资料维护内容，用户希望一次保存本次客户信息修改。因此创建和编辑应使用一个普通客户资料写入请求：

- 创建：一个 `POST /v1/customers/` 写入基础资料、可选行业、可选状态和可选授权汇总；
- 编辑：一个 `PUT /v1/customers/{id}` 以 dirty diff 写入本次变化字段；
- 编辑请求只递增一次客户 `version`，避免同一次保存因为多个接口串行递增多次；
- 状态资料维护不发送显式“赢单”通知，不创建审批；显式列表动作仍使用既有专用入口；
- 授权资料维护不触碰 `LicenseApplication`，正式 License 申请流程完全独立；
- 后端继续保留专用状态/授权 API，避免影响既有调用者，但本弹窗不再把它们暴露为用户操作按钮。

这样用户看到的是一次保存，数据层也确实是一次客户资料提交，而不是把多个流程按钮藏在一个按钮后面。

### 3.4 事务与失败语义

- 创建请求是一个客户创建原子：请求失败不创建半成品客户，表单输入保留供重试；
- 编辑请求是一个客户资料更新原子：请求成功则本次字段一起成功，失败则本次修改整体不生效；
- 客户智能档案刷新、操作日志等后处理失败不回滚已提交的客户事实，沿用现有异步/后处理边界；
- 409 乐观锁冲突保留当前输入，并提供获取最新数据或保留输入继续编辑；
- 不再需要“普通资料成功但授权失败”的前端部分成功分支，因为弹窗内字段由一次客户资料写入统一提交。

## 4. 字段与业务规则

### 4.1 基础资料

继续支持现有基础字段：

| 字段 | 创建 | 编辑 | 未填写语义 |
|---|---:|---:|---|
| `account_name` | 必填 | 必填 | 不允许为空 |
| `city` | 必填 | 必填 | 不允许为空 |
| `address` | 可选 | 可选 | 空值 |
| `company_scale` | 按现有创建规则 | 保留历史未知值 | 创建未选为空；编辑未触碰不覆盖 |
| `source_public_id` | 可选/按现有来源规则 | 可选 | 不选择时为空或保持原值 |
| `default_procurement_method_id` | 可选 | 可选 | 不选择时为空或保持原值 |

编辑必须使用 dirty diff：未修改字段不得因为折叠、未加载或表单初始化而被提交为 `null` 或空字符串。

### 4.2 行业

行业继续使用数据库层级接口 `GET /v1/industries/hierarchy`，不使用旧硬编码枚举作为编辑选项。

- 支持一级行业分组和二级行业选择；一级无子项时允许选择一级 code；
- 搜索同时匹配一级和二级名称；
- 触发器展示完整路径，例如“互联网 / 企业服务”；
- 请求只保存稳定行业 `code`；
- 当前客户行业已停用或不在活动层级时保留原值，并展示详情接口提供的 `industry_info`；停用项不可作为新选项选择；
- 行业层级加载失败只禁用行业控件并显示重试，其他客户字段仍可编辑和保存；
- 创建和编辑均可选填行业；未选择时创建请求不传行业，编辑未触碰时不提交行业变更。

### 4.3 客户状态

弹窗中的状态是客户资料字段，但只开放安全范围：

```text
0：跟进中
1：已成交
```

规则：

- 创建时状态下拉可选 0/1；未选择时后端默认 0（跟进中）；
- 编辑时当前为 0 或 1 可修改为另一值；
- 当前为 2 或 3 时只展示当前状态，不允许从弹窗覆盖；
- 不允许在弹窗中设置输单、失效或公海状态；
- 通过弹窗普通资料保存修改 0/1 时，只记录客户资料前后值并刷新客户上下文，不弹出赢单确认、不创建审批、不发送显式列表赢单通知；
- 列表中的“赢单”“输单”“失效”等显式动作保持原有行为，包括其已有原因、通知和专用处理。

后端普通创建/更新契约只接受 `0 | 1` 状态值；专用状态接口继续负责既有显式状态动作。

### 4.4 授权汇总

授权字段表示客户授权汇总，不代表正式 License 记录：

| 字段 | 交互 | 规则 |
|---|---|---|
| `license_type` | 试用 / 正式下拉 | 可选；只有汇总信息，不触发 License 流程 |
| `license_expiry_date` | 日期选择 | 可选；只能新增或改选，不提供清除按钮 |
| 授权状态 | 只读文字/徽章 | 由日期和类型实时计算 |

派生状态继续遵循：

```text
到期日为空                         → 未授权
到期日早于今天                     → 已过期
到期日有效且授权类型为 TRIAL        → 试用
到期日有效且授权类型为 OFFICIAL     → 正式
```

约束：

- 创建时两个字段均可不填；未填写则保存为空；
- 编辑时未触碰授权字段不提交；触碰任一字段时以当前完整授权组合提交，避免部分组合覆盖；
- 到期日非空时必须有授权类型，避免形成无类型授权快照；
- 到期日为空时，弹窗不提供清除操作；其他专用数据修复/API 仍可按既有契约处理空值；
- 直接补录不创建 `LicenseApplication`、审批实例、授权码或正式发放记录；
- 后续重新申请 License 使用现有 License 申请、审批和发放流程；正式发放回写客户快照的既有规则保持不变；
- 保存成功提示使用“客户资料已更新”，不使用“License 已发放”等容易混淆的文案。

## 5. 数据流与接口边界

### 5.1 创建

前端创建请求扩展为可选字段：

```json
{
  "account_name": "示例客户",
  "city": "上海",
  "industry": "internet.enterprise",
  "status": 1,
  "license_type": "TRIAL",
  "license_expiry_date": "2026-12-31",
  "primary_contact": {}
}
```

实际请求只包含用户填写的可选字段。后端 `CustomerCreate`：

- `status` 接受 `0 | 1`，默认 `0`；
- `industry` 继续校验有效行业 code；
- `license_type` / `license_expiry_date` 进行组合校验；
- 在一个客户创建事务中写入客户字段；
- 不创建 License 申请或状态变更事件。

### 5.2 编辑

前端以 `expected_version` 携带本次 dirty diff：

```json
{
  "expected_version": 12,
  "city": "上海",
  "status": 1,
  "license_type": "TRIAL",
  "license_expiry_date": "2026-12-31"
}
```

- 未变化字段不提交；
- 行业、状态和授权均作为客户资料变更的一部分提交；
- 后端在锁定并刷新客户后校验版本，再一次性更新字段并递增一次 `version`；
- `CUSTOMER_UPDATED` 审计记录包含实际变化字段及机器可读 before/after；
- 成功后沿用客户主数据 partial refresh；
- 专用 `/lifecycle-status`、`/license-snapshot` 路由保留给既有调用者，但弹窗不再直接调用。

### 5.3 前端组件边界

- `CustomerFormDialog.vue`：管理创建/编辑共有字段、更多区域、统一保存、dirty diff、错误和关闭保护；
- `IndustryHierarchySelectField.vue`：只管理行业层级搜索、分组、展示、选择和可访问性；
- `customer.ts` / schema：扩展创建与更新类型，继续对响应进行 Zod 校验；
- 不把行业级联逻辑塞入 `SelectField`；
- 不新增通用“多业务保存”抽象，因为本次弹窗使用单一客户资料提交。

## 6. 保存与并发模型

### 创建

```text
用户填写基础资料和可选更多信息
  → 一个 POST /v1/customers/
  → 客户、联系人和可选客户字段一次创建
  → 成功：关闭弹窗、刷新列表和详情上下文
  → 失败：保留输入、显示字段错误或重试提示
```

### 编辑

```text
用户修改任意基础/更多字段
  → 计算 dirty diff
  → 一个 PUT /v1/customers/{id}
  → 锁定并校验 expected_version
  → 一次性写入客户字段并递增 version
  → 成功：刷新列表和打开的匹配详情
  → 冲突：保留输入，提供最新数据/保留输入恢复
```

普通客户事实写入与智能档案后处理继续解耦：后台刷新失败不回滚客户字段。

### 失败恢复

- 普通资料校验失败：错误贴近字段，折叠区域自动展开并聚焦首个错误；
- 行业层级加载失败：只禁用行业控件，基础字段仍可保存；
- 并发冲突：保留全部当前输入，更新版本后允许重试；
- 客户切换：清空旧字段、旧错误和旧行业保留信息；
- 保存中：禁用保存和取消，防止重复提交或关闭造成状态不确定；
- 关闭未保存弹窗仍保留，这是输入保护，不是业务确认。

## 7. UX、无障碍与响应式

- “更多客户信息”触发器为文字按钮，稳定提供 `aria-expanded` 和 `aria-controls`；
- 创建和编辑均默认收起更多区域；
- 展开区域内字段使用与基础信息一致的标签、控件高度和间距，不使用嵌套业务卡片；
- 行业 Combobox 支持键盘打开、搜索、上下移动、回车选择和 Escape 关闭；
- 行业字段有可见标签“行业”，错误和帮助文字通过 `aria-describedby` 关联；
- 状态同时展示文字，不依赖颜色表达；
- 授权说明使用紧凑辅助文本，不依赖颜色传达风险；
- 桌面端基础字段使用双列布局，底部操作横向排列；
- 窄屏字段堆叠，底部主操作在取消之前，所有主要控件最小触达高度 44px；
- Dialog 保留动态视口最大高度、内部滚动和 safe-area scroll padding；
- 行业下拉列表跟随触发器宽度并在自身容器滚动，页面不得产生横向滚动；
- `prefers-reduced-motion` 下过渡不影响展开、选择和保存可用性；
- 不提供保存前确认弹窗；只保留关闭时未保存保护。

## 8. 审计、智能档案与正式流程

### 客户资料维护

- 创建继续记录 `CUSTOMER_CREATED`；
- 编辑统一记录 `CUSTOMER_UPDATED`，包含状态、行业和授权汇总字段的 before/after；
- 普通编辑不生成显式 `CUSTOMER_STATUS_CHANGED`，不冒充列表中的赢单动作；
- 客户资料成功后触发既有客户智能档案 partial refresh；
- 智能档案失败不回滚客户资料事实。

### 显式状态动作

列表中的赢单、输单、失效、公海等操作继续使用原有专用接口、审计和通知，不被统一客户资料保存替代。

### License 流程

弹窗直接填写的授权快照：

- 不写入或修改 `crm_license_applications`；
- 不创建审批实例、授权码或发放记录；
- 只影响客户列表、详情和客户智能上下文中的汇总展示；
- 后续正式申请仍按现有权限、审批和发放流程执行；
- 正式发放后的客户快照回写继续遵循现有 License 逻辑。

## 9. 验证策略

### 前端行为

1. 创建和编辑的更多区域默认收起；
2. 展开后行业、状态、授权类型、授权到期日以统一字段平铺显示；
3. 创建时可选填行业、0/1 状态和授权汇总，未填写字段不提交；
4. 编辑时一次保存请求包含所有被修改字段，并只包含 dirty diff；
5. 不再渲染“应用状态变更”“保存授权信息”“清除日期”按钮；
6. 只修改行业、状态或授权时，底部统一保存按钮可完成提交；
7. 行业支持层级搜索、一级无子项选择和停用值保留；
8. 行业加载失败只禁用行业控件，重试后恢复；
9. 状态 2/3 在编辑时只读，不能从弹窗覆盖；
10. 授权补录不调用 License 申请接口；
11. 保存冲突保留输入并可恢复；
12. 关闭未保存弹窗仍提示放弃更改；
13. 桌面与窄屏布局无横向滚动，窄屏主保存按钮位于取消按钮之前。

### 后端行为

1. `CustomerCreate.status` 只接受 0/1，缺省为 0；
2. `CustomerUpdate.status` 只接受 0/1，不能通过普通资料入口设置 2/3；
3. 创建/更新行业继续校验未知和新停用 code；
4. 创建/更新授权类型与到期日校验组合关系；
5. 编辑一次请求只递增一次客户 version，并执行 optimistic lock；
6. 普通资料审计包含状态、行业和授权字段的准确 before/after；
7. 普通资料更新不创建 LicenseApplication 或审批实例；
8. 显式赢单、输单、失效、公海、领取、移交和正式 License 流程回归不变；
9. team 隔离、客户编辑权限和响应 schema 校验继续生效；
10. 客户资料 partial refresh 失败不回滚客户主事实。

### 手动冒烟

- 创建客户，仅填写基础资料，确认更多字段为空且可正常创建；
- 创建客户时展开更多，选择行业、已成交、试用和日期，确认一次保存后列表/详情展示更新；
- 编辑客户时展开更多，修改行业、状态和授权，确认只有一个保存按钮且一次提交完成；
- 在已有正式 License 的客户上直接补录汇总，确认正式 License 记录未改变；
- 后续重新发起 License 申请，确认仍进入原有申请/审批流程；
- 在输单或失效客户上打开编辑，确认状态只读；
- 模拟版本冲突，确认输入保留、可获取最新数据或继续编辑；
- 在窄屏确认字段堆叠、主保存按钮在取消前、弹窗内部滚动且页面无横向滚动。

## 10. 设计自审

- 占位检查：无 `TBD`、`TODO` 或未实现占位；
- 业务一致性：弹窗资料维护、显式状态动作和正式 License 流程边界明确；
- 交互一致性：创建/编辑共用更多字段，一个保存按钮，无清除日期和保存前确认；
- 数据一致性：创建一次写入，编辑 dirty diff 一次写入，一次 version 递增；
- 安全性：普通更新仍执行 team/customer 权限和 0/1 状态限制；
- 兼容性：现有显式状态 API、License API 和数据库字段保留；
- 响应式：桌面双列、窄屏堆叠、内部滚动、safe-area 和 44px 触达要求均有明确验收项；
- 外部资料限制：飞书文档正文在当前环境仍需登录，设计依据采用仓库设计系统和实际业务链路。
