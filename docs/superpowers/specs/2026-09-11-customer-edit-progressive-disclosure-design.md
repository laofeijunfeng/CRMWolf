# 客户编辑弹窗渐进披露与低频字段编辑设计

- 日期：2026-09-11
- 状态：待用户审阅
- 范围：客户管理中的编辑客户 Dialog、客户主数据更新、客户状态快捷变更、客户授权汇总补录
- 上游：用户确认采用“渐进披露”方案；行业使用数据库中的一级/二级目录；授权补录不增加修改原因字段，仅展示风险提醒
- 相关规范：`CRM-Docs/design-system/patterns/form-page.md`、`CRM-Docs/design-system/patterns/detail-page.md`、`CRM-Docs/design-system/components/modal-sheet.md`、`CRM-Docs/design-system/components/input.md`

## 1. 背景与目标

当前客户编辑弹窗 `CRM-Client/src/components/dialogs/CustomerFormDialog.vue` 只编辑客户名称、城市、地址、公司规模、客户来源和默认采购方式。客户详情和列表还展示行业、客户状态、授权状态、授权到期等信息，但这些字段不能在同一编辑入口维护。

老客户需要补录授权类型和到期日期时，当前只能创建 License 申请并经过 License 流程。这个流程适合正式授权业务，不适合历史数据补录或客户汇总信息纠正。

本设计目标：

1. 保持普通客户编辑的首屏简洁，低频字段默认收起但可发现；
2. 允许在客户编辑上下文中维护行业；
3. 允许老客户直接补录客户授权汇总信息，不替代正式 License 流程；
4. 只开放低风险的客户状态快捷变更，避免绕过输单、公海和失效流程；
5. 保留客户状态、普通资料、授权汇总三类操作的业务边界、并发保护和结果反馈；
6. 在桌面、窄屏、键盘和读屏场景下保持现有 Dialog 的可恢复性。

## 2. 非目标与明确边界

本设计不做以下事情：

- 不在客户编辑弹窗中创建 License 申请、提交审批、审批或发放 License；
- 不修改 `crm_license_applications` 中的申请、审批、授权码、部署、合同或授权人数；
- 不直接提供“未授权 / 已过期 / 试用 / 正式”的可编辑状态下拉；授权状态仍由授权类型和到期日期计算；
- 不允许通过普通编辑入口直接设置“已输单”“已失效”或“公海”；
- 不改变负责人、协作者、公海、移交和领取的既有流程；
- 不在本期改造行业字典管理、行业筛选接口或全量历史行业迁移；
- 不增加“授权补录修改原因”字段；授权区域只展示明确风险提醒；
- 不引入新的通用字典或通用级联表单框架。

## 3. 方案选择

采用“基础信息首屏 + 更多客户信息默认收起 + 分业务保存”的方案。

### 3.1 交互层级

```text
编辑客户 Dialog
├── 基础信息（默认显示）
│   ├── 客户名称
│   ├── 所在城市
│   ├── 客户来源
│   ├── 公司规模
│   ├── 默认采购方式
│   └── 详细地址
├── 更多客户信息（默认收起）
│   ├── 客户补充信息
│   │   └── 所属行业
│   ├── 客户状态
│   │   └── 跟进中 ↔ 已成交快捷变更
│   └── 授权信息补录
│       ├── 授权类型
│       ├── 授权到期
│       └── 当前计算状态（只读）
└── Dialog Footer
    ├── 取消
    └── 保存客户资料
```

“更多客户信息”触发器必须是有文字的按钮，不使用只有图标的入口。若行业、状态或授权存在已有值，触发器显示摘要，例如：

```text
更多客户信息（已填写 3 项）
```

如果折叠区域内出现校验错误或接口错误，系统自动展开区域并将焦点移动到首个错误控件。

### 3.2 为什么不是全部平铺

全部平铺会让普通资料、生命周期状态和授权汇总出现在同一认知层级，用户容易把三种不同业务操作理解为一次普通保存。渐进披露符合当前设计系统关于“低频属性可展开”的规则，同时保留明确入口、已填写数量、键盘路径和错误可达性。

### 3.3 为什么不把所有字段交给一个保存按钮

普通客户资料、状态变更和授权补录的后端副作用不同：

- 普通资料更新走客户主数据 PUT，并刷新客户智能档案；
- 客户状态变更可能发送赢单/输单通知，并影响统计和状态快照；
- 授权汇总补录不能改变正式 License 业务记录，但会改变客户详情和列表展示。

因此采用分业务保存：普通资料由底部“保存客户资料”提交；状态使用“应用状态变更”；授权使用“保存授权信息”。一个区域失败时保留其他区域的结果和用户输入，避免出现不可解释的部分成功。

## 4. 字段与业务规则

### 4.1 普通客户资料

继续使用现有 PUT 客户接口。编辑字段为：

| 字段 | 交互 | 保存语义 |
|---|---|---|
| `account_name` | 输入框 | 客户主数据 |
| `city` | 输入框 | 客户主数据 |
| `address` | 输入框 | 客户主数据 |
| `company_scale` | 下拉 | 客户主数据 |
| `source_public_id` | 获客来源下拉 | 按来源 `public_id` 更新 |
| `default_procurement_method_id` | 采购方式下拉 | 会影响后续新建商机的默认采购方式 |
| `industry` | 二级目录可搜索选择器 | 保存行业 code |

前端必须采用 dirty diff：只提交用户实际修改过的字段。折叠区域没有展开或没有触碰时，不得将未加载字段作为 `null` 或空值提交。

### 4.2 行业

行业是数据库中的行业记录，不再使用旧的硬编码 `CustomerIndustry` 枚举作为编辑选项。

数据源使用现有：

```text
GET /v1/industries/hierarchy
```

响应语义：

```json
{
  "INTERNET": {
    "name": "互联网",
    "children": [
      { "code": "INTERNET_ENTERPRISE", "name": "企业服务" },
      { "code": "INTERNET_SOFTWARE", "name": "软件服务" }
    ]
  }
}
```

前端使用 shadcn-vue / Reka UI 的 `Combobox` 组合：

- `ComboboxInput`：搜索一级或二级行业名称；
- `ComboboxGroup`：按一级行业分组；
- `ComboboxItem`：选择二级行业或无子级的一级行业；
- 触发器展示完整路径，例如“互联网 / 企业服务”；
- 提交只保存稳定 `code`，不保存展示文案；
- 选中已有行业时保留完整路径；
- 当前客户行业 code 已停用或不在活动层级中时，允许原值保持不变，并使用详情接口返回的 `industry_info` 展示；不能在新选择中继续选择停用项；
- 行业选项加载失败时只禁用行业控件，显示“行业选项加载失败”和重试按钮，不阻塞其他基础资料的编辑和保存。

实现上新增一个聚焦行业层级选择的组件，复用现有 `Combobox` 基础组件和表单错误契约；不把级联逻辑塞入 `SelectField`，避免破坏现有扁平选择器。

行业修改会影响客户列表行业筛选、同行客户匹配和客户智能档案上下文，因此成功后沿用客户主数据的 partial refresh 事件。

### 4.3 客户状态

客户状态不是普通客户资料字段。弹窗只提供受控快捷操作：

```text
跟进中（0） ↔ 已成交（1）
```

规则：

- 当前为 `0` 时，可选择 `1`；
- 当前为 `1` 时，可选择 `0`；
- `2` 已输单：只展示当前状态，提示使用输单流程；
- `3` 已失效/非激活：只展示当前状态，提示使用失效流程；
- 公海仍由负责人/公海流程管理，不把 `status=3` 等同于公海；
- 不允许通过普通客户资料保存隐式改变状态。

点击“应用状态变更”后：

1. 使用当前 `expected_version` 发起状态变更；
2. 提交期间禁用状态控件；
3. 成功后更新 Dialog 内版本和状态，并刷新父列表/详情；
4. 失败保留选择，显示可重试错误；
5. 并发冲突提供“获取最新数据”路径。

后端可复用现有状态业务逻辑，但必须为弹窗快捷变更提供明确的 0/1 迁移边界、版本校验、状态变更审计和既有智能/通知副作用。输单、失效、公海和领取继续走原有专用入口。

### 4.4 授权汇总补录

授权状态是派生展示，不是独立编辑字段：

```text
到期日为空                         → 未授权
到期日早于今天                     → 已过期
到期日有效且授权类型为 TRIAL        → 试用
到期日有效且授权类型为 OFFICIAL     → 正式
```

编辑控件：

- `license_type`：试用 / 正式；
- `license_expiry_date`：日期选择；
- 派生状态：只读徽章，实时更新。

交互提醒固定显示在授权区域：

> 此处只更新客户授权汇总信息，不创建 License 申请、不发起审批，也不修改正式 License 记录。

即使客户已有正式 `ISSUED` License 记录，也允许覆盖客户汇总字段；系统不修改原 License 记录。由于本期不增加修改原因字段，风险通过上述持久提醒表达，保存成功反馈必须明确“已更新客户授权汇总”。

授权保存使用独立接口：

```text
PATCH /v1/customers/{customer_id}/license-snapshot
```

请求：

```json
{
  "expected_version": 12,
  "license_type": "TRIAL",
  "license_expiry_date": "2026-12-31"
}
```

约束：

- 复用客户编辑权限，不授予 `license:issue`；
- 使用行锁和 `expected_version`；
- `license_type` 只允许 `TRIAL`、`OFFICIAL` 或空值；
- 到期日为空时，类型同时归一为空，避免“无到期日但正式授权”的歧义；
- 到期日非空时，类型必须存在；
- 递增客户 `version`；
- 记录授权汇总前后值、操作人和时间；
- 不创建 License 申请、审批实例、授权码或正式发放记录；
- 成功后触发客户智能档案 partial refresh，保持客户主数据变更事件一致性。

## 6. 保存与并发模型

### 基础资料

```text
用户修改基础字段/行业
  → 计算 dirty diff
  → PUT /v1/customers/{id}
  → 成功：更新 loadedVersion，关闭或保留展开区域，刷新父上下文
  → 冲突：保留输入，提供使用最新数据/继续编辑
```

### 状态

```text
用户选择 0/1
  → 应用状态变更
  → 状态专用写入 + expected_version
  → 成功：更新状态和版本，刷新列表/详情
```

### 授权

```text
用户修改类型/到期日
  → 展示固定风险提醒
  → 保存授权信息
  → license-snapshot 写入 + expected_version
  → 成功：明确提示“客户授权汇总已更新”，刷新列表/详情
```

三类提交使用独立 loading、错误和成功状态。普通资料已成功但授权失败时，不回滚已经成功的普通资料；界面说明已完成和未完成部分，并保留授权输入供重试。

## 7. UX、无障碍与响应式约束

- “更多客户信息”使用 `Collapsible`，触发器最小触达高度 44px；
- 触发器包含稳定 `aria-expanded` 和 `aria-controls`；
- 展开/收起后焦点仍可预测，关闭 Dialog 后焦点返回打开按钮；
- 行业 Combobox 支持键盘打开、搜索、上下移动、回车选择和 Escape 关闭；
- 行业输入具有可见标签“所属行业”，错误和帮助文字通过 `aria-describedby` 关联；
- 错误发生在折叠内容时自动展开，不要求用户猜测错误位置；
- Dialog 保留现有 `max-h`、内部滚动和 safe-area scroll padding；
- 移动端行业选择器宽度跟随触发器，列表内部滚动，页面不产生横向滚动；
- `prefers-reduced-motion` 下折叠和选择器过渡不影响可用性；
- 不用颜色作为状态的唯一表达，状态同时展示文字；
- 授权提醒使用说明性文本，不依赖橙色本身传达风险。

## 8. 错误与权限

错误分类：

| 场景 | 行为 |
|---|---|
| 行业层级加载失败 | 行业字段禁用，显示重试；基础字段仍可保存 |
| 基础资料校验失败 | 展开相关区域，聚焦首个错误，保留输入 |
| 状态冲突 | 保留选择，提示客户已变化，允许获取最新数据后重试 |
| 授权补录冲突 | 保留授权输入，更新版本后重试，不静默覆盖 |
| 权限不足 | 说明具体受限操作；不把授权补录权限错误呈现为 License 发放权限 |
| 网络/服务失败 | 保留当前区域输入和上下文，提供重试 |
| 部分成功 | 明确列出已完成区域与待重试区域 |

权限：

- 基础资料和行业：现有 `customer:edit:own` / `customer:edit:all` 或客户成员 EDIT；
- 状态快捷变更：同一客户编辑前置权限，但后端只接受本入口规定的 0/1 迁移；
- 授权汇总补录：同一客户编辑前置权限，不等价于 `license:issue`；
- 所有接口继续按当前团队过滤客户。

## 9. 审计与智能档案

### 审计

新增或启用以下客户事件语义：

- `CUSTOMER_UPDATED`：普通资料/行业前后值和 changed fields；
- `CUSTOMER_STATUS_CHANGED`：旧状态、新状态、操作人、版本和时间；
- `CUSTOMER_LICENSE_SNAPSHOT_UPDATED`：旧授权类型/到期日、新授权类型/到期日、操作人、版本和时间。

审计记录不要求用户输入修改原因，但必须保留机器可读的前后值。

### 智能档案

- 行业普通更新沿用客户主数据 `partial` refresh；
- 状态快捷变更沿用状态变更的智能事件和既有赢单通知语义；
- 授权汇总更新入队客户主数据 `partial` refresh；
- 智能档案刷新失败不回滚已提交的客户事实，界面显示后台刷新状态。

## 10. 验证策略

### 前端行为

1. 编辑详情包含行业 code 时，打开弹窗能显示完整一级/二级路径；
2. 行业 Combobox 按一级行业分组，搜索二级名称能过滤，选择后提交 code；
3. 行业层级请求失败时只禁用行业控件并可重试；
4. 默认“更多客户信息”收起，已有低频值显示填写数量；
5. 展开区域发生校验错误时自动展开并聚焦错误；
6. 只修改行业时，普通资料 payload 只包含行业和 expected version，不覆盖未修改字段；
7. 状态快捷操作只允许 0/1，不能从该入口设置 2/3；
8. 授权保存 payload 只更新客户汇总字段，界面展示正式 License 不会被修改的提醒；
9. 普通资料成功、授权失败时，界面保留授权输入并说明部分成功；
10. 关闭 Dialog 仍遵循未保存保护。

### 后端行为

1. `CustomerUpdate.industry` 接收合法行业 code，拒绝未知 code；
2. 授权汇总接口校验类型/日期组合、团队隔离、客户编辑权限和 expected version；
3. 授权汇总更新不创建或修改 LicenseApplication；
4. 状态快捷接口拒绝 2/3 目标状态和过期版本；
5. 状态和授权汇总写入递增客户 version 并记录审计；
6. 普通更新、状态更新和授权汇总更新分别产生正确的客户智能事件；
7. 现有赢单、输单、失效、公海、领取和移交流程行为保持不变。

### 手动冒烟

- 打开客户编辑弹窗，确认更多区域默认收起；
- 展开行业选择器，按二级名称搜索并选择；
- 保存行业后刷新客户列表和客户详情，确认显示完整行业路径；
- 对老客户补录试用授权和到期日，确认无需创建 License 申请且客户列表授权状态更新；
- 在已有正式 License 的客户上补录，确认提醒可见且正式 License 记录未被修改；
- 执行跟进中 ↔ 已成交快捷变更，确认列表、详情、通知和版本刷新；
- 模拟并发版本冲突，确认输入保留并可恢复。
