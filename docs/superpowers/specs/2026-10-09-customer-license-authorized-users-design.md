# 客户管理授权人数设计

- 日期：2026-10-09
- 状态：已确认设计，待审阅
- 范围：客户管理列表、客户详情、列表筛选/排序、客户导出，以及 License 发放后的客户授权快照同步

## 1. 问题与目标

客户管理目前从 `crm_customers` 读取授权类型和授权到期日，但没有展示 License 申请中的 `authorized_users`。目标是在客户管理中增加“授权人数”，并保持以下顺序一致：

1. 授权状态
2. 授权人数
3. 授权到期

授权人数必须与现有客户授权状态、授权到期使用同一份客户授权快照，不应在列表请求中逐客户读取 License 申请。

## 2. 已确认的业务规则

### 2.1 数据来源

授权人数来源于 `LicenseApplication.authorized_users`，不是 `DeploymentInfo.authorized_users`，也不解析 License 内容。

只有 `status = ISSUED` 的申请可作为来源。`TRIAL` 和 `OFFICIAL` 两种 `license_type` 都纳入。

### 2.2 多条申请选取规则

按客户和团队维度筛选已发放申请后，取排序第一条：

```text
expiry_date DESC,
last_modified_time DESC,
id DESC
```

因此：

- 到期日更晚的申请优先；
- 到期日相同取最后修改的申请；
- 修改时间仍相同取 ID 更大的申请，保证结果稳定；
- 没有已发放申请时，授权人数、授权类型、授权到期均为空。

该规则与客户当前“最晚到期授权快照”的语义一致。

### 2.3 授权人数是否可人工编辑

不可编辑。客户人工授权快照表单继续只维护现有授权类型和授权到期日；授权人数由 License 发放流程和历史回填维护。

## 3. 方案与架构

采用客户表快照方案，不采用列表查询时实时关联方案。

### 3.1 数据模型

在 `crm_customers` 增加：

```text
license_authorized_users INTEGER NULL
```

SQLAlchemy 模型字段命名为 `Customer.license_authorized_users`，注释说明其为自动维护的客户 License 授权人数。

字段保持可空，以区分“没有已发放授权申请”与合法的授权人数值。客户创建、普通客户编辑和人工授权快照更新接口不接收该字段。

### 3.2 发放同步

`LicenseApplicationCRUD.issue()` 和 `issue_full()` 继续在申请状态变更为 `ISSUED` 后调用统一同步方法。

统一同步方法在客户锁内查询该客户团队下全部 `ISSUED` 申请，按已确认规则选出当前申请，并一次性更新三项客户快照：

- `license_expiry_date`
- `license_type`
- `license_authorized_users`

不能只根据本次发放申请与旧到期日比较后更新部分字段，否则可能出现授权到期日来自一条申请、授权人数来自另一条申请的不一致快照。同步方法的提交边界保持现有 `commit` 参数语义。

### 3.3 历史回填

Alembic migration 按同一选取规则为已有客户回填 `license_authorized_users`。回填同时校准已有的授权到期日和授权类型，使历史客户三项快照来自同一条已发放申请；没有已发放申请的客户保持三项为空。

迁移必须通过现有 Alembic 机制交付，不使用一次性 SQL 文件或临时脚本。回填查询必须带客户所属团队和客户关联条件，避免跨团队取数。

## 4. API、列表和导出契约

### 4.1 后端响应

在客户列表响应、客户详情响应及其 Pydantic schema 中增加：

```text
license_authorized_users: Optional[int]
```

客户列表响应组装直接读取 `customer.license_authorized_users`。

### 4.2 列表查询目录

在客户列表目录中增加数字字段：

```text
license_authorized_users
```

表达式使用 `Customer.license_authorized_users`，支持现有数字字段的筛选、排序和空值操作能力。目录顺序放在 `license_status` 后、`license_expiry_date` 前。

前端目录 manifest 不手工维护，通过现有生成脚本从后端目录生成，确保前后端字段类型和能力一致。

### 4.3 导出

在后端客户导出目录和导出行中增加：

```text
license_authorized_users -> 授权人数 -> number
```

字段放在“授权状态”和“授权到期”之间。前端导出 manifest 通过现有生成脚本同步生成。

### 4.4 前端类型与展示

同步更新客户 API 类型及 Zod schema 中的列表/详情字段。客户列表沿用现有通用目录驱动展示，不新增专用表格分支。空值显示遵循现有数字字段的空值规则。

## 5. 数据流

```text
LicenseApplication.issue / issue_full
        |
        v
状态变更为 ISSUED
        |
        v
按客户选出最晚到期的 ISSUED 申请
        |
        v
写入 Customer 三项授权快照
        |
        +--> 客户列表 API / 列表筛选排序
        +--> 客户详情 API
        +--> 客户列表导出
```

历史客户通过 migration 执行同一投影逻辑，避免线上新发放规则与历史数据规则不一致。

## 6. 错误处理与边界

- License 申请不属于传入团队时，不更新客户。
- 客户不存在时，不抛出新的业务异常，保持当前同步方法的无操作语义。
- 已发放申请的 `authorized_users` 按现有模型约束为非空整数；不增加隐式默认值或累加逻辑。
- 早于当前快照的申请仍可能改变客户快照中的授权人数，因此同步必须重算选中申请，而不是直接忽略整次发放。
- 列表、详情和导出均只读取客户快照，避免同一请求内出现不同申请选取结果。
- 不改变客户人工修改授权类型/到期日的既有接口语义；人工修改后不会伪造或修改授权人数。

## 7. 测试与验收

### 后端

1. 选取规则覆盖：仅 `ISSUED`、同时包含 `TRIAL/OFFICIAL`、到期日优先、同日按修改时间和 ID 兜底。
2. 发放同步覆盖：发放后客户三项快照来自同一条选中申请；较早申请不会覆盖更晚申请的快照；较早申请仍能补正人数到当前选中申请值。
3. 无已发放申请时快照字段为空。
4. 客户列表和详情响应包含授权人数。
5. 列表目录支持授权人数数字筛选与排序，字段顺序正确。
6. 导出目录、导出行和字段顺序包含授权人数。
7. Alembic migration 在本地执行升级，验证新增字段和历史回填结果。

### 前端

1. 客户响应类型和 Zod schema 接受可空授权人数。
2. 生成的列表/导出 manifest 包含授权人数，类型为 `number`，并保持授权三字段顺序。
3. 客户列表实际加载 API 数据时展示授权人数，空值不导致 schema 或列表渲染失败。

### 不在本次范围

- 不在客户编辑表单中增加授权人数输入。
- 不改 License 申请创建、审批、License 内容解析或部署信息字段。
- 不新增实时逐客户 LicenseApplication 查询。
- 不做与授权人数无关的列表重构或样式改造。
