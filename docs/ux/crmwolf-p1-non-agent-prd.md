# CRMWolf 非 Agent P1 UX 改造 PRD

- **文档状态**：PRD 初稿，待产品、设计、研发和业务负责人评审
- **版本**：v0.1
- **日期**：2026-09-02
- **关联文档**：CRMWolf UX 改造需求文档、CRMWolf UX 问题地图 + 关键任务优先级
- **范围说明**：本文仅覆盖非 Agent 的 P1 UX 问题；Agent / AI 自动化不在本文实施范围内

> 本 PRD 解决的不是一次视觉换肤，而是关键业务流程中的“看得懂、做得对、出错后能恢复”。当前静态分析尚未确认明确 P0，但财务执行、回款登记、审批和高风险操作需要以异常路径测试进一步排除 P0 风险。

## 1. 背景与机会

CRMWolf 当前已经具备统一导航、DataTable、Dialog / Sheet、移动端导航和部分无障碍基础。问题主要集中在关键任务跨页面运行时的体验不一致：用户在列表、详情、表单、审批和财务操作之间切换时，可能无法确定当前对象、操作状态、失败原因和下一步动作。

本 PRD 聚焦以下五类非 Agent P1 问题：

1. 任务状态反馈不统一；
2. 高风险操作确认、提交和恢复不统一；
3. 详情层级、弹窗和对象上下文复杂；
4. 错误恢复、权限反馈和表单可恢复性不足；
5. 响应式、键盘、读屏和放大场景缺少关键任务级验收。

## 2. 用户与关键任务

### 2.1 主要用户

- **销售人员**：查看客户、记录活动、推进商机、提交审批；
- **销售管理者 / 审批人员**：查看商机和合同状态，处理审批、驳回和撤回；
- **财务人员**：登记回款、修改或删除回款记录、处理财务审批；
- **团队管理员**：维护客户成员、联系人、部署、发票抬头及权限相关信息；
- **移动办公用户**：在小屏设备上快速查看客户和完成跟进。

### 2.2 第一批关键任务

| 任务 | 核心路径 | 本 PRD 关注点 |
|---|---|---|
| 客户跟进 | 客户列表 → 客户详情 → 添加活动 → 保存 → 设置下一次跟进 | 状态反馈、错误恢复、详情层级、移动端可达性 |
| 客户维护 | 客户详情 → 客户信息 → 编辑 → 提交 → 处理错误 | 表单恢复、权限反馈、Dialog 和焦点 |
| 商机推进 | 客户 → 商机 → 合同 → 提交审批 → 成功/驳回/撤回 | 对象上下文、状态持久化、高风险确认 |
| 财务执行 | 合同 → 回款计划 → 登记回款 → 审批/失败/重试 | 重复提交、金额准确、结果确认、P0 风险验证 |

## 3. 产品目标与成功标准

### 3.1 产品目标

- 用户能够持续知道当前处于哪个对象和流程阶段；
- 用户能够区分加载、空、失败、保存中、成功、部分成功和后台处理中；
- 高风险操作在执行前可理解后果，执行中不会重复提交，执行后有结果和恢复路径；
- 失败、超时、权限不足和并发修改不会迫使用户刷新页面或重新填写全部内容；
- 关键任务在桌面、移动端、键盘、读屏、200% 字体和软键盘环境下仍可完成。

### 3.2 成功标准

上线后通过基线测试和可用性测试验证：

1. 关键任务完成率提升，异常情况下的恢复完成率可统计；
2. 保存、审批和回款登记的重复点击与重复提交显著减少；
3. 删除、退回、输单、转移、撤回、驳回和财务修改的误操作率可控；
4. 用户能正确回答“当前操作是否已生效、失败后如何继续、返回会回到哪里”；
5. 键盘和读屏用户能够完成核心路径，200% 字体及 320px 宽度下不存在关键内容不可达。

## 4. 产品范围

### 4.1 本期范围

- 统一任务状态模型和反馈组件契约；
- 统一高风险操作的 Dialog / AlertDialog / Sheet 模型；
- 收敛客户、商机、合同、回款对象之间的上下文和返回关系；
- 统一表单错误、权限错误、网络错误、并发修改和未保存退出处理；
- 对关键任务进行响应式、键盘、读屏和移动端可达性改造与验收。

### 4.2 不在本期范围

- Agent / AI 的建议、草稿、自动写入、后台任务和人工接管；
- 全量视觉重做、品牌色重构、圆角和阴影统一；
- P2 列表高级工具渐进披露、Token 全量迁移和低频页面精修；
- 新增 CRM 业务能力或调整既有业务审批规则；
- 仅为拆分代码文件而进行的重构。

## 5. 需求详述

### P1-01：统一任务状态反馈

#### 用户故事

作为销售、审批或财务用户，我希望在加载、保存、审批和后台处理过程中明确知道系统状态，这样我不会重复点击，也不会误以为数据已经生效或丢失。

#### 需求描述

建立可复用的任务状态协议，覆盖列表、详情、表单、审批、回款和删除/转移等操作。页面不得仅依赖短时 Toast、静默日志或自动返回表达关键结果。

#### 状态与产品行为

| 状态 | 用户必须看到 | 用户可执行动作 |
|---|---|---|
| 加载中 | 正在加载的对象/区域 | 等待；必要时取消或返回 |
| 空数据 | 无数据原因 | 新建、清除筛选或返回 |
| 筛选无结果 | 当前筛选条件 | 修改条件、清空筛选 |
| 权限不足 | 无法执行的动作及原因 | 返回、申请权限或联系管理员 |
| 保存中 | 正在保存的对象 | 等待；禁止重复提交 |
| 成功 | 对象名称、最终状态 | 查看结果、继续下一步、返回 |
| 失败 | 失败类型和影响 | 修复、重试、人工处理 |
| 部分成功 | 已完成与未完成部分 | 查看明细、补做未完成部分 |
| 后台处理中 | 任务名称和当前进度/状态 | 离开、返回任务入口、取消（如支持） |

#### 交互要求

- 状态反馈应贴近发生操作的上下文；
- 关键状态同时提供视觉和辅助技术可感知的语义；
- 成功反馈根据风险和持续时间选择内嵌结果、状态卡或 Toast，不得统一使用 Toast；
- 离开页面后仍需能找回审批、同步等未完成任务的状态；
- 失败不清空表单，不自动跳转，不丢失用户已填写内容。

#### 验收标准

- 断网、超时、500、权限不足、重复点击、部分成功六类场景均有明确状态；
- 用户无需刷新页面即可判断是否成功并完成下一步或重试；
- 保存中按钮不会产生重复请求；
- 状态不只通过颜色表达，读屏可读出状态变化；
- 财务和审批操作成功后能看到最终业务状态，而不是只有“操作成功”提示。

### P1-02：统一高风险操作模型

#### 覆盖范围

删除、退回公海、标记输单、转移、撤回、驳回、冲红、修改或删除回款记录、提交审批等。

#### 用户故事

作为销售、审批或财务用户，我希望在执行不可逆或影响业务事实的操作前知道对象和后果，并在误操作或失败后有恢复方式。

#### 交互要求

**确认前**：

- 显示对象名称、对象类型、当前状态和操作后状态；
- 说明影响范围、是否不可逆、是否会触发审批或通知；
- 对“退回公海”“输单”“驳回”“删除回款”等动作说明后续影响；
- 需要理由时，字段有 label、示例、字数限制和错误提示。

**确认中**：

- 显示提交中状态；
- 禁止重复提交；
- 保留当前对象上下文；
- 对金额、日期、状态等关键字段在提交前再次呈现。

**成功后**：

- 显示实际生效对象和状态；
- 提供查看结果、继续流程或返回原上下文的入口；
- 有业务支持时提供撤销，否则提供明确的人工恢复路径。

**失败后**：

- 保留理由和已填写内容；
- 区分校验失败、权限失败、网络失败、冲突和服务失败；
- 提供重试、修复或人工处理入口；
- 不因失败自动关闭详情或把用户带离当前任务。

#### 验收标准

- 所有高风险操作使用统一的 Dialog / AlertDialog / Sheet，不再新增临时自定义 modal；
- 遮罩点击、Escape、关闭按钮的行为符合统一规则；有未保存输入时不会静默丢弃；
- 键盘用户可以完成确认、取消和错误修复；
- 移动端不出现固定宽度导致的横向溢出；
- 高风险操作不只能通过右键菜单发现或触发；
- 财务操作具备重复提交验证和最终状态查询，未完成验证前不得视为已排除 P0 风险。

### P1-03：收敛详情层级和对象上下文

#### 用户故事

作为销售、审批或财务用户，我希望在客户、商机、合同和回款之间切换时始终知道当前对象和返回位置，这样我不会在多个 Sheet / Dialog 中迷路。

#### 产品模型

统一对象上下文栈：

```text
客户
└── 商机
    └── 合同
        └── 回款计划 / 回款记录
```

#### 交互要求

- 当前对象名称、对象类型和关键状态持续可见；
- 提供明确的“返回上一级”和“关闭整个流程”动作；
- 返回上一级表示回到上层上下文，不等同于取消已提交操作；
- 关联对象优先在当前上下文内切换，避免无限叠加 Sheet；
- 客户详情中的档案、活动、客户信息和项目旅程要有明确任务边界；
- 页面动作、列表动作、行动作、详情 Footer 动作和关联对象动作按统一位置规则呈现；
- 控制页面、表格、Sheet、Dialog 的滚动容器数量，移动端优先自然页面滚动；
- 打开、返回、关闭和提交后焦点均有可预测的恢复位置。

#### 验收标准

- 用户在客户 → 商机 → 合同 → 回款路径中，能够随时说出当前对象和上一级对象；
- 返回、关闭、取消三个动作在文案和行为上可区分；
- 连续打开关联对象后，不出现无法关闭、遮罩叠加失控或焦点丢失；
- 详情 Sheet 在低高度屏幕和移动端不会因多重内部滚动导致主要内容不可达。

### P1-04：错误恢复、权限反馈和表单可恢复性

#### 用户故事

作为用户，我希望请求失败时仍保留工作上下文和输入内容，并知道是哪里出了问题以及如何继续，而不是被迫刷新或重新开始。

#### 错误分类与处理

| 错误类型 | 必须说明 | 恢复动作 |
|---|---|---|
| 字段校验 | 哪个字段、什么格式不正确 | 聚焦字段并修正 |
| 权限不足 | 哪个动作受限、需要什么权限 | 返回、申请权限、联系管理员 |
| 网络/超时 | 请求未完成，不代表业务未执行 | 重试、查询最终状态 |
| 服务错误 | 系统暂时不可用及影响 | 重试、稍后处理、保留输入 |
| 并发修改 | 数据可能已被他人改变 | 刷新、查看差异、重新编辑 |
| 部分成功 | 哪些内容已生效 | 查看明细、补做失败部分 |

#### 交互要求

- 详情加载失败不得默认自动返回上一页；
- 选项加载失败必须指出受影响字段并提供重试；
- 提交失败保留用户输入，错误与控件建立关联；
- 提交后自动聚焦首个错误，且错误摘要可被键盘和读屏发现；
- 未保存退出时提示用户保存、继续编辑或放弃；
- 网络错误与业务失败分开处理，必要时先查询最终状态，避免重复写入。

#### 验收标准

- 典型异常下用户可以在当前上下文完成恢复；
- 用户不需要重新输入已经填写的客户、联系人、金额、日期和理由；
- 错误信息不只写入日志或通过一次性 Toast 告知；
- 权限不足不会被误呈现为普通系统故障；
- 并发修改和请求超时不会诱导用户重复创建业务记录。

### P1-05：关键任务响应式与无障碍验收

#### 用户故事

作为使用键盘、读屏、放大字体或移动设备的用户，我希望核心任务仍然可操作、可理解、可恢复。

#### 验收环境

- 桌面键盘操作；
- 至少一种主流桌面读屏；
- 200% 字体或等效放大；
- 320px 窄屏；
- 手机横屏；
- 虚拟键盘打开；
- 低带宽、断网和超时；
- reduced motion。

#### 交互要求

- 核心主操作、错误信息和返回入口在 320px 和 200% 字体下可达；
- Dialog / Sheet 打开软键盘后，当前字段、错误信息和提交按钮可滚动到；
- Tab 顺序符合视觉和任务顺序；
- Dialog 有正确标题和描述，焦点进入、焦点恢复、Escape 行为明确；
- 表格行、行内按钮和上下文菜单不产生重复或冲突的读屏语义；
- Enter / Space、ContextMenu 键和 `Shift + F10` 的行为可理解；
- 状态、错误和风险不依赖颜色单独表达；
- 加载、保存中、成功和失败状态能被辅助技术感知；
- 移动端 Card、Sheet 和表单不因固定高度或内部滚动造成内容不可达。

#### 验收标准

客户跟进、客户维护、商机审批和回款登记四条路径至少各完成一次键盘、读屏、窄屏、放大字体和软键盘验收；异常路径也必须可理解和恢复，不能只验收 happy path。

## 6. 页面与组件改造优先级

| 优先级 | 对象 | 改造重点 |
|---:|---|---|
| 1 | Customers / 客户列表 | 高风险操作 modal、行操作可发现性、状态反馈、移动端布局 |
| 2 | CustomerDetailSheet | 对象上下文、层级、滚动、返回/关闭/焦点关系 |
| 3 | CustomerEdit 及客户信息相关表单 | 错误恢复、权限反馈、选项加载、未保存保护 |
| 4 | 商机/合同/审批链路 | 状态持久化、高风险确认、驳回/撤回/失败恢复 |
| 5 | 回款计划/回款记录 | 重复提交、金额和日期确认、最终状态、P0 风险验证 |
| 6 | DataTable / Dialog / Sheet 共享组件 | 统一契约、无障碍语义、响应式和跨页面复用 |

## 7. 交互与数据规则

### 7.1 提交幂等与最终状态

涉及审批、回款、删除、转移和状态推进的操作，产品和后端需要明确：

- 是否使用幂等键或客户端请求标识；
- 请求超时后如何查询最终状态；
- 前端如何防止重复点击和重复创建；
- 部分成功时如何展示已成功和未完成部分。

### 7.2 返回、关闭和取消

- **返回上一级**：保留已提交结果，回到上一级对象；
- **关闭详情**：退出当前详情上下文；
- **取消编辑**：放弃本次未提交修改，必要时二次确认；
- **取消请求/任务**：只有后端支持取消时才展示，取消后显示最终状态。

### 7.3 通知与持久状态

短时 Toast 仅用于低风险、短时、无需后续决策的结果。审批、回款、高风险操作和较长请求必须提供可回看或内嵌的持久状态。

1. 任务状态协议和状态文案表；

4. 客户 → 商机 → 合同 → 回款对象上下文和返回规则；
5. 四条关键任务的 happy path、异常路径和恢复路径流程图；
6. 关键页面交互稿和移动端适配稿；
7. 键盘、读屏、200% 字体、320px、软键盘和低带宽验收清单；
8. 任务指标埋点和上线前后对比报告。

## 9. 实施计划

### Phase 0：风险验证与基线

- 复现断网、超时、重复提交、权限不足、部分成功和并发修改；
- 优先验证回款登记、审批提交和财务事实修改是否存在重复写入或不可恢复问题；
- 记录任务完成率、恢复完成率、重复点击、误操作和放弃率基线。

### Phase 1：共享交互契约

- 实现任务状态协议；
- 收敛 Dialog / AlertDialog / Sheet 行为；
- 定义错误分类、表单错误关联和焦点管理；
- 定义对象上下文栈和滚动容器规则。

### Phase 2：关键业务闭环

按以下顺序迁移和验证：

1. 回款登记及审批；
2. 商机推进及合同审批；
3. 客户跟进和客户维护；
4. 移动端关键路径。

### Phase 3：扩展与治理

- 迁移其他页面；
- 禁止新增临时 modal 和新的旧 Token 用法；
- 建立共享组件使用检查和 UX 回归清单；
- 根据用户测试结果调整优先级。

## 10. 指标与发布门禁

### 10.1 指标

| 指标 | 适用范围 | 用途 |
|---|---|---|
| 任务完成率 | 四条关键任务 | 判断核心可用性 |
| 异常恢复完成率 | 网络、权限、服务和并发异常 | 判断错误是否可恢复 |
| 重复点击/重复提交次数 | 保存、审批、回款 | 判断反馈和幂等保护 |
| 高风险误操作率 | 删除、退回、输单、转移、驳回 | 判断确认模型有效性 |
| 首次找到操作时间 | 列表、详情和下一步 | 判断可发现性 |
| 表单放弃率 | 客户维护、回款登记 | 判断信息负担和错误摩擦 |
| 返回/关闭次数 | 多对象详情流程 | 判断层级是否迷路 |

### 10.2 发布门禁

- P1-01 至 P1-05 未完成关键异常路径验证，不得以“已统一”作为完成结论；
- 回款和审批未完成重复提交及最终状态验证，不得关闭 P0 风险项；
- 所有新增高风险操作必须使用统一组件和状态模型；
- 关键错误必须保留上下文、输入和恢复入口；
- 键盘、读屏、320px、200% 字体和软键盘场景不得存在阻断核心任务的问题；
- 不得仅通过增加 Toast 数量替代持久状态、错误恢复和对象上下文设计。

## 11. 依赖与待确认事项

### 11.1 依赖

- 共享 Dialog、AlertDialog、Sheet、DataTable 和表单状态能力；
- 审批、回款和状态推进接口具备幂等或最终状态查询能力；
- 业务负责人确认各类高风险操作的撤销、恢复和审计要求；
- 设计系统提供状态、焦点、间距、响应式和无障碍规范；
- 测试环境具备可复现的权限、网络、超时、并发和部分成功场景。

### 11.2 待确认事项

1. 哪些删除、退回、输单、转移、驳回和冲红操作可撤销，哪些只能人工恢复？
2. 回款登记和审批接口是否具备幂等键、重复提交保护和最终状态查询？
3. 客户详情中的“客户信息”是否按角色拆分为多个维护任务？
4. 是否需要统一的后台任务/审批状态入口，以避免用户离开页面后丢失任务？
5. 关键任务的目标用户、真实设备和可用性测试样本如何确定？
