# CRMWolf P1 UX 改造包拆分 PRD（非 Agent）

- **文档状态**：实施拆分版 PRD，待评审后进入 Issue / Ticket
- **版本**：v0.1
- **日期**：2026-09-02
- **上级文档**：CRMWolf 非 Agent P1 UX 改造 PRD
- **范围**：将非 Agent P1 UX 改造拆成 7 个可以独立开发、独立验收和分批上线的改造包

> 本文档的拆分原则是“按关键任务闭环验收”，而不是简单按 Vue 文件或组件数量拆分。每个改造包都必须有明确的用户问题、改造边界、依赖、验收条件和可回滚范围。

## 1. 拆分结论

建议将非 Agent P1 拆成以下 7 个改造包：

| 编号 | 改造包 | 核心解决问题 | 独立验收对象 | 建议顺序 |
|---|---|---|---|---:|
| P1-PKG-01 | 财务与高风险操作风险验证 | 重复写入、不可恢复、最终状态不明 | 回款登记、审批提交、删除/退回/转移 | 0 |
| P1-PKG-02 | 统一任务状态与结果反馈 | 用户不知道加载、保存、失败和成功结果 | 列表、详情、表单、审批、回款 | 1 |
| P1-PKG-03 | 高风险操作与弹窗统一 | 误操作、重复提交、关闭丢失和焦点问题 | Customers 及高风险业务 Dialog | 2 |
| P1-PKG-04 | 对象上下文与详情层级收敛 | 客户、商机、合同、回款之间容易迷路 | CustomerDetailSheet 及关联对象流程 | 3 |
| P1-PKG-05 | 表单错误、权限和未保存恢复 | 失败后丢输入、自动返回、权限不清晰 | CustomerEdit、客户信息及业务表单 | 4 |
| P1-PKG-06 | 响应式、滚动和移动端可达性 | 固定高度、嵌套滚动、小屏和软键盘不可达 | 移动端客户跟进及详情表单 | 5 |
| P1-PKG-07 | 键盘、读屏和无障碍关键任务验收 | 复杂表格、Dialog、表单的辅助技术不可用 | 四条关键任务全链路 | 并行/发布门禁 |

### 1.1 实施策略

- **P1-PKG-01 是风险验证包**，不一定直接修改 UI，但决定财务流程是否需要提升为 P0；
- **P1-PKG-02 和 P1-PKG-03 是共享交互基础**，先在一条真实任务中落地，不建议只做抽象组件而不验证业务结果；
- **P1-PKG-04 至 P1-PKG-06 是业务闭环包**，按财务、商机、客户任务逐步迁移；
- **P1-PKG-07 是横向验收包**，不应等所有页面完成后才开始，应从第一个改造包开始建立基线。

## 2. 统一验收原则

所有改造包均遵守以下原则：

1. 不以默认桌面截图作为唯一验收依据；
2. 必须覆盖 happy path 和至少一个异常恢复路径；
3. 不能仅通过 Toast 或日志证明操作完成；
4. 不能新增临时自定义 modal 或新的旧 Token 用法；
5. 发生请求超时或网络中断时，不能诱导用户重复创建业务记录；
6. 改造必须保留原有权限边界、审计要求和业务状态语义；
7. 组件改造必须至少在一个真实业务流程中验证，而非只验证 Storybook 或孤立 Demo。

## 3. 改造包详述

## P1-PKG-01：财务与高风险操作风险验证

### 3.1 目标

在正式改造 UI 之前，确认回款登记、审批提交及高风险状态变更是否存在重复写入、状态不一致或不可恢复问题，并建立后续 UI 设计所需的后端状态契约。

### 3.2 当前系统关注点

- 回款记录涉及金额、日期、合同和回款计划等高敏感业务字段；
- 审批、状态推进和后台请求可能存在请求已提交但前端未收到响应的情况；
- 删除、退回公海、标记输单、转移、撤回、驳回和冲红的恢复方式需要业务确认；
- 成功 Toast 不能证明最终业务状态已经落库。

### 3.3 范围

- 回款登记、修改、删除和审批提交；
- 商机/合同提交审批、撤回和驳回；
- 客户退回公海、标记输单和转移；
- 网络超时、重复点击、刷新、返回和并发修改场景。

### 3.4 需求

- 为每个写操作确认是否存在幂等键或等价的重复请求保护；
- 定义请求超时后的最终状态查询方式；
- 明确每个高风险操作是可撤销、可重试、可补偿还是只能人工恢复；
- 明确部分成功的业务语义和查询接口；
- 记录操作前状态、操作后状态和审计要求；
- 输出一份前后端可共同使用的“写操作状态矩阵”。

### 3.5 独立验收

- 对回款登记、审批提交和至少一种高风险状态变更完成重复点击、网络超时和刷新恢复测试；
- 能判断请求超时后业务是否已生效，不依赖猜测；
- 明确哪些操作可以自动重试，哪些操作必须先查询最终状态；
- 明确所有不可撤销操作的人工恢复责任人和处理入口；
- 若发现重复写入、无法查询最终状态或不可恢复数据损失，标记为 P0 风险并阻止对应流程直接上线。

### 3.6 交付物

- 高风险操作清单；
- 写操作状态矩阵；
- 幂等和最终状态验证记录；
- 可撤销/可补偿/人工恢复策略表；
- P0 风险结论。

## P1-PKG-02：统一任务状态与结果反馈

### 3.7 目标

让用户在列表、详情、表单、审批和回款操作中始终知道系统正在做什么、结果是什么以及下一步怎么做。

### 3.8 当前系统关注点

- 部分页面通过 Toast 表达失败或成功；
- `CustomerEdit` 在详情获取失败时存在错误处理后返回上一页的路径；
- 选项加载失败可能只记录日志，用户不知道表单为何不可用；
- DataTable、详情 Sheet、表单和异步业务请求的状态表达不完全一致。

### 3.9 范围

- DataTable 列表加载、空数据、筛选无结果和刷新；
- CustomerDetailSheet 详情加载和关联对象加载；
- CustomerEdit 及客户信息表单加载、保存和失败；
- 商机、合同、审批和回款操作的处理中、成功、失败和重试；
- 状态卡、内嵌反馈、Toast 和页面级反馈的使用规则。

### 3.10 需求

统一定义以下状态：

- 加载中；
- 空数据；
- 筛选无结果；
- 权限不足；
- 保存中；
- 成功；
- 失败；
- 可重试；
- 部分成功；
- 后台处理中；
- 已取消。

每种状态必须定义：状态文案、展示位置、是否阻塞、用户可执行动作、是否需要持久化、辅助技术语义。

### 3.11 独立验收

- 列表、详情、表单和业务写操作各有明确的加载/空/错误/成功状态；
- 保存中不会产生重复提交；
- 失败后不清空输入，不自动跳转，提供重试或恢复动作；
- 成功反馈至少包含对象和最终状态；
- 审批、回款等长任务离开当前页面后仍可找到状态；
- 在断网、超时、500、权限不足和部分成功场景下，用户无需刷新页面即可继续。

### 3.12 交付物

- 任务状态协议；
- 状态文案和反馈位置规范；
- 共享状态组件或 composable；
- 列表、详情和表单的迁移示例；
- 异常状态回归测试清单。

## P1-PKG-03：高风险操作与弹窗统一

### 3.13 目标

把高风险操作从临时 modal 和分散的确认逻辑迁移到统一的 Dialog / AlertDialog / Sheet 交互模型，降低误操作和关闭丢失风险。

### 3.14 当前系统关注点

- `Customers.vue` 中“退回公海”和“标记输单”存在自定义 modal；
- 自定义 modal 的 Dialog 语义、焦点管理、Escape、遮罩关闭、提交中和错误恢复需要统一；
- 行操作和右键菜单可能隐藏高风险操作；
- 移动端固定宽度可能导致布局问题。

### 3.15 范围

第一批覆盖：

- 退回公海；
- 标记输单；
- 删除客户或关联对象；
- 转移客户；
- 撤回/驳回审批；
- 修改、删除或冲红回款记录。

### 3.16 需求

**确认前**：展示对象名称、对象类型、当前状态、操作后状态、影响范围和不可逆后果。

**填写中**：理由字段必须有 label、校验、错误关联和未保存保护。

**提交中**：按钮禁用重复提交，保留对象上下文，并显示进行中状态。

**成功后**：展示最终状态、对象入口、下一步和可用的撤销/恢复方式。

**失败后**：保留输入和上下文，区分校验、权限、网络、冲突和服务失败，并提供重试或人工恢复。

**关闭行为**：明确 Escape、遮罩、关闭按钮和返回动作；存在未保存输入时不得静默丢弃。

### 3.17 独立验收

- 第一批覆盖的高风险操作均使用统一组件；
- 键盘用户可打开、填写、确认、取消和修复错误；
- 读屏用户能理解当前对话框的标题、描述、对象和风险；
- 遮罩点击和 Escape 行为不会意外提交或静默丢失输入；
- 移动端不出现横向溢出或按钮不可达；
- 高风险操作至少有可验证的撤销、补偿或人工恢复路径；
- 高风险操作不只依赖右键菜单才能发现。

### 3.18 交付物

- Dialog / AlertDialog / Sheet 选型规则；
- 高风险确认文案模板；
- 通用提交中/成功/失败状态处理；
- Customers 高风险 modal 迁移；
- 键盘、读屏和移动端弹窗验收记录。

## P1-PKG-04：对象上下文与详情层级收敛

### 3.19 目标

让用户在客户、商机、合同、回款计划和回款记录之间切换时，始终知道当前对象、上一级对象和关闭范围。

### 3.20 当前系统关注点

`CustomerDetailSheet` 同时承载客户档案、客户信息、客户活动和项目旅程，并可能进一步打开商机、合同及多个业务 Dialog，导致层级、返回和滚动关系复杂。

### 3.21 范围

- CustomerDetailSheet 一级任务划分；
- 客户 → 商机 → 合同 → 回款计划/回款记录的上下文栈；
- Sheet、Dialog、详情内嵌对象之间的打开、返回和关闭；
- 页面、列表、行、详情 Footer 和关联对象的动作位置；
- 页面、表格、Sheet、Dialog 的滚动容器关系。

### 3.22 需求

- 持续显示当前对象名称、对象类型和关键状态；
- 提供明确的返回上一级和关闭整个流程入口；
- 区分返回、关闭和取消，不以相同图标表达不同语义；
- 关联对象优先复用同一上下文，不无限叠加模态层；
- 客户档案、活动、客户信息和项目旅程建立清晰任务边界；
- 打开、返回、关闭和提交后焦点恢复到可预测位置；
- 限制并行滚动容器，移动端优先自然页面滚动。

### 3.23 独立验收

- 用户在客户 → 商机 → 合同 → 回款流程任意位置都能说出当前对象和上一级对象；
- 返回上一级不会误取消已提交的业务操作；
- 关闭整个流程和返回上一级的行为可区分；
- 连续打开关联对象后不出现遮罩叠加失控、无法关闭或焦点丢失；
- 低高度桌面和移动端主要内容可达，滚动容器数量可解释。

### 3.24 交付物

- 对象上下文栈交互稿；
- CustomerDetailSheet 信息架构调整方案；
- 详情层级和返回/关闭规则；
- 滚动容器清单；
- 关键对象链路可用性测试记录。

## P1-PKG-05：表单错误、权限和未保存恢复

### 3.25 目标

让客户维护及其他业务表单在加载失败、校验失败、权限不足、网络失败和并发修改时，保留上下文和用户输入，并提供可执行的恢复路径。

### 3.26 当前系统关注点

- `CustomerEdit` 详情加载失败后存在返回上一页的处理；
- 选项加载失败可能无法直接反馈给用户；
- 客户信息包含联系人、发票抬头、部署和成员等不同维护任务；
- 多个 Dialog 叠加时，错误、焦点和未保存状态容易被遮蔽。

### 3.27 范围

- CustomerEdit；
- 客户信息及联系人、成员、部署、发票抬头相关表单；
- 商机、合同、回款相关编辑表单；
- 权限不足、选项加载失败、并发修改和未保存退出。

### 3.28 需求

- 详情加载失败提供重试、返回和权限处理入口，不默认自动返回；
- 选项加载失败指出受影响字段并提供重试；
- 字段错误与控件关联，提交后聚焦首个错误，并提供错误摘要；
- 保存失败保留用户输入，区分校验、权限、网络、服务和并发错误；
- 未保存退出时提供保存、继续编辑和放弃选择；
- 并发修改时提供刷新、查看差异或重新编辑路径；
- 空状态区分无数据、无筛选结果、尚未创建和无权查看。

### 3.29 独立验收

- 断网、超时、权限不足、选项加载失败和校验失败时，用户不需要重新填写全部内容；
- 首个错误可被键盘和读屏发现；
- 详情加载失败不丢失原页面上下文；
- 用户能理解权限问题不是普通系统故障；
- 并发修改不会诱导用户重复创建或覆盖他人数据。

### 3.30 交付物

- 表单错误分类和文案规范；
- 表单状态处理模板；
- CustomerEdit 及客户信息表单迁移；
- 未保存退出和并发修改交互稿；
- 错误恢复回归测试。

## P1-PKG-06：响应式、滚动和移动端可达性

### 3.31 目标

确保关键任务在小屏、低高度、横屏和软键盘环境下仍能完成，避免固定高度和嵌套滚动造成内容不可达。

### 3.32 当前系统关注点

- 多个列表页使用类似 `calc(100vh - ...)` 的固定高度；
- DataTable 内部存在固定表格区和内部滚动；
- CustomerDetailSheet、Dialog 和表单可能形成多重滚动；
- 移动端 Card、Sheet 和软键盘场景需要真实设备验证。

### 3.33 范围

- Customers、CustomerTracking、Contracts 等列表；
- DataTable 桌面表格和移动端 Card；
- CustomerDetailSheet；
- 客户跟进、客户维护、商机审批和回款登记表单；
- 320px 宽度、手机横屏、软键盘、低高度桌面和 safe area。

### 3.34 需求

- 桌面高密度列表可以使用固定表格区，但低高度场景必须可自适应；
- 移动端优先自然页面滚动，避免用户不知道应滚动哪个容器；
- 使用动态 viewport 和 safe area 时验证软键盘打开后的实际行为；
- 主要字段、错误信息、提交按钮和返回入口在窄屏和放大字体下可达；
- Card 操作入口和详情操作入口不被固定高度裁切；
- 横向溢出、遮挡和粘性区域冲突必须可检测。

### 3.35 独立验收

- 320px 宽度、手机横屏和软键盘打开时，四条关键任务均可完成核心操作；
- 低高度桌面不会把工具栏、主要内容和分页同时挤出可视区域；
- 无法通过默认滚动路径访问的内容视为验收失败；
- 不出现无法关闭的 Sheet、被软键盘遮挡的字段或不可点击的提交按钮；
- reduced motion 下不影响状态反馈和导航理解。

### 3.36 交付物

- 响应式场景矩阵；
- 列表、详情和表单滚动容器调整方案；
- 移动端关键任务交互稿；
- 真机和不同高度 viewport 验收记录；
- 小屏回归用例。

## P1-PKG-07：键盘、读屏和无障碍关键任务验收

### 3.37 目标

将无障碍从组件属性检查提升为关键任务级验收，确保表格、行操作、Dialog、表单错误和状态反馈在辅助技术下可理解和可操作。

### 3.38 当前系统关注点

- DataTable 使用整行交互、tabindex 和上下文菜单键盘支持，需要真实读屏确认表格语义是否冲突；
- Dialog、Sheet 和行内操作的焦点进入、恢复与重复触发需要全链路验证；
- 已有 aria 状态和错误关联基础，但不能仅凭代码属性数量证明体验可用。

### 3.39 范围

- DataTable 行、行内按钮、筛选、排序和上下文菜单；
- Dialog / AlertDialog / Sheet；
- 表单 label、错误摘要、字段错误和提交中状态；
- 加载、成功、失败、权限不足和后台处理中状态；
- 客户跟进、客户维护、商机审批和回款登记四条关键路径。

### 3.40 需求

- 明确 Tab 顺序、Enter / Space、ContextMenu 键和 `Shift + F10` 行为；
- Dialog 有正确标题、描述、焦点进入、焦点恢复和 Escape 行为；
- 行内按钮不会重复触发行点击；
- 读屏可获得对象名称、关键状态和操作结果；
- 错误信息与字段关联，错误摘要可被发现；
- 成功、失败、风险和权限状态不依赖颜色单独表达；
- 加载、保存中和状态变化能被辅助技术感知。

### 3.41 独立验收

- 首个错误、保存中、成功、失败和权限不足状态均可被理解；
- 无障碍阻断问题作为发布阻断项，而不是降级为后续视觉优化。

### 3.42 交付物

- 无障碍关键任务测试脚本；

- 问题分级及修复清单；

## 7. 完成定义（Definition of Done）

一个改造包只有同时满足以下条件，才可标记为完成：

1. 需求范围内的页面和组件已明确迁移清单；
2. 至少一条真实业务闭环已完成 happy path 验证；
3. 至少一个网络、权限、校验、并发或用户取消异常路径已验证；
4. 视觉、交互、前端、后端状态和权限边界已共同确认；
5. 移动端或响应式要求已按改造包范围验收；
6. 键盘和读屏要求已按改造包范围验收；
7. 关键指标有基线和改造后记录，或明确记录暂无法采集的原因；
8. 不引入新的临时 modal、重复状态模型或旧 Token 用法；
9. 有回滚方式和已知遗留问题清单；
10. 能拆分为后续 GitHub Issue / Ticket，并且每个 Ticket 仍然指向一个用户任务结果。
