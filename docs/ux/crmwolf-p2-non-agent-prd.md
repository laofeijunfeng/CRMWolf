# CRMWolf 非 Agent P2 UX 优化 PRD

- **文档状态**：PRD 初稿，基于当前代码审计整理，待产品、设计、研发和业务负责人评审
- **版本**：v0.1
- **日期**：2026-09-04
- **上级文档**：CRMWolf 非 Agent P1 UX 改造 PRD
- **关联分析**：CRMWolf UX 问题地图 + 关键任务优先级
- **范围说明**：本文仅覆盖非 Agent 的 P2 UX 剩余缺口；AI / Agent 自动化及相关指标不在本期范围

> 本文不是对原始 UX 问题清单的重复搬运，而是结合当前源码和已有 P1 改造结果后的“剩余 P2 需求”。已经实现的能力列入排除项，不再作为本期开发需求。

## 1. 结论先行

当前系统不存在需要重新建设的 DataTable 基础能力、行操作入口或通用列表状态能力。P2 的主要问题已经从“有没有功能”收敛为“已有能力是否足够透明、一致、可治理和可度量”。

本期建议保留 5 个独立改造包：

| 编号 | 改造包 | 核心问题 | 独立验收 |
|---|---|---|---|
| P2-01 | 列表视图状态透明化与渐进披露 | 工具能力已齐，但当前筛选、排序、列配置和视图状态不够持续可见，工具栏也缺少层级 | 是 |
| P2-02 | 行操作语义与跨页面一致性治理 | 操作入口已可发现，但同类动作的命名、层级、禁用原因和结果反馈仍可能不一致 | 是 |
| P2-03 | 页面动作收尾与下一步导航一致性 | 操作成功后经常只刷新或弹 Toast，用户下一步缺少稳定预期 | 是 |
| P2-04 | 设计系统迁移治理与共享状态组件收敛 | Token、颜色和空/加载/错误组合仍存在历史分叉，缺少持续门禁 | 是 |
| P2-05 | 关键任务性能与反馈度量 | 当前缺少普通业务 UX 关键指标，无法判断等待、重复点击和失败恢复成本 | 是 |

这 5 个改造包不改变客户、商机、合同、回款、审批等既有业务规则，也不要求重新设计业务流程。优先级建议为：P2-01、P2-03、P2-05 先行，P2-02 与 P2-04 可并行推进。

## 2. 系统现状核对与排除项

### 2.1 已实现，不纳入本期需求

经源码核对，下列能力已经存在，不能在本 PRD 中再次立项：

- `DataTable` 统一组件，以及搜索、筛选、排序、分页和列配置基础能力；
- 列显示/隐藏、自定义筛选视图、个人/团队视图范围等基础能力；
- 列表 loading、Skeleton、空数据、筛选无结果、错误保留旧数据和重试基础状态；
- 表格固定高度、表头固定、表格内部滚动、横向滚动和分页固定在表格卡片底部；
- 桌面端行主操作、“更多”菜单、右键菜单、键盘菜单和移动端卡片操作区；
- 操作列按当前页操作需求动态计算宽度，避免按钮被裁切；
- P1 已建设的统一错误类型、字段错误解析、结果未知提示和部分页面的恢复反馈；
- P1 高风险操作 Dialog / Sheet 的基础规范和迁移方向；
- 设计系统文档、V2 语义 Token、焦点/禁用/主题/动效等基础定义；
- Agent / AI 自动化、Agent 任务状态和相关指标。

主要核对依据包括：`CRM-Client/src/components/crmwolf/DataTable.vue`、`ListFilterPopover.vue`、`ListSortPopover.vue`、`ColumnConfigPopover.vue`、`useCustomFilterViews.ts`、`DesktopTableRowActions.vue`、`TableRowActions.vue`、各业务列表页，以及 `CRM-Docs/design-system/` 下的设计系统文档。

### 2.2 本期只处理的剩余缺口

本期只处理以下五类问题：

1. 已有列表工具缺少当前状态摘要和清晰的首屏层级；
2. 已有行操作入口的跨页面语义和反馈不一致；
3. 低风险业务操作完成后缺少统一、适度的下一步收尾；
4. 设计系统已有规范但迁移和治理没有形成闭环；
5. 普通业务关键任务没有统一的 UX 性能和结果度量。

## 3. 背景与问题定义

CRMWolf 已完成一轮 P1 基础体验收敛，系统在“能操作”和“出现基础反馈”方面已有明显基础。但在持续使用中，用户仍需要额外解释和记忆：当前列表为什么显示这些数据、某个按钮到底代表什么、完成操作后下一步应该做什么，以及某次等待或失败究竟发生在接口、前端还是用户反馈层。

这些问题单独看通常不会阻断功能，但会持续增加认知成本、误操作概率和排查成本，尤其影响高频列表工作、跨页面业务动作和低频异常场景。因此 P2 不再扩大基础组件范围，而是对已有能力做透明化、一致性、收尾和度量治理。

## 4. 产品目标

### 4.1 总体目标

- 让用户在列表中持续知道当前视图由哪些条件构成；
- 让同一业务动作在不同页面使用相同的名称、层级和结果表达；
- 让保存、审批、状态推进和登记等操作完成后，用户知道结果及合理的下一步；
- 让设计 Token 和共享状态组件的迁移有清单、有规则、有检查结果；
- 建立普通业务关键任务的 UX 数据基线，为后续优化提供证据。

### 4.2 成功标准

- 用户离开筛选、排序或视图弹层后，仍能在列表上下文中判断当前数据集的主要来源；
- 同一业务动作在桌面按钮、更多菜单、右键菜单和移动端操作区中不出现语义分叉；
- 低风险保存和状态推进完成后，用户无需猜测是否成功，也不被无必要的二次弹窗打断；
- 新增代码不再扩大旧 Token、raw color 和重复状态组件的使用范围；
- 能够统计关键任务的首个反馈时间、完成时间、成功/失败/重试/结果未知和重复点击情况。

## 5. 非目标与约束

- 不新增 CRM 业务对象、字段、审批规则或财务规则；
- 不改变现有客户、商机、合同、回款、发票和审批的业务流转顺序；
- 不把所有操作都改成多步骤向导，也不为低风险操作增加确认弹窗；
- 不重复建设 DataTable、筛选排序、列配置、固定高度和行操作入口；
- 不进行全量视觉换肤、品牌色重构、圆角/阴影重做；
- 不以 P2 方案替代 P1 的高风险确认、错误恢复、响应式和无障碍验收；
- 不采集业务敏感数据，不记录客户名称、合同金额、回款金额等可识别业务内容；
- AI / Agent 自动化及相关指标完全排除在本期之外。

## 6. 需求详述

## P2-01：列表视图状态透明化与渐进披露

### 6.1 用户问题

列表的筛选、排序、列配置和自定义视图基础能力已经存在，但用户关闭弹层后，往往无法快速确认当前结果集的主要条件。工具按钮同时平铺时，首屏选择数量也偏多；当视图切换、异步应用或配置加载失败时，用户缺少稳定的上下文说明。

### 6.2 当前实际状态

主要列表页已统一使用 `DataTable`，并配置筛选、排序、列配置、自定义视图、固定高度和内部滚动。当前缺口不是补齐这些能力，而是把“当前状态”从弹层内部提升为列表上下文的一部分，并对常用工具和高级工具做轻量分层。

覆盖页面至少包括：客户、客户跟进、线索、商机、合同、回款计划、回款记录、发票和审批中心。

### 6.3 产品需求

**工具栏分层。** 搜索、刷新和当前业务最常用的筛选入口默认可见；排序、列配置、保存/管理视图等低频工具收进“更多设置”或同类的高级工具入口。现有能力的入口不能被隐藏到用户无法发现的位置。

**当前视图摘要。** 在表格顶部、工具栏下方或同等稳定区域展示当前主要状态，包括当前视图名称/范围、已生效筛选数量、排序状态和隐藏列数量。无条件时显示“全部数据”或页面对应的默认语义，不显示空白区域。

**条件可移除。** 对已生效的筛选条件提供单项移除；提供“一键清除筛选”入口。清除筛选时明确说明不会影响排序、列显示和已保存视图，除非当前页面确实存在不同规则。

**视图切换反馈。** 切换内置 Tab 或自定义视图时，保留当前列表容器和滚动结构，显示轻量的“正在应用视图”状态；应用失败时保留原视图数据，并提供局部重试，不要求刷新整页。

**状态与分页关系。** 筛选、排序或视图改变后，分页回到第一页；摘要与实际请求参数保持一致；刷新或返回列表时，在既有业务允许的范围内保留当前视图上下文。

### 6.4 不改变的既有行为

不改变现有筛选、排序、列配置、自定义视图、固定高度、表格内部滚动、分页和移动端 Card 行为。不要求把所有高级工具改成新的交互控件，也不要求新增后端查询能力。

### 6.5 验收标准

- 关闭筛选、排序、列配置弹层后，用户仍能看到当前视图的主要状态摘要；
- 无筛选、单条件、多条件、筛选无结果和清除筛选场景均有明确表现；
- 视图应用中不会出现整页空白或误显示旧视图名称；
- 视图应用失败时，原有数据和用户上下文保留，局部重试可恢复；
- 切换条件后分页正确回到第一页，表格仍保持固定高度和内部滚动；
- 桌面宽度、窄屏和移动端下，摘要不会遮挡搜索、刷新和主要动作；
- 各主要列表的工具命名和状态摘要结构一致。

## P2-02：行操作语义与跨页面一致性治理

### 6.6 用户问题

行操作入口已经从“主要依赖右键”改为桌面主操作 + 更多菜单 + 右键/键盘 + 移动端操作区，但同类业务动作在不同列表的名称、主次层级、禁用原因和完成反馈仍可能不一致。用户因此需要重新理解“编辑、查看、提交、完成、撤回、下载、删除”等动作。

### 6.7 当前实际状态

`DesktopTableRowActions`、`TableRowActions` 和 `DataTable` 已提供统一的操作承载方式，并按当前页操作需求计算操作列宽度。本期不再增加入口，而是建立跨页面的动作语义治理表，并对差异进行收口。

### 6.8 产品需求

**动作命名统一。** 建立业务动作词典，明确查看/详情、编辑、完成/关闭、提交、撤回、驳回、删除、下载、复制和更多等词的适用场景。动作名称使用业务结果，不使用同义混称。

**主次层级统一。** 高频且低风险的当前任务动作作为主操作；低频、危险或需要进一步确认的动作进入更多菜单；详情打开和行点击的关系保持一致。主操作规则不得仅由单个页面开发者自行决定。

**多入口语义一致。** 同一动作在桌面按钮、更多菜单、右键菜单和移动端 Card 中使用相同名称、禁用状态、禁用原因和后续结果。入口可以因设备不同而改变承载形式，但不能改变动作含义。

**不可用原因可理解。** 对权限不足、状态不允许或缺少前置数据导致的不可用动作，提供简短原因；不能只通过灰色按钮让用户猜测。

**反馈归属一致。** 操作反馈明确指向对象和结果；失败时沿用 P1 的错误分类和恢复契约，不另起一套 Toast 或弹窗规则。

### 6.9 不改变的既有行为

不撤回桌面端可见操作、更多菜单、右键菜单、键盘入口和移动端操作区；不把所有操作强制平铺；不改变危险操作的确认规则；不改变后端权限判断和业务状态机。

### 6.10 验收标准

- 主要列表均有动作词典映射，且同一动作不存在无理由的多种叫法；
- 同一动作在至少两种承载形式下名称、禁用原因和结果反馈一致；
- 主操作数量和选择规则可解释，危险操作不会因“可见性”而被提升为默认主操作；
- 不可用动作能说明用户可理解的原因或前置条件；
- 操作列仍能容纳当前页所需按钮，不出现裁切、跳动或遮挡；
- 验收不以“是否增加了按钮”为标准，而以语义一致、结果可理解为标准。

## P2-03：页面动作收尾与下一步导航一致性

### 6.11 用户问题

不同页面的保存、提交、审批、状态推进和登记完成后，系统有时只刷新列表，有时只显示短时 Toast，有时会打开下一步 Dialog。用户能够知道“请求结束”，但不一定知道对象最终处于什么状态、下一步可以做什么，或是否应该继续留在当前上下文。

### 6.12 当前实际状态

系统已具备操作级 Toast、列表刷新、部分页面的下一步 Dialog 和 P1 的结果反馈基础，但成功后的收尾模式尚未形成统一契约。本期只收敛低风险和常规任务，不重做 P1 高风险操作的确认与恢复。

### 6.13 产品需求

**低风险编辑/保存。** 成功后保留当前页面或详情上下文，反馈“哪个对象已保存”；如果存在明显下一步，提供非阻塞的查看详情、继续创建或返回列表入口，不强制弹窗。

**状态推进。** 完成、关闭、提交、审批等动作成功后，反馈对象的最终状态和当前可执行的后续动作。列表数据、详情状态和操作按钮应同步更新，避免用户看到旧状态。

**财务常规操作。** 回款登记、计划更新、发票相关常规保存完成后，明确显示结果对象和是否需要后续审批；结果未知时沿用 P1 的查询/重试语义，不直接提示“成功”。

**返回与焦点。** 从详情、Sheet 或 Dialog 完成操作后，返回位置和焦点恢复到可预测的列表行、详情分区或触发按钮；不因为收尾反馈而打断用户原本的浏览上下文。

**反馈强度分级。** 成功 Toast 只承担短反馈；影响后续业务的结果使用页面内状态、对象状态或可进入详情的持久反馈；不为每一次成功都追加第二个弹窗。

### 6.14 不改变的既有行为

不改变业务动作本身、审批链、状态机和接口契约；不强制用户进入详情页；不强制所有操作跳转；不取消现有必须保留的下一步 Dialog；不把 P1 高风险操作的确认、提交中和恢复逻辑降级为普通 Toast。

### 6.15 验收标准

- 至少覆盖客户保存、跟进完成、商机状态推进、合同/审批提交、回款登记等代表性任务；
- 每个代表性任务都有明确的成功结果、对象状态和下一步表达；
- 成功后列表、详情和按钮状态不长期停留在旧数据；
- 用户不需要刷新页面才能判断常规操作是否生效；
- 低风险操作不会被无必要的二次弹窗打断；
- 从 Sheet/Dialog 返回后，用户仍能回到原列表上下文或原触发位置；
- 失败、超时和结果未知场景继续遵循 P1 恢复规范。

## P2-04：设计系统迁移治理与共享状态组件收敛

### 6.16 用户问题

设计系统已经定义了 V2 语义 Token、焦点、禁用、主题和状态规范，但源码中仍存在旧 Token、raw color、页面级重复样式及多个状态组合。短期看是代码维护问题，长期会造成不同页面的颜色、状态、间距和反馈表达再次分叉。

### 6.17 当前实际状态

`CRM-Docs/design-system/` 已有组件、模式、迁移和治理文档，`CRM-Client/src/styles/variables-v2.scss` 和基础样式也已建立。但审计仍发现部分页面或共享组件存在 raw hex、rgba 和历史 Token 引用，且需要把“规范已定义”转化为“新增代码不再扩大分叉、遗留点按优先级迁移”。

优先审计对象包括：`AppLayout.vue`、`SalesDashboard.vue`、`MetricCard.vue`、`TopBarTabs.vue`、`PaymentPlanDetailContent.vue` 及高频空/加载/错误/反馈组合。

### 6.18 产品需求

**建立迁移清单。** 按共享组件、高频页面、低频页面记录旧 Token/raw color、替代 Token、负责人、状态和回归风险。清单以可验证代码位置为单位，不做笼统的“全站换肤”。

**新增代码门禁。** 新增或修改的业务样式不得继续引入可由语义 Token 替代的 raw hex、rgba 或历史 Token；例外必须在代码或迁移清单中说明原因。

**优先收敛共享组件。** 先处理被多个页面复用的颜色、状态、卡片、Tab、空状态、加载态、错误态和反馈组合，再处理单个低频页面，避免重复修复。

**统一状态组合。** 对空、加载、错误、无结果和操作反馈建立推荐组合与使用边界，保留页面差异所需的文案和业务内容，不要求所有页面视觉完全相同。

**迁移后回归。** 重点验证暗色/亮色主题、状态色对比度、焦点环、禁用态、移动端布局和 reduced motion，不因 Token 迁移破坏既有 P1 可达性。

### 6.19 不改变的既有行为

不进行全量视觉重做；不强制删除兼容层；不为了“清理得更彻底”修改业务组件的行为、布局高度或 DataTable 滚动模型；不把设计系统治理变成一次性大规模重构。

### 6.20 验收标准

- 有可追踪的迁移清单，至少覆盖已确认的共享组件和高频页面遗留点；
- 新增代码检查能够识别主要旧 Token/raw color 引用，并支持合理例外；
- 共享组件的状态色、焦点、禁用态和主题表现通过回归；
- 空/加载/错误/无结果组合不再因页面复制而产生明显语义分叉；
- 迁移不会导致 DataTable 固定高度、内部滚动、操作列和移动端布局回归；
- 文档中的设计系统实现状态与源码审计结果保持同步。

## P2-05：关键任务性能与反馈度量

### 6.21 用户问题

当前普通业务流程缺少统一的前端 UX 度量。系统无法稳定回答：用户点击后多久得到首个反馈、多久完成、是否重复点击、失败后是否重试、结果是否未知，以及等待主要来自接口还是前端呈现。

### 6.22 当前实际状态

`request.ts` 已有 Axios 请求和 30 秒超时，部分页面有请求序号或局部状态处理，但未发现覆盖普通业务关键任务的统一前端 telemetry、interaction id、请求耗时和任务结果模型。后端局部 duration 或业务 telemetry 不能替代前端用户体验指标。

### 6.23 产品需求

**定义事件模型。** 普通业务事件至少包含任务开始、首个可见反馈、请求完成、成功、失败、重试、取消和结果未知。每次用户发起的关键任务生成不可识别用户和业务内容的 interaction id。

**首批覆盖任务。** 客户保存、跟进完成、商机状态推进、合同/审批提交、回款登记、列表首次加载、列表刷新、筛选/排序/视图应用。Agent / AI 任务不在本期采集范围。

**区分时间指标。** 分别记录点击到首个反馈、点击到请求结束、请求结束到界面完成更新；列表场景补充首屏可交互时间和刷新完成时间。

**记录结果而非业务内容。** 仅记录页面、动作类型、结果类型、HTTP 状态类别、耗时区间、重试次数和是否重复点击等必要维度，不记录客户名称、合同金额、回款金额、自由文本和完整请求参数。

**支持异常分析。** 能按页面、动作类型和结果类别查看长尾耗时、失败率、结果未知率、重试率和重复点击率；异常指标与 P1 的错误分类、恢复路径相互关联。

**性能预算。** 首次实施先建立基线，不预先拍脑袋规定所有接口必须达到同一个绝对耗时。基于基线为首批关键任务设定 P2 后续迭代可执行的目标区间。

### 6.24 不改变的既有行为

不改变接口超时策略、业务请求顺序和用户可见流程；不为了采集指标增加阻塞式确认或额外表单；不采集 Agent / AI 业务数据；埋点失败不能影响业务操作。

### 6.25 验收标准

- 首批关键任务均能产生可关联的开始、首反馈和最终结果事件；
- 成功、失败、重试、取消和结果未知能够区分，重复点击能够识别；
- 事件中不包含客户、合同、金额和自由文本等敏感内容；
- 埋点异常、网络不可用或采集服务故障不影响主流程；
- 能生成页面/动作维度的基础耗时和结果报表；
- 产品、研发和 UX 能依据基线确定下一轮性能优化对象，而不是依赖主观感受。

## 8. 实施顺序与依赖

### 8.1 建议顺序

1. **P2-01 列表视图状态透明化**：依赖现有 DataTable 和视图状态，收益直接、风险较低；
2. **P2-03 页面动作收尾**：依赖 P1 结果反馈契约，可与 P2-01 并行设计；
3. **P2-05 关键任务度量**：在 P2-01/P2-03 的交互规则稳定后接入，避免采集不稳定事件；
4. **P2-02 行操作语义治理**：可与前述工作并行，先产出动作词典和差异清单；
5. **P2-04 设计系统治理**：贯穿上述改造，作为新增代码的门禁和迁移约束。

### 8.2 依赖

- P1 任务状态、错误恢复、高风险操作和无障碍规范作为基础约束；
- 业务负责人确认各模块动作名称、状态含义和下一步规则；
- 研发提供可安全使用的 telemetry 接入方式和数据留存策略；
- 设计系统维护者确认 Token 例外、状态组件边界和迁移优先级。

## 9. 跨改造包验收要求

- [ ] 代表性列表在桌面、窄屏和移动端保持固定高度、内部滚动和分页行为；
- [ ] 筛选、排序、视图切换后，当前状态和请求结果保持一致；
- [ ] 同一行操作在不同入口下语义一致，危险操作仍遵循 P1 确认规则；
- [ ] 保存、状态推进、审批和回款等任务完成后有明确结果和适度下一步；
- [ ] 错误、超时、权限不足和结果未知继续保留 P1 的上下文和恢复能力；
- [ ] Token 迁移和状态组件收敛不破坏焦点、主题、响应式和 DataTable 行为；
- [ ] 关键任务指标可查询，且不采集敏感业务内容；
- [ ] 不包含 Agent / AI 自动化需求，不引入与本期无关的视觉重做。

## 10. 风险与待确认事项

**业务词汇风险。** “完成”“关闭”“提交”“审批通过”等词在不同模块可能具有不同业务含义，需要业务负责人确认词典，而不是只按 UI 文字强行统一。

**成功后下一步风险。** 不同角色的下一步可能不同，P2 只统一反馈契约和默认路径，不应把所有角色强制导向同一页面。

**视图状态风险。** 筛选、排序、列配置和自定义视图的持久化边界可能不同，需要确认哪些状态跨刷新、跨页面和跨用户保留。

**埋点合规风险。** telemetry 需要由产品、研发和安全/合规负责人确认字段白名单、留存周期和访问权限。

**迁移回归风险。** Token 和共享状态组件迁移可能影响主题、无障碍对比度和移动端布局，应按组件批次回归，禁止一次性全量替换。

## 11. 交付物

- 列表视图状态摘要与工具分层规范；
- 跨页面行操作动作词典和差异清单；
- 页面动作成功收尾与下一步反馈契约；
- Token/状态组件迁移清单、检查规则和回归记录；
- 普通业务关键任务 telemetry 事件字典、字段白名单和基础报表；
- 代表性页面的验收记录和遗留问题清单。

## 12. 与 P1 的边界

P1 解决关键任务是否可靠：状态是否明确、高风险操作是否可控、错误是否可恢复、对象上下文是否清晰、关键任务是否可达。P2 解决在这些基础能力已有之后，系统是否足够透明、一致、可治理和可度量。

因此，本 PRD 不重复 P1 的 Dialog、错误反馈、详情层级、固定高度、移动端和无障碍建设；如果实施过程中发现某个页面仍未达到 P1 基线，应回到对应 P1 改造包处理，而不是把 P1 缺口混入 P2。
