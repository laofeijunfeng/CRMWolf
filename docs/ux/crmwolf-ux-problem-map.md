## 1. 执行摘要

### 1.1 总体判断

CRMWolf 已经具备较完整的 UX 基础设施，但目前的主要问题不是缺少某个单独的控件，而是**跨页面的一致性和复杂任务的收束程度不足**：

- 导航、列表、移动端、Agent 状态和无障碍已经有明确的 V2 建设方向；
- 业务页面仍存在旧 Token、临时 modal、自行管理请求状态、固定高度和多层详情等实现分叉；
- Agent 已经开始承担异步复杂度，但“建议、草稿、已保存、后台处理中、失败、可撤销”之间的业务语义还需要统一；
- 客户详情、商机推进和财务执行涉及多个对象及权限，当前需要进一步降低用户的记忆负担和层级判断负担。

**不建议立即进行一次大规模视觉重做。** 更优先的方向是建立以下 4 套跨页面 UX 规则：

1. **任务状态规则**：加载、空、错误、权限不足、处理中、成功、失败、重试、取消；
2. **高风险操作规则**：删除、退回、转移、输单、审批、回款和发票操作；
3. **自动化透明规则**：AI 做了什么、依据什么、何时写入、如何修改和撤销；
4. **复杂信息分层规则**：列表、详情 Sheet、关联对象详情、Dialog 的职责边界。

### 1.2 优先级结论

| 优先级 | 重点 | 判断 |
|---|---|---|
| P0 | 当前是否存在不可恢复的数据损失、重复写入或 AI 静默改写 | 静态分析尚未确认 P0；需要通过异常路径测试排查 |
| P1 | 弹窗/焦点、高风险操作、统一状态反馈、Agent 自动化透明度、详情层级、响应式可达性 | 应优先进入 UX 改造计划 |
| P2 | 列表高级能力的渐进披露、行操作可发现性、Token 收敛、成功后的下一步 | 在 P1 稳定后推进 |
| P3 | 视觉精修、动效、空状态和愉悦度增强 | 不应先于任务可靠性和可恢复性 |

## 2. 分析框架

飞书 UX 规范强调：心理学原则是决策镜头，不是机械套用的公式。本文对每个问题同时看 4 个维度：

1. **用户任务**：用户想完成什么，而不是页面提供了什么功能；
2. **原则映射**：问题涉及 Jakob、Fitts、Miller、Hick、Postel、峰终、视觉显著性、Tesler、Doherty 或伦理规范中的哪一项；
3. **当前证据**：当前代码或设计系统中的可观察事实；
4. **风险与验证**：问题可能造成什么影响，以及需要用什么测试确认。

### 2.1 风险等级定义

- **P0**：可能导致不可恢复的数据损失、重复业务写入、越权或用户无法完成关键任务；需要阻断发布或立即验证。
- **P1**：显著影响关键任务完成、错误恢复、数据安全、自动化信任或无障碍；应优先处理。
- **P2**：主要影响效率、认知负荷、可发现性和跨页面一致性；适合系统性优化。
- **P3**：主要影响视觉精致度、愉悦度和长期体验；应建立在 P1/P2 基础上。

## 5. 详细问题地图

## A. 关键任务可靠性

### A1. 加载、空、错误、处理中和成功状态不统一

- **优先级**：P1
- **对应原则**：Postel、峰终定律、Doherty 阈值、Tesler 定律
- **用户任务**：确认系统是否收到操作、当前数据是否可用、失败后继续完成任务。

#### 当前观察

当前系统已经有 loading、skeleton、toast、Agent processing 和后台任务状态，但不同页面仍自行管理状态，呈现模型不完全一致：

- 有些失败只通过 Toast 告知；
- 有些失败后直接返回上一页；
- 有些选项加载失败只写日志；
- 有些表单使用局部 spinner；
- 普通业务请求和 Agent 异步任务的状态语义不统一。

`CustomerEdit.vue` 是一个明确例子：

```ts
catch (error: unknown) {
  handleApiError(error, '获取客户详情')
  router.back()
}
```

见：`CRM-Client/src/views/CustomerEdit.vue:96-101`。

选项加载失败时只记录日志：

```ts
catch (error) {
  logger.error('[CustomerEdit]', '获取选项失败', { error })
}
```

见：`CRM-Client/src/views/CustomerEdit.vue:104-111`。

#### UX 风险

- 用户不知道表单为什么不可用；
- 用户失去原有编辑上下文；
- 失败后没有明确重试入口；
- 用户无法判断数据究竟保存成功还是请求失败；
- 同一种失败在不同页面呈现不同，增加学习成本。

#### 优化方向

建立全局请求状态协议，而不是继续增加单页 if/else：

| 状态 | 最低呈现要求 |
|---|---|
| 加载中 | 正在加载什么，必要时显示结构化 Skeleton |
| 空状态 | 是没有数据、没有筛选结果，还是尚未创建 |
| 错误 | 发生了什么，是否影响当前任务 |
| 可重试 | 直接提供重试，不要求用户刷新或返回 |
| 权限不足 | 说明权限边界和可替代动作 |
| 保存中 | 禁止重复提交，并保留当前上下文 |
| 成功 | 明确保存对象和结果 |
| 失败 | 保留输入，提供修复或重试 |
| 后台处理中 | 显示任务状态、预计时间和离开页面后的行为 |

#### 验证方式

- 断网、超时、接口 500、权限不足、重复提交；
- 用户是否能在不刷新页面的情况下完成恢复；
- 错误后再次完成任务的时间；
- 用户是否能正确回答“这次操作到底成功了吗”。

### A2. 高风险操作的确认、后果和撤销不统一

- **优先级**：P1
- **对应原则**：Fitts、Postel、峰终定律、伦理规范
- **用户任务**：删除、退回、输单、转移、审批、冲红、回款操作时，确认影响范围并避免误操作。

#### 当前观察

客户列表中“退回公海”和“标记输单”仍使用临时自定义 modal：

- `CRM-Client/src/views/Customers.vue:979-1029`
- `CRM-Client/src/views/Customers.vue:1170-1190`

这两个弹窗使用普通 `div`、遮罩点击关闭和普通表单控件。当前呈现层未体现统一的：

- Dialog 语义；
- 焦点进入和恢复；
- Escape 行为；
- 未保存输入保护；
- 字段错误关联；
- 提交中状态；
- 成功后的结果确认和撤销。

项目其他区域已经使用 `Dialog`、`AlertDialog` 和 `Sheet`，因此这里形成了明显的交互模型分叉。

#### UX 风险

- 用户可能误触遮罩而丢失已填写原因；
- 读屏用户可能无法识别当前是一个模态对话框；
- 移动端 `min-width: 400px` 可能造成布局问题；
- 危险操作的对象、后果、不可逆性不一定足够清晰；
- 操作成功后仅看到 Toast，无法确认业务对象的最终状态。

#### 优化方向

统一高风险操作模型：

1. **确认前**：展示对象名称、操作后状态、影响范围和不可逆后果；
2. **确认中**：明确提交中，禁止重复提交；
3. **成功后**：展示实际结果、下一步和必要的撤销入口；
4. **失败后**：保留输入和上下文，提供重试；
5. **关闭时**：有未保存输入时，明确询问是否放弃；
6. **移动端**：使用适合窄屏的 Dialog/Sheet，不依赖固定宽度。

#### 验证方式

- 任务完成率和误操作率；
- 取消路径完成时间是否不明显高于确认路径；
- 用户能否复述操作后果；
- 键盘、读屏、Escape、遮罩点击和焦点恢复测试；
- 删除、退回、输单是否具备实际撤销或人工恢复路径。

### A3. AI 自动化的结果边界和人工接管不够清晰

- **优先级**：P1
- **对应原则**：Tesler、Postel、Doherty、峰终定律、伦理规范
- **用户任务**：使用 Agent 处理客户活动、客户档案、评分、建议或后台任务，并准确知道哪些内容已经生效。

#### 当前观察

Agent 已有较完整的技术状态展示。客户智能档案刷新流程也已经区分：

- 正在更新；
- 更新成功；
- 更新失败；
- 仍在后台更新。

见：`CRM-Client/src/views/CustomerDetailSheet.vue:435-459`。

但对于 CRM 业务数据而言，还需要进一步明确：

- AI 生成的是建议、草稿还是正式数据；
- 哪些字段被 AI 新增或修改；
- 信息来自用户输入、历史数据还是模型推断；
- AI 的评分或建议依据是什么；
- 低置信度结果如何处理；
- 用户是否必须确认后才写入；
- 后台任务失败后是否可以人工接管；
- 是否可以撤销自动写入。

#### UX 风险

- 用户可能把 AI 建议误认为系统事实；
- 用户可能不知道客户数据已经被自动修改；
- 长任务完成后，用户只看到“成功”，但不知道具体改动；
- AI 失败或降级时，用户可能继续使用不完整信息；
- 自动化效率提高，但信任和责任边界变模糊。

#### 优化方向

为每类 Agent 行为定义统一的结果卡片：

- **动作类型**：建议 / 草稿 / 已确认写入 / 后台任务；
- **影响对象**：客户、活动、商机、合同、回款等；
- **变更摘要**：新增、修改、未处理的字段；
- **依据和不确定性**：来源、证据、置信度或缺失信息；
- **用户动作**：确认、编辑、拒绝、重试、撤销；
- **最终状态**：已保存、部分保存、失败、等待人工。

#### 验证方式

- 用户能否区分“建议”和“事实”；
- 用户能否找到 AI 的依据和变更摘要；
- 用户能否拒绝、编辑和撤销；
- 任务失败后能否人工完成同一任务；
- 用户是否知道离开页面后后台任务仍会继续。

## B. 信息架构和复杂度

### B1. CustomerDetailSheet 承载过多任务

- **优先级**：P1/P2
- **对应原则**：Miller、Hick、Tesler、Jakob
- **用户任务**：在客户上下文中快速查看档案、添加活动、推进商机或维护关联信息。

#### 当前观察

客户详情 Sheet 一级导航目前包含：

- 客户档案；
- 客户信息；
- 客户活动；
- 项目旅程。

见：`CRM-Client/src/views/CustomerDetailSheet.vue:167-178`。

整体采用 Sheet + ContextTabs + ScrollArea + Footer 结构：

- `CRM-Client/src/views/CustomerDetailSheet.vue:961-1008`
- `CRM-Client/src/views/CustomerDetailSheet.vue:1007-1155`
- `CRM-Client/src/views/CustomerDetailSheet.vue:1157-1194`

`customer-info` 中还集中承载联系人、发票抬头、授权、部署、团队成员等管理内容；底部又可能出现新建联系人、新建抬头、新建部署和编辑等多个动作。

#### UX 风险

- “客户信息”成为多个不同任务的集合，而不是单一用户心智模型；
- 用户需要在长页面中寻找低频管理内容；
- 底部多个按钮竞争主操作；
- 客户、商机、合同、回款等关联对象可能形成多层 Sheet/Dialog；
- 用户需要始终判断当前正在操作哪一个对象、哪一层级。

#### 优化方向

建议先做任务分层，再决定是否拆组件或拆页面：

| 层级 | 建议承载内容 |
|---|---|
| 客户核心 | 客户档案、客户活动、商机旅程 |
| 客户管理 | 基本信息、联系人、成员、部署、发票抬头 |
| 业务关联 | 合同、发票、回款计划、回款记录 |
| 高风险流程 | 转移、删除、审批、退回、输单 |

可能的交互策略：

- 保留高频一级 Tab；
- 对低频内容使用二级分组或“更多关联信息”；
- Footer 只放当前 Tab 的主操作；
- 次要动作放在当前卡片或局部更多菜单；
- 嵌套详情明确显示“返回客户 / 返回商机 / 返回合同”；
- 控制嵌套层级，避免用户在多个 Sheet/Dialog 中迷路。

#### 验证方式

- 观察用户找到“添加活动”“新建商机”“编辑客户”的时间；
- 统计详情 Sheet 内返回、关闭和重复打开次数；
- 询问用户当前正在查看的对象和层级；
- 对比拆分前后的任务完成时间和错误率。

---

### B2. 关联对象的嵌套 Sheet / Dialog 层级较多

- **优先级**：P1/P2
- **对应原则**：Jakob、Miller、Tesler、Postel
- **用户任务**：从客户进入商机或合同详情，完成操作后返回原上下文。

#### 当前观察

`CustomerDetailSheet.vue` 中，客户详情 Sheet 内可以切换到嵌入式商机或合同详情：

- `CRM-Client/src/views/CustomerDetailSheet.vue:962-993`

随后客户详情还挂载多个表单 Dialog：

- `CRM-Client/src/views/CustomerDetailSheet.vue:1199-1225`
- 后续还包括商机、合同、发票、回款等相关 Dialog。

#### UX 风险

- 关闭当前层级和返回上一层级的含义可能不同；
- 焦点恢复容易回到错误位置；
- 用户可能误以为关闭详情会取消刚刚的业务操作；
- 嵌套滚动和遮罩叠加会增加认知负担。

#### 优化方向

建立统一的“对象上下文栈”模型：

```text
客户
└── 商机
    └── 合同
        └── 回款计划 / 回款记录
```

界面上需要持续显示：

- 当前对象名称；
- 当前对象类型；
- 上一级对象；
- 返回上一级的明确入口；
- 关闭整个工作流的入口。

不要仅依赖多个相似的返回箭头或关闭图标让用户猜测行为。

---

### B3. 列表高级工具的首屏选择成本较高

- **优先级**：P2
- **对应原则**：Hick、Miller、Von Restorff
- **用户任务**：快速找到目标记录，必要时再进行高级筛选、排序和视图配置。

#### 当前观察

DataTable 工具栏可以同时提供：

- 筛选；
- 排序；
- 列配置；
- 保存视图；
- 页面自定义工具。

见：`CRM-Client/src/components/crmwolf/DataTable.vue:733-766`。

这说明能力集中做得很好，但不代表所有能力都应该在首屏以同等权重出现。

#### UX 风险

- 用户可能不知道筛选、排序、列配置和视图之间的区别；
- 当前筛选状态不够显眼时，用户容易误判结果集；
- 高级配置能力可能压过“开始查找”的主任务；
- 移动端如果复用过多桌面工具，决策成本会更高。

#### 优化方向

建议进行渐进披露：

- 默认显示最常用的搜索/筛选和排序；
- 列配置和保存视图放入“更多设置”；
- 显示当前状态摘要，例如“已筛选 3 项”“已隐藏 2 列”；
- 清空筛选时明确是否同时重置分页、排序和视图；
- 保存视图时提供命名、范围和恢复反馈；
- 保留熟练用户的快捷入口，不牺牲高级能力。

## C. 交互一致性和可发现性

### C1. 自定义 modal 与统一 Dialog / Sheet 分叉

- **优先级**：P1
- **对应原则**：Jakob、Fitts、Postel、无障碍规范
- **用户任务**：在任何页面打开、填写、确认和关闭弹窗，并知道焦点和上下文如何变化。

#### 当前观察

系统已有大量 `Dialog`、`AlertDialog` 和 `Sheet`，但客户列表仍有两个临时自定义 modal：

- `CRM-Client/src/views/Customers.vue:979-1029`
- `CRM-Client/src/views/Customers.vue:1170-1190`

#### UX 风险

- 同类行为在不同页面表现不同；
- 自定义 modal 可能缺少焦点陷阱、读屏语义和关闭保护；
- 固定 `min-width: 400px` 不适合窄屏；
- 后续维护容易继续复制临时实现。

#### 优化方向

将弹窗行为收敛到共享组件，优先补齐：

- `Dialog` / `AlertDialog` / `Sheet` 的选型规则；
- 标题、描述、字段和按钮的语义关联；
- Escape、遮罩、关闭按钮和未保存保护；
- 焦点进入与恢复；
- 移动端宽度和高度策略；
- 提交中、错误和成功状态。

---

### C2. 行操作主要隐藏在右键菜单

- **优先级**：P1/P2
- **对应原则**：Jakob、Fitts、Hick、无障碍规范
- **用户任务**：在列表中对某条记录执行查看、编辑、转移、删除或其他操作。

#### 当前观察

DataTable 将桌面行操作设计为右键/键盘上下文菜单，不占用操作列：

- `CRM-Client/src/components/crmwolf/DataTable.vue:428-459`
- `CRM-Client/src/components/crmwolf/DataTable.vue:852-862`

代码同时支持 ContextMenu 键和 `Shift + F10`，键盘基础是积极的。

#### UX 风险

- 普通用户可能不知道右键有更多操作；
- 触控设备没有自然的右键模型；
- 高价值操作被隐藏后，可发现性不足；
- `<tr role="button">` 的读屏语义需要实际验证，不能只依据属性数量判断无障碍质量。

#### 优化方向

采用“主操作可见、次要操作收敛”的混合方案：

- 行点击打开详情；
- 行尾提供更多按钮；
- 右键保留为熟练用户快捷方式；
- 移动端 Card 提供明确的操作入口；
- 删除、转移、退回等高风险操作不只依赖右键菜单；
- 通过 tooltip、首次提示或空状态说明提升可发现性。

---

### C3. 页面级动作、局部动作和对象动作边界不稳定

- **优先级**：P2
- **对应原则**：Jakob、Hick、Von Restorff

当前系统同时存在：

- TopBar 页面动作；
- DataTable 工具栏动作；
- 行级动作；
- 详情 Sheet Footer 动作；
- 卡片内动作；
- 右键菜单动作。

这些层级本身都有合理用途，但需要形成明确规则：

| 动作类型 | 推荐位置 |
|---|---|
| 页面范围动作 | TopBar 或页面主操作区 |
| 列表范围动作 | DataTable 工具栏 |
| 单条记录打开 | 行点击或主链接 |
| 单条记录常用操作 | 行尾更多或卡片操作区 |
| 当前详情 Tab 主操作 | Sheet Footer |
| 关联对象操作 | 关联对象卡片内部 |
| 危险动作 | 对象上下文内，带明确确认 |

如果相同动作在不同页面出现在不同位置，用户会形成错误的空间记忆。

---

### C4. 旧 Token 与 V2 Token 并存

- **优先级**：P2
- **对应原则**：美观即易用效应、Jakob、Von Restorff

当前源码中仍大量使用 `$wolf-*`、`--wolf-*` 和 `variables-v2.scss`。这会造成：

- 同类状态颜色和层级可能不一致；
- 主题、间距、圆角和焦点样式难以统一；
- 设计评审无法稳定判断目标实现；
- 新增页面容易继续复制旧样式模式。

这更像是**设计系统治理问题**，不是简单的视觉问题。建议先建立允许使用的 Token 范围和迁移优先级，再做逐步收敛。

## D. 响应式、可达性和性能

### D1. 固定 viewport 高度与嵌套滚动

- **优先级**：P1
- **对应原则**：Postel、Tesler、Doherty、无障碍规范

#### 当前观察

多个列表页向 DataTable 传入固定高度，例如：

```vue
height="calc(100vh - 121px)"
```

示例：

- `CRM-Client/src/views/Customers.vue:816-837`
- `CRM-Client/src/views/CustomerTracking.vue:576-591`
- `CRM-Client/src/views/Contracts.vue:505-519`

DataTable 内部又有固定卡片和内部滚动：

- `CRM-Client/src/components/crmwolf/DataTable.vue:708-715`
- `CRM-Client/src/components/crmwolf/DataTable.vue:960-976`

#### UX 风险

- 页面滚动、表格滚动、Sheet 滚动、Dialog 滚动可能同时存在；
- 低高度屏幕中工具栏和分页占用比例过高；
- 字体放大后内容可能不可达；
- 手机软键盘或横屏场景可能裁切内容；
- 用户不清楚当前需要滚动哪个容器。

#### 优化方向

不要简单删除固定高度，而是建立场景规则：

- 桌面大屏高密度列表：可以保留固定表格区；
- 低高度桌面：允许内容区自适应；
- 移动端 Card：优先页面自然滚动；
- 详情 Sheet：控制主滚动容器数量；
- 使用 `100dvh` 和 safe area 时同时验证软键盘和字体放大；
- 保证 200% 字体下核心内容仍然可达。

### D2. 字体放大、小屏和软键盘下的内容可达性

- **优先级**：P1
- **对应原则**：Postel、Fitts、Miller

当前系统已经有移动端适配和触控尺寸，但静态 CSS 无法证明以下场景都可用：

- 200% 字体；
- 320px 宽度；
- 手机横屏；
- 虚拟键盘打开；
- 低视力和高对比度；
- 输入错误后返回字段；
- 长错误信息或多行帮助文案。

需要将这些作为关键任务验收条件，而不是只验收默认 viewport 下的截图。

---

### D3. 首次反馈时间和长任务性能缺少系统性度量

- **优先级**：P1/P2
- **对应原则**：Doherty 阈值、峰终定律

代码中已经有不少 loading、processing 和后台任务状态，但静态代码不能证明：

- 用户点击后是否在足够短时间内看到反馈；
- 首次内容出现是否稳定；
- 列表筛选和分页是否有延迟期间的明确状态；
- Agent 首个反馈是否足够快；
- 长任务是否持续更新；
- 网络较慢时是否出现误以为“没有反应”的情况。

建议采集：

- 点击到首次视觉反馈时间；
- 点击到首个业务结果时间；
- 加载完成时间；
- 长任务成功、失败、重试和取消比例；
- 用户在等待期间的重复点击次数。

### D4. 复杂表格行的读屏语义需要实测

- **优先级**：P1/P2
- **对应原则**：Postel、Fitts、无障碍规范

这可能在视觉和键盘上有效，但表格原生语义与按钮语义的组合需要使用真实读屏测试确认：

- 用户是否仍能理解行列关系；
- 当前焦点是否读出客户名称和关键状态；
- Enter/Space 是否触发预期行为；
- 行内按钮是否会重复触发行点击；
- ContextMenu 键是否可发现。

## E. 峰终体验和视觉层级

### E1. 成功反馈较多依赖短时 Toast

- **优先级**：P2
- **对应原则**：峰终定律、Doherty、Postel

Toast 适合表示轻量完成，但对于客户转移、商机推进、审批、回款、AI 更新等任务，仅显示“成功”不一定足够。

建议按任务风险和持续时间决定反馈方式：

- 轻量设置：Toast；
- 当前页面数据改变：Toast + 局部高亮；
- 高风险动作：结果摘要 + 下一步；
- 后台任务：持久状态卡 + 任务详情；
- 部分成功：明确成功和未完成部分；
- 可撤销动作：提供撤销窗口或恢复入口。

客户智能档案刷新已经是较好的模式，可作为其他异步流程的参考：

- `CustomerDetailSheet.vue:441-451`

---

### E2. 页面主操作和异常状态的强调规则需要收敛

- **优先级**：P2/P3
- **对应原则**：Von Restorff、Fitts、美观即易用

当前页面中可能同时出现：

- 页面主按钮；
- 多个 Footer 按钮；
- 状态 Badge；
- 待确认 Badge；
- 错误颜色；
- AI 相关视觉；
- 行内链接和 hover 状态。

需要确保视觉差异真正对应任务优先级：

- 一个页面尽量只有一个主操作；
- 异常、待确认和待审批要突出但不能泛滥；
- 不只用颜色表达状态；
- 危险操作使用清晰文案和确认结构，而不是单纯使用红色。

---

### E3. 空状态、完成收尾和下一步引导需要系统化

- **优先级**：P2/P3
- **对应原则**：峰终定律、Miller、Hick

空状态和成功状态是用户记忆中很重要的结束节点。建议区分：

- 从未创建过数据；
- 当前筛选无结果；
- 没有权限查看；
- 数据仍在加载或后台生成；
- 数据生成失败。

成功后提供下一步时，应与当前任务自然衔接，例如：

- 添加活动成功后，建议设置下一次跟进；
- 新建商机成功后，进入项目旅程；
- 回款登记成功后，查看回款计划；
- AI 整理成功后，查看变更摘要并确认。

不能用庆祝动画或泛化 Toast 掩盖实际结果不清晰的问题。

---

## 6. 关键任务地图

以下任务覆盖 CRMWolf 当前最重要的业务闭环，并能同时暴露信息架构、表单、自动化、权限、异步和高风险操作问题。

### T1. 客户跟进任务

```text
客户列表
  → 筛选 / 搜索客户
  → 打开客户详情
  → 查看客户档案和历史活动
  → 添加客户活动
  → Agent 解析或补充活动信息
  → 用户确认 / 编辑
  → 保存活动
  → 设置下一次跟进
```

- **主要用户**：销售人员
- **核心目标**：快速记录客户互动，并形成可执行的下一步行动。
- **关键原则**：Jakob、Fitts、Postel、Tesler、Doherty、伦理规范
- **主要风险**：
  - 列表行操作不易发现；
  - 详情 Sheet 层级复杂；
  - AI 建议和正式保存边界不清；
  - 活动保存失败后是否可恢复；
  - 后续跟进是否被明确确认。
- **优先级**：P1

### T2. 客户维护任务

```text
客户列表
  → 打开客户详情
  → 进入客户信息
  → 编辑基本信息 / 联系人 / 成员 / 部署 / 发票抬头
  → 提交
  → 处理权限、校验或接口错误
  → 确认最终结果
```

- **主要用户**：销售人员、团队管理员
- **核心目标**：维护客户主数据及相关成员、联系人和部署信息。
- **关键原则**：Miller、Hick、Postel、Fitts
- **主要风险**：
  - “客户信息”承载多个不同任务；
  - Footer 操作过多；
  - 失败后返回上一页丢失上下文；
  - 权限不足和选项加载失败不够可见；
  - 多个 Dialog 之间焦点和关闭关系复杂。
- **优先级**：P1

### T3. 商机推进任务

```text
客户详情
  → 项目旅程
  → 查看商机
  → 推进阶段 / 创建合同 / 提交审批
  → 等待后台处理或审批
  → 成功 / 驳回 / 失败 / 撤回
  → 返回客户上下文
```

- **主要用户**：销售人员、审批人员、销售管理者
- **核心目标**：推动商机从客户关系进入合同和审批流程。
- **关键原则**：Jakob、Tesler、Doherty、峰终定律、伦理规范
- **主要风险**：
  - 客户、商机、合同三个对象层级容易混淆；
  - 后台审批状态与页面状态可能不同步；
  - 提交、撤回、驳回和删除的风险提示不统一；
  - 用户不清楚当前操作完成到了哪一步。
- **优先级**：P1

### T4. 财务执行任务

```text
合同详情
  → 回款计划
  → 登记回款记录
  → 修改 / 删除 / 提交审批
  → 等待审批或后台任务
  → 查看成功、失败、驳回或重试结果
```

- **主要用户**：销售、财务、审批人员
- **核心目标**：准确登记和推进回款，不产生重复或错误记录。
- **关键原则**：Fitts、Postel、峰终定律、Doherty、伦理规范
- **主要风险**：
  - 金额、日期、对象和阶段必须准确；
  - 重复提交可能产生重复业务写入；
  - 删除和修改影响财务事实；
  - 成功 Toast 不能替代最终状态确认；
  - 审批链路的等待、失败、重试和撤回需要持久反馈。
- **优先级**：P1，必要时提升为 P0 验证项

### T5. 移动端快速任务

```text
移动端 BottomNav
  → 客户 / 商机 / 合同
  → Card 列表
  → 打开详情
  → 完成添加活动或查看状态
```

- **主要用户**：外出或移动办公的销售人员
- **核心目标**：在小屏幕和触控环境下完成高频、低步骤任务。
- **关键原则**：Fitts、Hick、Postel、Miller
- **主要风险**：
  - Card 操作入口是否可发现；
  - 表单和 Sheet 是否被软键盘遮挡；
  - 固定高度和内部滚动是否导致内容不可达；
  - 更多菜单是否隐藏了关键能力。
- **优先级**：P1/P2

## 7. 关键任务优先级矩阵

| 排名 | 任务 | 业务价值 | 数据/流程风险 | 当前主要 UX 问题 | 建议优先级 |
|---:|---|---|---|---|---|
| 1 | 客户跟进 + Agent 解析 | 高 | 高 | 自动化边界、确认、失败恢复、下一步 | P1 |
| 2 | 财务执行和回款登记 | 高 | 很高 | 重复提交、金额准确性、审批状态、结果确认 | P1 / P0 验证 |
| 3 | 商机推进到合同审批 | 很高 | 高 | 多对象层级、异步审批、撤回和驳回 | P1 |
| 4 | 客户维护 | 高 | 中高 | 详情信息过载、表单错误恢复、权限反馈 | P1 |
| 5 | 列表查找和筛选 | 高 | 中 | 工具栏选择成本、行操作可发现性 | P1/P2 |
| 6 | 移动端快速查看和跟进 | 中高 | 中 | 小屏、软键盘、滚动和更多菜单 | P1/P2 |
| 7 | 低频设置和视觉精修 | 中 | 低 | Token、视觉层级、空状态和动效 | P2/P3 |

### 7.1 推荐的第一批验证范围

第一批不需要覆盖所有页面，建议先验证 3 条闭环：

1. **客户跟进闭环**：客户列表 → 客户详情 → 添加活动 → Agent 解析 → 确认保存；
2. **商机推进闭环**：客户 → 商机 → 合同 → 审批 → 成功/驳回/撤回；
3. **财务执行闭环**：合同 → 回款计划 → 回款记录 → 审批/失败/重试。

这 3 条闭环能覆盖当前最重要的：

- 列表；
- 详情 Sheet；
- Dialog；
- 表单；
- 权限；
- Agent；
- durable workflow；
- 高风险操作；
- 异常恢复；
- 移动端和无障碍。

## 8. P1 优先改进主题

### P1-1：统一任务状态反馈

建立共享的状态模型和组件契约，优先覆盖：

- 列表请求；
- 详情请求；
- 表单加载；
- 表单保存；
- 后台 Agent 任务；
- 审批；
- 回款；
- 删除、退回、转移。

### P1-2：统一高风险操作和弹窗语义

优先迁移自定义 modal，并对所有高风险动作建立相同的：

- 后果说明；
- 对象确认；
- 提交中；
- 失败恢复；
- 撤销或人工恢复；
- 焦点和键盘行为。

### P1-3：建立 Agent 自动化透明规范

把 Agent 输出从“聊天消息”提升为可审查的业务结果：

- 建议与事实分离；
- 变更摘要；
- 证据和不确定性；
- 人工确认；
- 可编辑；
- 可撤销；
- 后台状态持久化。

### P1-4：降低详情层级和滚动复杂度

先从用户任务而不是代码文件入手：

- 识别客户详情的高频任务；
- 减少同层级动作竞争；
- 建立对象上下文栈；
- 限制嵌套 Sheet/Dialog 的层级；
- 在小屏幕下减少并行滚动容器。

### P1-5：关键任务无障碍和响应式验收

至少纳入：

- 键盘；
- 读屏；
- 200% 字体；
- 320px 宽度；
- 横屏；
- 软键盘；
- reduced motion；
- 低带宽；
- 断网和超时。

## 9. 验证计划

### 9.1 行为指标

| 指标 | 适用任务 | 目标用途 |
|---|---|---|
| 任务完成率 | 所有关键任务 | 判断是否真正可用 |
| 完成时间 | 列表查找、添加活动、回款登记 | 判断效率和认知负担 |
| 首次找到操作时间 | 列表、详情、Agent | 判断可发现性 |
| 误操作率 | 删除、退回、转移、审批 | 判断风险控制 |
| 重复点击次数 | 保存、回款、审批、Agent | 判断反馈是否及时 |
| 放弃率 | 表单、Agent、复杂详情 | 判断摩擦和信息过载 |
| 恢复完成率 | 错误、超时、权限不足 | 判断 Postel 和错误恢复 |
| 返回/关闭次数 | 嵌套 Sheet/Dialog | 判断层级是否迷路 |

### 9.2 异常路径

必须覆盖：

- 输入错误；
- 重复提交；
- 误触；
- 网络中断；
- 服务超时；
- 权限不足；
- 后台任务延迟；
- 自动重试；
- 部分成功；
- 用户取消；
- 未保存退出；
- AI 结果错误；
- 数据被其他用户同时修改。

### 9.3 自动化理解度

对于 Agent 任务，额外测量：

- 用户是否知道 AI 做了什么；
- 用户是否知道哪些内容已经写入；
- 用户是否能找到证据或变更摘要；
- 用户是否能拒绝或编辑建议；
- 用户是否知道任务失败或仍在后台运行；
- 用户是否能在不依赖 AI 的情况下完成人工接管。

### 9.4 无障碍验收

- Tab 顺序；
- Enter / Space 行操作；
- ContextMenu 键和 `Shift + F10`；
- Dialog 焦点进入和恢复；
- Escape 和遮罩关闭；
- label 与控件关联；
- 错误与控件关联；
- 不依赖颜色表达状态；
- 200% 字体；
- 320px 宽度；
- reduced motion；
- 读屏下对象和状态是否可理解。

## 10. 暂不建议优先做的事情

在 P1 问题解决之前，不建议优先投入以下工作：

- 全量重做颜色、圆角和阴影；
- 为所有页面增加复杂动效；
- 将所有高级列表能力删除；
- 单纯把右键菜单全部改成操作列；
- 机械替换所有 `$wolf-*` Token 而不验证页面行为；
- 仅通过增加 Toast 数量来解决状态问题；
- 仅通过拆分 Vue 文件来解决详情页复杂度。

这些工作可能改善表面一致性，但不一定解决关键任务中的数据风险、恢复成本和认知负荷。

## 11. 后续产出建议

建议下一步按以下顺序继续：

1. 为 T1/T3/T4 三条关键任务补充真实界面流程图；
2. 为每条流程列出 happy path、异常路径、恢复路径和退出路径；
3. 建立 P1 问题的可用性测试脚本；
4. 将问题拆成 GitHub Issues 或实施 tickets；
5. 先改共享状态、Dialog、Agent 结果展示和详情层级规则；
6. 逐页面迁移并用任务指标验证；
7. 最后再处理视觉精修、Token 收敛和动效增强。
