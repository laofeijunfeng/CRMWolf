# CRMWolf UX 改造需求文档

- **文档状态**：需求初稿，基于静态 UX 分析，待真实用户测试和异常路径验证
- **分析日期**：2026-09-02
- **目标位置**：飞书知识库「产品需求」节点下
- **关联分析**：CRMWolf UX 问题地图 + 关键任务优先级
- **适用系统**：CRMWolf Web 端及移动端关键业务流程

> 本文档将现有 UX 问题地图转化为可执行的需求范围、优先级、验收标准和实施顺序。当前尚未通过静态分析确认明确 P0，但财务执行、回款登记、审批等流程存在需要优先验证的 P0 风险项。本文不等同于最终交互稿或技术方案。

## 1. 背景与问题定义

CRMWolf 已具备统一导航、DataTable、详情 Sheet、移动端导航、Agent 状态和无障碍建设基础，但当前体验问题主要表现为跨页面规则不一致，以及复杂任务中的状态、层级和恢复路径没有完全收束：

- 相同的加载、保存、错误、成功和后台处理中状态，在不同页面的表达方式不同；
- 删除、退回公海、标记输单、转移、审批、回款等高风险操作的确认、提交中、失败恢复和撤销语义不统一；
- 客户详情同时承载档案、活动、联系人、部署、发票抬头、商机和合同等多类任务，信息层级与对象边界不够清晰；
- Sheet、Dialog、自定义 modal、右键菜单、移动端 Card 等交互模型并存，用户不一定能发现或理解操作入口；
- 固定高度、嵌套滚动、小屏幕、字体放大和软键盘等场景仍需以关键任务为单位验证；
- AI / Agent 已具备技术状态展示，但建议、草稿、正式写入、后台任务、失败和人工接管之间的业务边界需要统一。

## 2. 需求目标

### 2.1 总体目标

让用户在客户跟进、客户维护、商机推进和财务执行等关键任务中，能够：

1. 快速理解当前所在对象、任务阶段和可执行动作；
2. 明确知道操作是否已提交、是否生效、是否仍在后台处理；
3. 在错误、超时、权限不足和部分成功时保留上下文并完成恢复；
4. 在高风险业务操作前理解对象、后果和影响范围，避免误操作和重复写入；
5. 在桌面端、移动端、键盘和读屏场景下完成核心任务；
6. 对 AI 产出知道“它做了什么、依据是什么、哪些内容已写入、如何修改或撤销”。

### 2.2 非目标

本阶段不以全量视觉重做为目标，也不先做大范围动效、颜色和圆角调整。AI / Agent 自动化作为独立专题纳入整体规划，但不应阻塞非 AI 的 P1 基础体验改造。

## 3. UX 原则依据

本需求依据飞书文档《UX 规范：基于〈Laws of UX〉的设计原则》及其子文档，重点采用以下原则：

- **Jakob 定律**：让交互位置和行为符合用户已有经验，减少跨页面学习成本；
- **Fitts 定律**：让高频、关键和危险操作具备合适的尺寸、距离和可发现性；
- **Hick 定律与 Miller 定律**：控制首屏选择数量，降低详情页和工具栏的认知负担；
- **Tesler 定律**：不要把复杂度直接转嫁给用户，应由系统承担状态、层级和恢复复杂度；
- **Postel 定律**：容忍输入和环境差异，并提供明确、可恢复的错误路径；
- **Doherty 阈值与峰终定律**：及时反馈，尤其要改善长任务、失败和任务完成后的最终体验；
- **伦理与无障碍规范**：不让用户误把推断当事实，不以颜色作为唯一状态表达，并保证键盘、读屏和放大场景可用。

## 4. 关键任务与优先级

| 排名 | 关键任务 | 业务价值 | 风险 | 本阶段优先级 |
|---:|---|---|---|---|
| 1 | 客户跟进：查看客户 → 添加活动 → 解析/补充 → 确认保存 → 设置下一步 | 高 | 高 | P1 |
| 2 | 财务执行：合同 → 回款计划 → 登记回款 → 审批/失败/重试 | 高 | 很高 | P1，含 P0 验证 |
| 3 | 商机推进：客户 → 商机 → 合同 → 审批 → 成功/驳回/撤回 | 很高 | 高 | P1 |
| 4 | 客户维护：编辑客户、联系人、成员、部署、发票抬头 | 高 | 中高 | P1 |
| 5 | 列表查找：搜索、筛选、排序、查看、行操作 | 高 | 中 | P1/P2 |
| 6 | 移动端快速查看和跟进 | 中高 | 中 | P1/P2 |

## 5. P1 需求范围

### UX-P1-01：建立统一任务状态反馈协议

**用户问题**：用户无法稳定判断当前数据是否正在加载、是否为空、是否保存成功、是否失败或是否仍在后台处理；失败后常需要刷新、返回或重新输入。

**需求**：为列表、详情、表单、审批、回款和后台任务统一定义并复用以下状态：加载中、空数据、筛选无结果、权限不足、保存中、成功、失败、可重试、部分成功、后台处理中、已取消。

**最低要求**：

- 状态文案说明“正在处理什么”，而不是只显示通用 loading；
- 保存中禁止重复提交，但保留用户上下文和已填写内容；
- 失败时保留输入，提供直接重试或人工继续入口；
- 权限不足说明影响范围和可替代动作；
- 后台任务离开当前页面后仍有可追踪的持久状态；
- 成功反馈至少说明对象和最终状态，不能只依赖短时 Toast。

**验收标准**：在断网、超时、500、权限不足、重复点击和部分成功场景下，用户无需刷新页面即可知道结果并继续或恢复任务。

### UX-P1-02：统一高风险操作确认、提交和恢复模型

**覆盖操作**：删除、退回公海、标记输单、转移、撤回、驳回、冲红、修改或删除回款记录、提交审批等。

**用户问题**：不同页面使用不同 modal 和确认方式，用户可能误触关闭、重复提交，或不清楚操作后果和最终结果。

**需求**：所有高风险操作使用统一的 Dialog / AlertDialog / Sheet 选型和状态模型，替换临时自定义 modal。

**最低要求**：

- 确认前显示对象名称、当前状态、操作后状态、影响范围和不可逆后果；
- 对需要理由的操作，理由字段有明确 label、校验和错误关联；
- 提交中禁用重复提交并显示进行中状态；
- 关闭时若存在未保存输入，明确询问是否放弃；
- 失败时保留原因和输入，支持重试或人工恢复；
- 成功后展示最终结果、下一步和可用的撤销/恢复路径；
- 支持 Escape、键盘焦点进入与恢复、合理的遮罩关闭策略和移动端窄屏布局；
- 删除、退回和财务事实修改不得仅依赖右键菜单触发。

**验收标准**：用户能复述操作后果；键盘和读屏用户能完整完成确认和取消；不会因遮罩点击或重复点击造成意外业务写入。

### UX-P1-03：收敛弹窗、详情层级和对象上下文

**用户问题**：客户详情 Sheet 同时承载多个对象和多个管理任务，嵌套 Sheet / Dialog 后用户容易迷失，不清楚关闭、返回和取消的区别。

**需求**：建立统一的对象上下文栈和层级规则：

```text
客户 → 商机 → 合同 → 回款计划 / 回款记录
```

页面必须持续表达当前对象、对象类型、上一级对象、返回上一级入口和关闭整个工作流入口。

**最低要求**：

- 客户档案、客户活动、客户信息、项目旅程等一级任务有清晰职责边界；
- 关联对象详情优先复用同一上下文，而非无限叠加模态层；
- 页面级动作、列表级动作、行级动作和对象级动作位置保持一致；
- 控制并行滚动容器数量，避免页面、表格、Sheet、Dialog 同时滚动；
- 返回上一级不等同于取消当前已提交操作；
- 焦点在打开、返回和关闭后恢复到合理位置。

**验收标准**：用户在客户 → 商机 → 合同 → 回款流程中，能够随时说出当前对象和返回位置；移动端不出现无法关闭、无法回到上一级或滚动容器互相遮挡的情况。

### UX-P1-04：提升错误恢复、权限反馈和表单可恢复性

**用户问题**：部分页面在详情加载或选项加载失败时直接返回或只记录日志，导致用户失去上下文，不知道如何继续。

**需求**：错误应在当前任务上下文中被解释和处理，不以静默日志、自动返回或通用 Toast 作为唯一反馈。

**最低要求**：

- 详情加载失败提供重试、返回和联系权限管理员等动作；
- 选项加载失败明确指出受影响字段，并提供重试；
- 字段校验错误关联到字段，提交后聚焦首个错误；
- 保存失败保留用户输入，区分校验失败、权限失败、网络失败和服务失败；
- 并发修改时提示数据可能已变化，并给出刷新、合并或重新编辑路径；
- 空状态区分“没有数据”“筛选无结果”“尚未创建”和“无权查看”。

**验收标准**：典型异常下任务恢复完成率可测，用户不需要凭记忆重新填写已经输入的内容。

### UX-P1-05：关键任务的响应式和无障碍验收

**用户问题**：默认桌面 viewport 之外，固定高度、嵌套滚动、软键盘和字体放大可能造成内容不可达；复杂表格行语义需要实测而非仅看属性。

**需求**：将下列环境纳入三条第一批关键任务的验收：键盘、读屏、200% 字体、320px 宽度、手机横屏、软键盘打开、低带宽、断网和 reduced motion。

**最低要求**：

- 核心操作在 320px 宽度和 200% 字体下仍可访问；
- 表单、Dialog、Sheet 打开软键盘后，当前字段和提交按钮可滚动到；
- 不依赖颜色单独表达成功、失败、审批和风险状态；
- Dialog 有正确标题、描述、焦点进入、焦点恢复和 Escape 行为；
- 表格行、行内按钮和右键/键盘菜单的读屏语义不冲突；
- 移动端优先自然页面滚动，避免无解释的固定 viewport 高度；
- 加载、保存和后台处理有可被辅助技术感知的状态。

**验收标准**：键盘和至少一种主流桌面读屏完成客户跟进、商机审批和回款登记的核心路径；异常状态同样可理解和恢复。

### UX-P1-06：AI / Agent 自动化透明与人工接管（独立专题）

**范围说明**：该项纳入整体需求文档，但作为独立专题推进，不阻塞非 AI 的 P1 基础体验收敛。

**用户问题**：用户不一定能区分建议、草稿、已保存数据和后台处理中结果，也不一定知道 AI 修改了什么、依据是什么以及失败后如何人工完成。

**需求**：所有 Agent 业务输出使用统一结果模型，并明确以下字段：

- 动作类型：建议、草稿、已确认写入、后台任务；
- 影响对象：客户、活动、商机、合同、回款等；
- 变更摘要：新增、修改、未处理字段；
- 来源与不确定性：用户输入、历史数据、系统规则或模型推断；
- 用户动作：确认、编辑、拒绝、重试、取消、撤销；
- 最终状态：未写入、已保存、部分保存、失败、等待人工。

**验收标准**：用户能区分建议和事实，找到变更摘要和依据，拒绝或编辑 AI 结果，并在 AI 失败时不依赖 AI 完成同一业务任务。

## 6. P2 需求范围

### UX-P2-01：列表工具渐进披露与状态摘要

默认突出搜索、常用筛选和排序；列配置、保存视图等高级能力放入“更多设置”。明确显示已启用的筛选、排序、隐藏列和视图范围，并在清空时说明会重置哪些条件。

### UX-P2-02：提升行操作可发现性

行点击用于打开详情；行尾或 Card 操作区提供明确的更多按钮；右键和 `Shift + F10` 保留为熟练用户快捷方式。高风险操作不能只藏在右键菜单中。

### UX-P2-03：统一页面动作层级和完成后的下一步

建立 TopBar、列表工具栏、行操作、详情 Footer、关联对象卡片的动作放置规则。对于保存活动、推进阶段、登记回款等任务，成功后明确下一步，例如查看详情、继续审批、设置下次跟进或返回原上下文。

### UX-P2-04：设计 Token 和组件迁移治理

建立允许使用的 Token 范围、旧 Token 禁止新增规则和迁移优先级。迁移以共享组件和关键页面为单位，同时验证状态颜色、间距、焦点和主题行为，避免只做机械替换。

### UX-P2-05：长任务和首个反馈性能度量

采集点击到首次反馈、点击到首个结果、加载完成、长任务成功/失败/重试/取消、重复点击次数等指标，优先覆盖列表筛选、保存活动、审批和回款登记。

## 7. P3 需求范围

P3 事项在 P1/P2 稳定后推进：

- 空状态、成功收尾和下一步引导的统一文案与视觉表现；
- 页面主操作、异常状态和风险状态的视觉层级精修；
- 动效、峰终体验和 reduced motion 下的替代表现；
- 低频页面的视觉一致性和细节打磨。

## 8. 第一阶段实施顺序

### 阶段一：先建立共享规则和验证基线

1. 定义任务状态协议和错误分类；
2. 定义 Dialog / AlertDialog / Sheet 选型、焦点和关闭规则；
3. 建立高风险操作清单和回滚/人工恢复策略；
4. 为客户跟进、商机推进、财务执行建立 happy path、异常路径和恢复路径测试脚本；
5. 建立键盘、读屏、320px、200% 字体和软键盘验收基线。

### 阶段二：优先改三条关键闭环

1. **客户跟进闭环**：客户列表 → 客户详情 → 添加活动 → Agent 解析 → 确认保存 → 设置下一次跟进；
2. **商机推进闭环**：客户 → 商机 → 合同 → 审批 → 成功/驳回/撤回；
3. **财务执行闭环**：合同 → 回款计划 → 回款记录 → 审批/失败/重试。

### 阶段三：扩展到客户维护、列表和移动端

在共享规则稳定后，处理客户信息多任务拆分、列表渐进披露、行操作可发现性、移动端自然滚动和 Token 收敛。

### 阶段四：视觉和愉悦度优化

最后再投入全局视觉精修、空状态、动效、成功收尾和低频页面一致性。

## 9. 验收指标与测试

### 9.1 行为指标

| 指标 | 目标 |
|---|---|
| 关键任务完成率 | 客户跟进、商机审批、回款登记可稳定完成 |
| 异常恢复完成率 | 断网、超时、权限不足、服务失败后可继续任务 |
| 重复点击次数 | 保存、审批、回款和 Agent 提交过程显著降低 |
| 误操作率 | 删除、退回、转移、输单和财务修改可控 |
| 首次找到操作时间 | 列表行操作、详情主操作和下一步入口更容易发现 |
| 放弃率 | 表单、详情 Sheet 和 Agent 任务因层级或错误放弃的比例降低 |
| 返回/关闭次数 | 复杂对象链路中无目的返回和反复关闭减少 |

### 9.2 异常路径清单

必须覆盖输入错误、重复提交、遮罩误触、网络中断、服务超时、权限不足、后台延迟、部分成功、用户取消、未保存退出、并发修改和 AI 结果错误。

### 9.3 发布门禁

- 财务登记、审批提交和高风险操作未验证重复写入风险前，不得宣称 P0 风险已排除；
- 新增页面不得继续引入临时自定义 modal 和新的旧 Token 用法；
- 关键任务的错误、权限、保存中和成功状态必须可见、可恢复、可被辅助技术理解；
- AI 结果未明确建议/草稿/正式写入边界时，不得默认静默修改正式 CRM 数据。

## 10. 依赖、风险与待确认问题

### 10.1 依赖

- 统一 Dialog、Sheet、DataTable、表单状态和通知组件；
- 后台任务、审批和回款接口提供可查询的最终状态及幂等语义；
- 设计系统提供状态、焦点、间距、响应式和无障碍规范；
- 产品和业务负责人确认各类高风险操作的撤销、恢复或人工处理路径。

### 10.2 待确认问题

1. 删除、退回、输单、转移、冲红和回款修改中，哪些操作可撤销，哪些只能人工恢复？
2. 回款登记和审批接口是否具备幂等键、重复提交保护和最终状态查询？
3. 客户详情中的客户信息是否需要按角色拆分为维护任务，而不是继续作为一个大 Tab？
4. Agent 生成内容在什么情况下可自动写入，什么情况下必须人工确认？
5. 是否需要统一的后台任务中心，让用户跨页面查看审批、Agent 和同步任务？
6. 第一批可用性测试的真实用户角色、设备和业务数据集如何确定？
