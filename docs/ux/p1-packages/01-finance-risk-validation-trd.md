# P1-PKG-01 财务与高风险操作风险验证 TRD

- **文档类型**：Technical Requirements Document（技术需求文档）
- **所属改造包**：P1-PKG-01 财务与高风险操作风险验证
- **适用系统**：CRMWolf 回款计划、回款记录、通用审批中心
- **排除范围**：Agent / AI 自动化；通知渠道本身的体验改造；财务核算系统对接
- **编写基线**：基于当前仓库静态代码核查，最终上线前需以联调和测试环境实测结果为准
- **日期**：2026-09-02

## 1. 技术目标

本改造包不直接改变回款业务规则，而是为高风险写操作建立可验证、可恢复的技术契约。用户在登记回款、提交审批、修改、删除、审批、驳回或撤回时，系统必须能够明确回答三个问题：这次操作是否已经生效、当前业务状态是什么、如果没有生效下一步应该怎么做。

本期目标是把“点击后等待结果”的交互，收敛为“有操作身份、有确定状态、有冲突处理、有恢复路径”的闭环。凡是无法确认最终状态的请求，不允许让前端以“失败”引导用户盲目重试；凡是可能造成金额重复累计、审批实例重复创建或状态错乱的路径，必须在上线前阻断。

## 2. 当前业务与技术基线

### 2.1 业务对象关系

回款业务以“合同 → 回款计划 → 回款记录”为主链路：

- **回款计划（PaymentPlan）**：归属合同，包含阶段名称、计划金额、到期日和计划状态；一个计划可以有多条回款记录。
- **回款记录（PaymentRecord）**：归属回款计划，包含实际回款金额、付款方、回款日期、凭证、提成协作成员和登记人；回款记录必须经过审批。
- **审批实例（Approval）**：通过 `business_type=PAYMENT + business_id=PaymentRecord.id` 关联回款记录；审批实例下有审批节点和审批操作记录。
- **合同回款汇总**：由已审批通过的回款记录金额汇总得到，并反映到计划状态及合同回款状态。

当前模型的关键金额语义是：回款计划 `paid_amount` 只统计 `approval_phase=approved` 的回款记录，`remaining_amount=planned_amount-paid_amount`。因此，登记一笔回款并不等于已入账；只有审批最终通过后，该金额才应进入已回款统计。

### 2.2 当前状态字段

| 对象 | 字段 | 当前取值 | 技术语义 |
|---|---|---|---|
| 回款计划 | `status` | `PENDING` / `OVERDUE` / `PARTIAL` / `COMPLETED` | 根据已审批通过金额及到期日计算的业务状态 |
| 回款记录 | `approval_phase` | `draft` / `pending_review` / `approved` / `rejected` | 回款记录审批生命周期 |
| 回款记录 | `confirmation_status` | `PENDING` / `CONFIRMED` / `DISPUTED` | 回款确认/入账语义；审批通过后自动置为 `CONFIRMED` |
| 审批实例 | `status` | `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED` | 通用审批引擎状态 |
| 合同 | `payment_status` | `UNPAID` / `PARTIAL` / `COMPLETED` / `OVERDUE` | 合同层回款汇总状态 |

这些字段不能由前端相互推断。服务端响应必须提供足够信息，前端只负责展示服务端给出的当前状态及允许动作。

### 2.3 当前主要接口

| 业务动作 | 当前接口 | 当前实现要点 | 本 TRD 关注点 |
|---|---|---|---|
| 创建回款计划 | `POST /v1/payments/contracts/{contract_id}/payment-plans` | 支持批量创建；总计划金额不得超过合同总额 | 重复提交、批量部分成功、事务边界 |
| 修改/删除回款计划 | `PUT/DELETE /v1/payments/payment-plans/{plan_id}` | 已完成计划不可改；有记录时限制修改/删除 | 并发修改、不可恢复删除、错误码 |
| 登记回款 | `POST /v1/payments/payment-plans/{plan_id}/records` | 校验累计登记金额不超过计划金额；登记后进入审批链路 | 金额并发超额、重复写入、超时查询 |
| 修改回款记录 | `PUT /v1/payments/payment-records/{record_id}` | 仅创建人或全局编辑权限；审批中不可改；草稿/驳回可改 | 版本冲突、审批状态竞态 |
| 删除回款记录 | `DELETE /v1/payments/payment-records/{record_id}` | 通过审批删除保护；已确认记录不可删除 | 删除前状态确认、补偿与审计 |
| 提交回款审批 | `POST /v1/payments/records/{record_id}/submit-approval` | 按金额匹配 PAYMENT 审批流并创建审批实例 | 重复提交可能重复建实例，需幂等 |
| 通用提交审批 | `POST /v1/approvals/{entity_type}/{entity_id}/submit` | 通过 `ApprovalTransactionManager` 处理草稿、驳回重提和状态切换 | 与业务语义端点统一，避免双入口分叉 |
| 审批通过/驳回 | `POST /v1/approvals/{entity_type}/{entity_id}/approve` | 由审批引擎和 PaymentRecordAdapter 回写记录状态 | 乐观锁、终态查询、重复审批 |
| 撤回审批 | `POST /v1/approvals/{entity_type}/{entity_id}/cancel` | 仅提交人可撤回 PENDING 审批 | 并发审批与撤回竞态 |
| 查询回款记录 | `GET /v1/payments/payment-records` | 支持分页、状态、审批状态和待我审批数量 | 作为最终状态查询入口，响应一致性 |
| 查询审批详情 | `GET /v1/approvals/{entity_type}/{entity_id}/detail` | 返回审批节点、操作记录和更新时间 | 超时恢复、操作前后状态确认 |

## 3. 状态机与不变量

### 3.1 回款记录审批状态机

```text
draft --提交审批--> pending_review
pending_review --最后节点通过--> approved
pending_review --任一节点驳回--> rejected
pending_review --提交人撤回--> draft
rejected --修改后重新提交--> pending_review
approved --禁止普通修改/删除--> approved
```

状态约束：

1. 创建回款记录后默认为 `approval_phase=draft`，`confirmation_status=PENDING`；若系统当前创建流程自动提交审批，则必须在同一响应中返回审批实例及当前状态。
2. 提交审批成功后，回款记录必须有且仅有一个当前有效审批实例，审批实例状态为 `PENDING`，回款记录状态为 `pending_review`。
3. 最后审批节点通过后，审批实例为 `APPROVED`，回款记录为 `approved`，并由 `PaymentRecordAdapter.on_approved` 将 `confirmation_status` 置为 `CONFIRMED`、写入确认时间并刷新计划及合同状态。
4. 驳回后，审批实例为 `REJECTED`，回款记录为 `rejected`，金额不计入 `paid_amount`；登记人修改后只能重新提交，不能复用已终结审批实例。
5. 撤回后，审批实例为 `CANCELLED`，回款记录回到 `draft`；撤回不产生已回款金额，重新提交必须创建新的审批实例或由服务端明确记录重提版本。
6. 已 `approved` 或已 `CONFIRMED` 的回款记录不允许通过普通编辑/删除接口改变金额、日期或凭证；如确需冲正，必须另行设计受控的冲正/红冲流程，不在本包直接放开。

### 3.2 回款计划与合同汇总不变量

以下不变量必须在数据库事务提交后始终成立：

- `sum(同计划下 approval_phase=approved 的 actual_amount) <= planned_amount`。
- `paid_amount` 等于上述审批通过记录金额之和，不包含草稿、审批中、驳回、撤回记录。
- `remaining_amount = planned_amount - paid_amount`；禁止出现因并发或异步刷新导致的负数，超额场景必须在事务内拒绝。
- 计划状态映射：`paid_amount >= planned_amount → COMPLETED`；`0 < paid_amount < planned_amount → PARTIAL`；`paid_amount=0 且 due_date < 当前业务日期 → OVERDUE`；否则为 `PENDING`。
- 合同 `payment_status` 必须基于同一批最新计划/记录结果刷新；刷新失败不能静默覆盖主交易结果，必须记录可追踪异常并提供补偿入口。
- 通知、客户业务对象刷新等提交后的副作用不能改变主交易的成功/失败结论，也不能重复创建主业务记录。

### 3.3 审批实例唯一性

对于同一团队、同一业务类型和同一回款记录：

- `PENDING` 状态最多存在一个有效审批实例。
- `APPROVED` 的记录不可再次提交审批。
- `REJECTED` 或 `CANCELLED` 的记录重新提交时，应创建新的审批实例并保留旧实例历史；或者引入“审批轮次”字段明确区分，不得覆盖旧实例导致历史不可追溯。
- 任何提交请求在服务端完成“查询已有有效审批实例 → 决定返回已有实例或创建新实例”的原子判定，不能只依赖前端按钮禁用。

## 4. 高风险操作技术要求

### 4.1 幂等键与请求语义

所有会创建或推进业务状态的写接口必须接受请求幂等键，建议统一使用请求头 `Idempotency-Key`。幂等键作用域为 `team_id + operator_id + operation + resource_type + resource_id + key`，服务端保存请求摘要、处理状态、响应摘要及过期时间。

建议覆盖以下动作：

| 操作 | 幂等要求 | 重复请求处理 |
|---|---|---|
| 创建回款计划（含批量） | 必须 | 相同 key 且请求摘要一致，返回原创建结果；摘要不一致返回 409 |
| 登记回款 | 必须 | 返回原 `record_id/record_number`，不得新增第二条记录 |
| 提交审批 | 必须且需业务唯一性兜底 | 返回当前有效审批实例；不得重复创建 PENDING 实例 |
| 审批通过/驳回 | 必须结合审批版本 | 同版本重复请求返回当前终态；过期版本返回 409 |
| 撤回审批 | 必须结合审批版本 | 已撤回返回当前状态；已被他人终结返回 409 |
| 修改/删除 | 建议必须 | 相同 key 重放不重复执行；资源版本过期返回 409 |

幂等记录推荐独立表 `crm_idempotency_records`，至少包含：`idempotency_key`、`team_id`、`operator_id`、`operation`、`resource_type`、`resource_id`、`request_hash`、`status`（PROCESSING/SUCCEEDED/FAILED）、`response_code`、`response_body`、`created_time`、`expires_time`。对 `(team_id, operator_id, operation, idempotency_key)` 建唯一索引。

注意：幂等键只能防止同一请求重放，不能替代业务唯一约束。登记回款还必须通过金额锁或数据库事务约束防止两个不同请求并发超额；审批提交还必须通过有效审批实例唯一性防止两个不同 key 重复建审批。

### 4.2 版本与并发控制

当前审批实例已有 `updated_time`，审批操作已经具备乐观锁冲突返回 409 的基础。建议统一扩展为：

- 回款记录和回款计划增加 `version` 整数列，初始值为 1，每次成功修改或状态变更递增。
- 更新、删除、提交审批请求携带 `expected_version`；服务端使用 `WHERE id=? AND version=?` 原子更新。
- 审批动作携带 `expected_updated_time` 或改为 `expected_version`，不要同时维护两套语义。
- 冲突响应固定返回 `409 RESOURCE_VERSION_CONFLICT`，包含 `resource_id`、`expected_version`、`current_version`、`current_status` 和 `latest_updated_time`，前端据此刷新，而不是继续重试原写请求。

登记回款金额校验必须在事务内执行。推荐对回款计划行执行 `SELECT ... FOR UPDATE`（或数据库等价锁），重新查询已登记金额后再判断本次金额；不能使用请求进入时前端看到的剩余金额作为最终依据。

### 4.3 事务边界

**登记回款**的主事务至少包括：校验计划、锁定计划、生成唯一记录编号、创建回款记录、创建/准备审批关联、更新必要的审批阶段字段、写操作审计。事务提交后再发送通知和刷新非主链路对象。

**审批提交**的主事务至少包括：读取并锁定回款记录、确认当前状态可提交、匹配审批流程、创建审批实例和首条 `SUBMIT` 记录、更新回款记录 `approval_phase`、写审计。不得出现“审批实例已提交但回款记录仍是草稿”或反向状态。

**审批通过/驳回/撤回**的主事务至少包括：锁定审批实例和业务记录、校验状态/版本/权限、写审批操作记录、推进审批实例状态、通过 PaymentRecordAdapter 更新回款记录、重算计划与合同状态、写审计。通知失败、客户智能刷新失败只作为提交后的副作用处理。

数据库提交后副作用应具备可重试记录。当前系统已有“通知失败不阻断主流程”和手动补发思路，本 TRD 要求将该语义扩展到所有提交后任务：主交易成功后，即使通知失败，查询接口仍应返回主交易成功状态，并能通过日志或运维入口定位补发。

### 4.4 超时后的最终状态查询

任何写请求出现客户端超时、连接断开或 5xx 时，前端不得直接提示“操作失败并重新执行”。统一恢复顺序：

1. 保留本次 `Idempotency-Key`、资源 ID和请求时间；
2. 以指数退避查询资源详情；
3. 回款记录查询 `GET /v1/payments/payment-records/{record_id}`（若当前不存在，则查询所属计划记录列表）；
4. 审批操作查询 `GET /v1/approvals/PAYMENT/{record_id}/detail`；
5. 以服务端返回的 `approval_phase`、`confirmation_status`、审批 `status` 和 `updated_time` 判定最终结果；
6. 只有明确确认“未创建/未生效”后，才允许用户使用同一幂等键重新提交；无法确认时显示“正在确认结果”，并提供刷新/继续查询，不自动生成第二次操作。

如现有路由缺少单条回款记录详情接口，应补充 `GET /v1/payments/payment-records/{record_id}`，响应与列表项保持同一状态语义，并返回 `record_number`、`version`、`approval_id`、`approval_phase`、`confirmation_status`、所属计划金额汇总和 `updated_time`。

## 5. API 契约调整

### 5.1 统一成功响应

高风险写接口建议统一返回：

```json
{
  "operation_id": "op_01...",
  "resource_type": "PAYMENT_RECORD",
  "resource_id": 12345,
  "resource_number": "PAY202609020001",
  "status": "PENDING_REVIEW",
  "approval_id": 67890,
  "idempotency_key": "...",
  "version": 2,
  "accepted_at": "2026-09-02T15:00:00+08:00",
  "message": "回款已登记，等待审批"
}
```

具体字段可按接口裁剪，但必须有资源定位、当前状态、版本/更新时间和可查询标识。成功 Toast 不再作为唯一反馈依据。

### 5.2 统一错误码

| HTTP | 错误码 | 使用场景 | 前端处理 |
|---|---|---|---|
| 400 | `PAYMENT_AMOUNT_EXCEEDS_PLAN` | 金额超过计划剩余金额 | 保留表单，提示最新剩余金额 |
| 400 | `APPROVAL_FLOW_NOT_FOUND` | 未匹配审批流程 | 不重试写入，提示联系管理员配置 |
| 403 | `PAYMENT_OPERATION_FORBIDDEN` | 无查看/编辑/提交/审批权限 | 不重试，展示权限说明 |
| 404 | `RESOURCE_NOT_FOUND` | 记录、计划或审批不存在 | 刷新上下文，避免继续操作 |
| 409 | `RESOURCE_VERSION_CONFLICT` | 资源已被修改或审批已被处理 | 拉取最新状态并锁定旧操作 |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 同 key 对应请求摘要不同 | 要求生成新 key，不执行当前请求 |
| 409 | `ACTIVE_APPROVAL_EXISTS` | 已存在有效 PENDING 审批 | 返回已有审批实例及详情 |
| 409 | `RESOURCE_STATE_NOT_ALLOWED` | 已通过/已确认等终态不可操作 | 展示当前状态和允许动作 |
| 500/503 | `OPERATION_STATUS_UNKNOWN` | 服务端无法安全返回最终结果 | 进入结果查询，不盲目重试 |

现有接口中的中文 `detail` 可以继续保留用于用户提示，但前端逻辑必须依赖稳定的 `error_code`，不能根据中文文案或 HTTP 400 的字符串匹配分支。

### 5.3 两套提交入口收敛

当前同时存在业务语义端点 `POST /v1/payments/records/{record_id}/submit-approval` 和通用入口 `POST /v1/approvals/PAYMENT/{record_id}/submit`。两者必须共享同一服务层，不允许一个入口直接调用 `create_approval_generic`、另一个入口调用 `ApprovalTransactionManager` 而产生不同的幂等、重提或状态语义。

建议保留业务语义端点作为前端稳定入口，但内部统一委托审批事务服务；通用端点仅作为审批中心/跨业务复用入口。两者返回同一响应结构、使用同一错误码和同一幂等校验。完成迁移后再评估是否将业务语义端点标记为兼容入口。

## 6. 前端状态与交互契约

前端 `PaymentRecords.vue`、`PaymentRecordDetailSheet.vue` 和 `ApprovalProcessGeneric.vue` 必须使用服务端状态矩阵驱动操作按钮：

- `draft`：允许登记人编辑、删除、提交审批；提交中禁用按钮并显示“正在提交”。
- `pending_review` / 审批 `PENDING`：只允许查看审批详情；登记人不能编辑或删除；审批人仅显示当前节点动作。
- `rejected`：显示驳回原因、允许登记人编辑并重新提交；重新提交前必须刷新记录版本。
- `approved` + `CONFIRMED`：只读；如需更正，入口指向受控冲正流程，不提供普通删除。
- `cancelled` / 回到 `draft`：显示“已撤回”，允许修改后重新提交。
- 状态查询中：保留用户上下文，显示“正在确认结果”，禁止再次创建同类操作。

前端提交按钮需要具备：一次点击锁定、请求超时转查询、409 转刷新、重复响应复用、刷新后状态恢复。详情 Sheet 要显示记录编号、计划/合同/客户上下文、金额与剩余金额、审批实例、当前节点、最近更新时间和允许动作原因。

## 7. 审计与可观测性

每次高风险操作至少记录以下信息：

- `operation_id`、幂等键摘要、团队 ID、操作人 ID/姓名；
- 资源类型、资源 ID/编号、合同 ID、计划 ID；
- 操作类型、操作前状态、操作后状态、前后版本；
- 金额、计划金额、操作时剩余金额；
- 审批实例 ID、审批轮次、节点和审批动作；
- 请求时间、提交时间、完成时间、耗时；
- 结果：成功、业务拒绝、版本冲突、未知、通知失败；
- 关联错误码和异常摘要；
- 提交后副作用状态（通知、汇总刷新、客户业务对象刷新）。

必须能够按 `record_id`、`record_number`、`approval_id`、`operation_id` 和 `idempotency_key` 追溯一条完整链路。日志不得记录凭证文件内容、access token 或不必要的敏感信息。

建议监控以下指标：回款登记重复请求命中率、审批重复提交拦截数、未知结果数、409 冲突数、金额超额拒绝数、通知失败数、状态修复任务数。`OPERATION_STATUS_UNKNOWN`、发现重复记录或发现已审批金额超额时，自动触发 P0 告警并阻断继续放量。

## 8. 测试与验收

### 8.1 自动化测试

- 同一幂等键重复登记：数据库只存在一条回款记录，两次响应资源 ID一致。
- 不同幂等键并发登记：计划锁生效，累计审批/登记金额不能超过计划金额。
- 同一幂等键重复提交审批：只存在一个有效 PENDING 审批实例。
- 驳回后修改并重提：旧审批实例保留为 REJECTED，新审批实例可追溯，记录进入 PENDING_REVIEW。
- 撤回与审批并发：只允许一个终态胜出，另一方收到 409 并可查询最新状态。
- 审批通过：回款记录、确认状态、计划金额、合同汇总在同一主事务后保持一致。
- 审批操作重复请求：不重复追加业务效果；审批记录是否追加需按审计策略明确，但不能重复推进节点。
- 更新/删除并发：旧版本请求不覆盖新数据；已确认记录无法普通删除。
- 提交后通知失败：主事务保持成功，通知失败可观测且可补发。
- 服务端提交成功后模拟客户端超时：查询能够还原最终结果。

### 8.2 手工验收矩阵

| 场景 | 操作 | 预期结果 | 失败即升级 |
|---|---|---|---|
| 重复点击登记 | 快速连续点击提交 | 只生成一条记录，按钮进入处理中 | 是，若生成重复金额 |
| 网络超时登记 | 提交后断网/延迟 | 页面进入结果查询，不出现盲目重试 | 是，若无法确定结果 |
| 刷新恢复 | 提交后立即刷新页面 | 可通过记录号/列表查到真实状态 | 是，若状态不可追踪 |
| 并发超额 | 两人登记接近剩余金额 | 至多一个请求成功，另一请求明确超额或冲突 | 是，若累计超额 |
| 重复提交审批 | 双开页面同时提交 | 只保留一个有效审批实例 | 是，若重复建 PENDING |
| 审批/撤回竞态 | 审批人和提交人同时操作 | 一个成功，另一个 409，页面展示最终状态 | 是，若两者都成功 |
| 驳回重提 | 驳回后修改并提交 | 保留旧历史，创建新审批轮次 | 否，但若历史覆盖则升级 |
| 已确认删除 | 删除已通过回款 | 服务端拒绝并给出受控恢复/冲正提示 | 是，若可直接删除 |
| 副作用失败 | 模拟通知/刷新失败 | 主交易结论不变，失败可定位/补发 | 否，若主链路受影响 |

### 8.3 上线门禁

满足以下条件才允许进入普通 P1 发布：

- [ ] 回款登记、审批提交、审批动作、撤回、修改、删除均有自动化测试和手工记录。
- [ ] 相同请求重放不会生成重复回款记录、重复审批实例或重复金额累计。
- [ ] 超时后可通过记录/审批详情查询最终状态；不存在只能依赖用户猜测的分支。
- [ ] 409 冲突、金额超额、审批流缺失、权限不足均有稳定错误码和明确恢复路径。
- [ ] 回款记录、审批实例、计划状态、合同汇总的事务边界经评审确认。
- [ ] 已确认数据不提供普通删除/覆盖入口；冲正需求有负责人和人工流程。
- [ ] 发现重复写入、审批实例重复、金额超额、主交易已成功但状态不可查询等任一问题，立即按 P0 风险阻断上线。

## 9. 发布与回滚策略

建议采用后端先行、前端兼容、逐步放量的顺序：先增加幂等与查询能力及错误码，再切换前端提交态处理，最后收敛两个审批提交入口。旧客户端缺少 `Idempotency-Key` 时，服务端在迁移期可生成服务端兜底操作号，但不能把缺少幂等键作为长期状态。

数据库迁移应先增加可空字段、索引和审计表，再回填版本默认值，最后切换为非空或强约束；任何唯一约束上线前先扫描并处理历史重复数据。回滚时关闭新前端入口和新写路径，保留只读查询、审计和状态核查能力，禁止通过回滚脚本删除已产生的审批历史或回款数据。

灰度期间重点观察：重复请求命中、未知结果、409 冲突、计划金额不变量、审批实例数量、通知失败及人工修复量。连续一个完整业务周期无 P0 风险且数据核对通过后，再扩大范围。

## 10. 待确认事项与实现拆分

以下事项在编码前需要产品、财务和后端共同确认：

1. 当前登记回款接口在所有环境是否自动创建审批，还是部分环境由用户登记后再手动提交；两种语义需要统一。
2. `approval_phase` 与 `confirmation_status` 是否保留双字段；若保留，必须明确谁是展示主状态、谁是账务入账依据。
3. 回款记录的“登记金额”是否允许多个未审批记录累计占用计划额度；当前代码按全部 `payment_records` 校验，需要确认这是否符合业务规则。
4. 计划金额、合同金额的精度、币种和舍入规则；当前金额字段为 `Numeric(12,2)`，TRD 默认按两位小数处理。
5. 驳回重提是否新建审批实例，还是在同一实例中增加审批轮次；本 TRD 推荐新建实例、保留历史。
6. 已确认回款的更正是否通过冲正记录实现，谁有权限发起，是否需要财务二次审批。
7. 幂等记录保留周期、未知状态查询轮询时长和人工介入 SLA。
8. 提交后客户业务对象刷新失败的补偿负责人和运维入口；本包不展开 Agent/AI 自动化，但必须保证不阻塞回款主交易。

建议按以下技术任务实施：

- **TRD-01：状态与错误码契约**：统一状态枚举、响应字段、错误码和前端动作矩阵。
- **TRD-02：幂等与唯一性**：幂等记录表、有效审批唯一性、回款记录号唯一性和并发金额校验。
- **TRD-03：事务与版本**：回款记录/计划版本字段、审批提交及动作的锁与乐观并发控制。
- **TRD-04：最终状态查询**：单条回款记录详情、审批详情一致性、超时查询服务和前端恢复态。
- **TRD-05：审计与可观测性**：操作链路、指标、未知状态告警和人工补偿入口。
- **TRD-06：验证与灰度**：自动化测试、故障注入、并发测试、数据核对和发布门禁。

本 TRD 的 P0 判断标准不是“当前静态代码已经确认存在 P0”，而是“在关键验证完成前不能假设不存在 P0”。只有完成上述验证并证明重复写入、金额超额、审批实例重复和最终状态不可查询均被阻断，P1-PKG-01 才能关闭风险验证并进入后续体验改造。
