# P1-PKG-02 统一任务状态与结果反馈 TRD

- **文档类型**：Technical Requirements Document（技术需求文档）
- **所属改造包**：P1-PKG-02 统一任务状态与结果反馈
- **优先级**：P1
- **日期**：2026-09-03
- **适用系统**：CRMWolf 非 Agent / AI 自动化业务链路
- **排除范围**：Agent / AI 自动化状态模型、Agent 专属 operation/job 协议及其 UI 组件迁移
- **分析基线**：基于当前仓库静态代码核查及现有 P1 PRD；上线前必须通过联调、异常注入和关键任务验收

> 本 TRD 解决的是“状态语义和结果反馈不一致”问题，不是把所有页面强行改成同一个 Loading 组件。技术方案必须保留正常路径的短链路：普通查询不新增确认页，普通保存不新增中间页，只有无法确定结果、需要跨页面持续处理或存在并发风险的操作才进入增强状态。

## 1. 背景与技术判断

当前系统已经具备 `DataTable`、`ErrorState`、`LoadingSkeleton`、`ConfirmDialog`、审批状态徽章和部分回款结果确认能力，说明基础组件和局部异常处理并非空白。但状态仍主要由页面私有的 `loading`、`saving`、`processing`、`error` 布尔值和 Toast 组合出来，导致“请求状态”“资源状态”“业务最终状态”经常被混在一起。用户看到的提示往往只能回答“刚才发生了一个请求”，不能可靠回答“数据是否已经生效、当前对象处于什么状态、失败后能否继续”。

本期采用“统一协议 + 场景适配”的方式。统一的是状态含义、错误分类、恢复动作和可观测字段；不统一页面的布局，不把所有请求都升级为持久化任务，也不以新增弹窗或确认步骤替代原有直接操作。

## 2. 当前系统盘点

### 2.1 前端现有能力与差异

`CRM-Client/src/components/crmwolf/DataTable.vue` 已集中处理分页、筛选、排序、加载骨架、空行和移动端卡片，但当前只有 `loading`、`data`、`emptyTitle`、`emptyDescription` 等基础输入。加载时通过 `v-if="loading"` 整体替换表格，刷新期间用户看不到最近一次成功数据；空状态只有一个通用文案，组件本身不能区分“确实无数据”“筛选无结果”“尚未创建”和“无权查看”。组件内部的字段配置加载、保存和恢复失败目前直接使用不同 Toast 文案，尚未进入统一状态协议。

主要列表页 `Customers.vue`、`Opportunities.vue`、`Contracts.vue`、`PaymentPlans.vue`、`PaymentRecords.vue` 和 `ApprovalCenter.vue` 都有独立的列表 loading 和请求 catch 逻辑。普通列表页大多只调用 `handleApiError`，没有在列表内容区提供保留数据、重试、筛选上下文和权限语义；`ApprovalCenter.vue` 已有全局 403 / 加载失败 ErrorState，是可迁移的正向样板，但它与其它列表的实现仍不一致。

`CustomerDetailSheet.vue` 的 `loadAllData` 并行加载客户、跟进、商机、合同、发票抬头、部署、成员、档案和证据。除客户主详情外，多项请求使用 `.catch(() => [])` 或 `.catch(() => null)` 降级，结果是子模块请求失败可能被呈现为“空列表”而不是“该模块加载失败”；详情页也只有一个顶层 `loading`，不能表达核心详情成功但某个关联面板失败的部分成功状态。

`CustomerEdit.vue` 的客户详情加载失败后直接 `router.back()`，会丢失用户当前编辑上下文；采购方式和客户来源等选项加载失败只记录日志，不向用户提供可执行反馈。保存失败虽然没有主动清空表单，但状态、错误摘要、首个错误聚焦和可重试行为没有统一实现。该页面的提交按钮位于 `form` 外部，依赖 `@click="onSubmit"`，同时保留表单 `@submit`，需要在迁移时收敛为单一提交入口；另外当前基础 Button 组件没有声明 `loading` prop，不能把 `:loading="submitting"` 当作已经实现了按钮忙碌态和禁用态。

`ApprovalProcessGeneric.vue` 已实现审批详情重试、审批动作互斥、409 冲突刷新、驳回理由保留等能力，是本期状态协议迁移的主要样板。但其 store 使用单一 `loading` 表示详情加载、提交、审批和列表加载，组件本地又维护 `actionPending`，调用层仍通过 Toast 表达成功；这使共享层难以区分“读请求正在进行”和“写操作正在进行”。

`errorHandler.ts` 已区分网络、服务器、认证、业务、数据契约和未知错误，并提供回款结果未知提示，但错误分类仍主要以 HTTP 状态和错误消息关键词推断，缺少稳定的业务错误码、资源上下文、可重试标志和冲突版本信息。结果未知能力目前主要服务回款登记，尚未形成非 Agent 业务可复用的最小契约。

### 2.2 后端状态基础

后端已有业务对象状态和部分结果查询能力：审批模型包含 `PENDING`、`APPROVED`、`REJECTED`、`CANCELLED`；回款计划包含 `PENDING`、`OVERDUE`、`PARTIAL`、`COMPLETED`，回款记录包含确认和审批阶段；付款 API 已有通过隐藏幂等键查询最终结果的路径；审批 API 已有更新时间/版本冲突处理；操作日志服务可以记录资源操作历史。

这些能力足以支撑第一阶段的统一反馈，但不同对象返回结构和状态字段仍不完全一致。因此本期不要求所有业务对象马上改成同一数据库状态字段，而是在 API 适配层提供统一的“显示状态投影”和操作结果元数据。业务真实状态仍由各领域模型决定，统一层不能覆盖或重新解释业务状态。

## 3. 技术目标与非目标

### 3.1 技术目标

1. 让每一次关键读取、保存、审批、删除和结果确认都有明确的状态语义、展示位置和恢复动作。
2. 让页面状态与业务状态分离：加载失败不伪造业务失败，保存失败不覆盖详情，空状态不伪装成请求失败。
3. 让所有关键写操作具备最小的防重复提交能力；涉及高风险或超时未知结果的操作必须能够查询最终状态。
4. 让列表、详情、表单和审批在断网、超时、500、403、404、409、422 和部分成功场景下不依赖强制刷新恢复。
5. 使状态反馈可被键盘、读屏和 200% 字体用户理解，不能只依赖颜色或短时 Toast。
6. 以回款链路现有的隐藏幂等键、超时查询和权威状态刷新作为高风险操作迁移样板，但不重新设计回款业务规则。

### 3.2 非目标

- 不建立 Agent / AI 自动化的统一状态模型，不迁移 `CRM-Client/src/components/agent*`、`CRM-Client/src/composables/useAgentAsyncOperations.ts` 或后端 Agent operation/job 契约。
- 不把普通 CRUD 请求全部改成后台任务，不新增无必要的任务中心、确认页或手工刷新步骤。
- 不改变合同、商机、审批、回款的业务规则、权限规则、金额计算和审批流程定义。
- 不进行全量视觉 Token 迁移、低频页面重做或与状态反馈无关的代码重构。

## 4. 统一状态协议

### 4.1 三层状态模型

不能用一个枚举同时表示“页面在加载”“列表为空”和“回款已审批”。本期采用三层模型：

```ts
type ViewState =
  | 'idle'
  | 'loading'
  | 'refreshing'
  | 'success'
  | 'empty'
  | 'no_results'
  | 'forbidden'
  | 'not_found'
  | 'error'

type MutationState =
  | 'idle'
  | 'validating'
  | 'saving'
  | 'processing'
  | 'success'
  | 'failure'
  | 'conflict'
  | 'outcome_unknown'
  | 'partial_success'
  | 'cancelled'

type DurableOperationState =
  | 'accepted'
  | 'processing'
  | 'succeeded'
  | 'failed'
  | 'retryable'
  | 'partially_succeeded'
  | 'cancelled'
  | 'expired'
  | 'unknown'
```

`ViewState` 只描述读取容器；`MutationState` 描述用户本次操作；`DurableOperationState` 只用于操作可能跨请求、跨页面或需要最终状态查询的任务。审批和回款的业务状态仍由领域字段提供，例如 `approval.status`、`approval_phase`、`payment_plan.status`，不能将 `processing` 直接写入业务状态字段。

### 4.2 状态对象

共享 composable 使用带上下文的状态对象，不再以多个无关联 boolean 作为公共接口：

```ts
interface TaskFeedbackState {
  state: ViewState | MutationState | DurableOperationState
  label: string
  description?: string
  errorCode?: string
  resourceType?: string
  resourceId?: string | number
  operationId?: string
  requestId?: string
  canRetry: boolean
  canCancel: boolean
  updatedAt?: string
  staleAt?: string
}
```

状态对象必须是可序列化的纯数据，不能把 Axios error、组件实例或表单对象直接放进 store。`operationId` 仅在服务端或客户端已经有可查询的操作身份时使用；普通保存不为了填充字段而强行创建 operation。

### 4.3 状态转换规则

普通读取：`idle → loading → success | empty | no_results | forbidden | not_found | error`。已有数据刷新：`success → refreshing → success | error`，刷新失败时保留最近一次成功数据，并在内容上方显示“刷新失败，可重试”，不能把已有数据替换为空白错误页。

普通表单写入：`idle → validating → saving → success | failure | conflict | outcome_unknown`。422 校验错误回到可编辑状态；403 保留输入并显示权限原因；409 先刷新资源并显示冲突差异/最新状态；网络超时或连接中断进入 `outcome_unknown`，不能自动重新创建；服务端确认未生效后才允许用户重试。

审批和高风险写入：`idle → processing → success | failure | conflict | outcome_unknown`。成功条件不是 HTTP 请求返回 200，而是拿到资源或审批的权威最终状态；若响应只确认“已受理”，则显示处理中并保留查询入口。

### 4.4 页面阻塞规则

首次进入页面且没有任何内容时可以显示骨架屏；已有数据刷新时不得用骨架屏替换全部内容，只显示局部刷新状态。保存中只禁用当前提交动作和会产生同类副作用的控件，不阻塞无关详情查看。审批动作执行中禁用同一审批实例的其它动作，但不阻塞用户阅读审批历史。结果未知时保留表单和对象上下文，禁止自动关闭 Dialog、自动跳转或清空输入。

## 5. 统一错误与恢复协议

### 5.1 错误分类

| 分类 | 判断依据 | UI 状态 | 默认恢复动作 | 是否允许自动重试 |
|---|---|---|---|---|
| `validation` | 422 或字段级校验 | failure | 定位首个错误，保留全部输入 | 否 |
| `permission` | 401 / 403 | forbidden 或 failure | 登录、申请权限或返回可访问上下文 | 否 |
| `not_found` | 404 且资源不存在 | not_found | 返回列表或重新定位对象 | 否 |
| `conflict` | 409 / 版本不一致 | conflict | 拉取最新资源，展示当前状态后决定覆盖或取消 | 否 |
| `network` | 无响应、断网、连接失败 | error 或 outcome_unknown | 读取重试；写操作先查询最终结果 | 读取可重试，写入需确认 |
| `timeout` | 客户端超时但服务端结果未知 | outcome_unknown | 使用 operation/idempotency key 查询 | 不直接重建 |
| `server` | 5xx | error 或 failure | 保留上下文并重试，持续失败转人工处理 | 仅幂等读取/受控写入 |
| `partial_success` | 主结果成功、关联刷新/通知等副作用未完成 | partial_success | 展示已完成项和待处理项，提供局部重试 | 仅副作用 |
| `cancelled` | 用户或系统取消 | cancelled | 返回可执行的重新开始动作 | 否 |
| `data_contract` | 响应不符合前端 schema | error | 记录 request id，刷新或联系管理员 | 否 |

后端新增或补充稳定 `code`、`message`、`request_id`、`resource`、`current_state`、`retryable` 字段；前端不得长期依赖中文错误消息关键词判断业务分支。兼容期内 `errorHandler.ts` 可保留旧判断，但新接入页面必须优先读取稳定错误码。

### 5.2 统一反馈位置

Toast 只作为即时补充，不能作为关键结果唯一载体。列表错误放在列表区域顶部或内容区，并保留筛选和排序上下文；详情错误放在对应面板，核心对象仍可查看；表单错误放在字段、错误摘要和提交按钮附近；审批结果放在审批区状态徽章、时间线和操作区；回款结果放在记录详情和计划汇总中；跨页面长任务放在明确的任务入口或对象详情中。

成功反馈应包含对象和最终业务状态，例如“回款记录 RC-20260903-001 已登记，当前状态：待审批”，而不是只显示“保存成功”。如果只是受理而非最终完成，必须使用“已受理/处理中”，不得使用“成功”误导用户。

## 6. 前端共享实现

### 6.1 建议新增的共享模块

建议新增以下非 Agent 模块，名称可在实现阶段按项目约定调整：

- `CRM-Client/src/types/taskFeedback.ts`：三层状态、错误码和状态对象类型；
- `CRM-Client/src/composables/useViewState.ts`：读取容器的首次加载、刷新、空态和错误态；
- `CRM-Client/src/composables/useMutationFeedback.ts`：保存、提交、冲突、未知结果和重试锁；
- `CRM-Client/src/components/crmwolf/TaskStatusBanner.vue`：上下文内状态提示，支持 info、warning、error、success；
- `CRM-Client/src/components/crmwolf/InlineErrorState.vue`：模块级错误和重试；
- `CRM-Client/src/components/crmwolf/EmptyState.vue`：无数据、筛选无结果、尚未创建、无权查看四类语义；
- `CRM-Client/src/utils/errorHandler.ts`：扩展稳定错误码、重试能力和结果未知处理。

共享组件只负责状态投影和反馈，不在内部发请求、不拥有业务路由、不决定业务权限。请求和领域状态仍由页面或领域 store 持有。

### 6.2 DataTable 迁移

将 `DataTable` 的接口从单一 `loading` 扩展为兼容式输入：保留 `loading` 作为过渡字段，新增 `view-state`、`has-active-query`、`can-create`、`error` 和 `on-retry`。迁移后应支持“首次加载骨架”“已有数据刷新遮罩”“列表错误保留旧数据”“筛选无结果”“真正无数据”和“无权查看”六种表现。

分页、筛选、排序请求需要带请求序号或 AbortController，后返回的旧请求不能覆盖新查询结果。查询失败时不清空上一页数据，也不篡改当前筛选条件；若当前筛选导致 0 条，显示“未找到匹配结果”和“清除筛选”动作，而不是“暂无数据”。

### 6.3 CustomerDetailSheet 迁移

将 `loadAllData` 拆为核心详情状态和面板状态。客户主详情失败时显示详情级 ErrorState，但保留 Sheet 外层和返回入口；关联面板分别维护 `idle/loading/success/empty/error`，移除 `.catch(() => [])` 对用户可见状态的吞并。某个面板失败时显示“跟进记录加载失败，重试”，不能呈现为“暂无跟进记录”。

所有刷新操作使用请求序号防止旧响应覆盖新响应。客户编辑、合同、商机、回款和审批的成功回调只刷新受影响面板，避免每次操作都触发整套 `loadAllData`，但涉及跨对象汇总的回款/审批操作仍必须重新读取权威汇总。

### 6.4 CustomerEdit 与表单迁移

表单统一使用一个提交入口：按钮放回 `form` 内部或通过 `form` 属性绑定，不能同时依赖 form submit 和按钮 click 调用同一个 handler。`submitting` 必须映射到真实 `disabled`、`aria-busy` 和按钮内 loading 图标，不依赖基础 Button 未声明的 `loading` 属性。

详情加载失败不再自动 `router.back()`；应保留当前路由和返回入口，显示“客户详情加载失败”及“重试”。选项加载失败不能只写日志：如果字段不可用，明确标记该字段“选项加载失败”，提供局部重试；若选项是保存必需依赖，禁用提交并说明原因。422 错误按字段映射；未知错误显示表单级摘要；失败后保留用户已填写内容；首个可聚焦错误字段获得焦点。

### 6.5 审批迁移

以 `ApprovalProcessGeneric.vue` 和 `ApprovalCenter.vue` 为样板，将 store 的单一 `loading` 拆为 `detailViewState`、`listViewState`、`submitState`、`decisionState`。审批动作完成后必须更新审批详情、状态徽章、当前节点、历史时间线和待办计数；Toast 仅补充，不作为唯一证明。

409 必须保留用户已输入的驳回意见，重新读取最新审批详情，并根据最新状态显示“已被其他人处理”；不能让用户在旧状态上继续提交。批量审批使用逐项结果模型，返回全成功、部分成功和全失败三种汇总，失败项提供单项重试，不能以一个总 Toast 掩盖部分失败。

### 6.6 回款迁移

P1-PKG-01 已实现的回款登记结果确认作为本期迁移样板：前端持有隐藏幂等键，超时先查询最终记录，查询仍未确认时保留表单并显示结果未知；成功后刷新记录详情、回款计划汇总和审批状态。P1-PKG-02 不新增用户输入幂等键、不新增确认页、不改变金额或审批规则，只将该模式抽象为 `useMutationFeedback` 的可选 adapter。

回款计划和回款记录列表失败时不能将数据静默置空；详情中必须区分“记录不存在”“无权限”“审批数据加载失败”和“确实没有回款记录”。删除、重新提交、审批等动作需复用同一操作锁，避免详情 Sheet、列表行菜单和移动端卡片同时触发重复请求。

## 7. API 与数据契约

### 7.1 读取接口

读取接口保持现有业务返回结构，新增或统一以下响应头/元数据：

```json
{
  "request_id": "req_...",
  "resource": { "type": "CUSTOMER", "id": "123" },
  "server_time": "2026-09-03T10:00:00Z"
}
```

列表接口继续返回 `items` 和 `total`；如存在部分面板错误，不能把失败面板伪装成空数组。可采用面板独立请求或顶层 `warnings`，但必须能让前端区分“空结果”和“请求失败”。

### 7.2 写入接口

普通同步写入成功时返回资源最新版本和业务状态：

```json
{
  "data": { "id": 123, "status": "PENDING_REVIEW", "updated_time": "..." },
  "operation": {
    "id": "op_...",
    "state": "succeeded",
    "final": true
  },
  "request_id": "req_..."
}
```

不需要持久化 operation 的普通 CRUD 可以省略 `operation`，但必须返回可用于后续刷新或冲突判断的资源标识和版本信息。被受理但尚未完成的请求返回 `state=processing`；客户端超时不应猜测服务端失败。

### 7.3 错误响应

统一错误响应最小格式：

```json
{
  "error": {
    "code": "RESOURCE_VERSION_CONFLICT",
    "message": "该对象已被其他人修改",
    "retryable": false,
    "resource": { "type": "CONTRACT", "id": 123 },
    "current_state": "PENDING_REVIEW",
    "current_version": "2026-09-03T10:02:00Z"
  },
  "request_id": "req_..."
}
```

兼容旧接口时由前端 adapter 将 HTTP 状态、旧 `detail` 和新 `error.code` 映射到同一 `ApiErrorInfo`。不允许在领域组件中各自解析错误文本。

### 7.4 最终状态查询

需要支持最终状态查询的操作必须具备稳定查询键：回款登记使用现有隐藏幂等键；审批使用业务类型、业务 ID 和审批实例/版本；其它长任务使用服务端 operation ID。客户端处于 `outcome_unknown` 时只能查询或等待，不得生成新的业务写入请求。查询到终态后再将 UI 收敛为成功、失败或冲突。

## 8. 后端实现边界

本期后端优先补齐三项能力：稳定错误码及 request id；审批、回款等关键写操作的权威状态返回；对需要跨请求确认的操作提供查询键和最终状态查询。后端不新增一张覆盖所有业务的“万能任务表”，除非具体业务已经存在后台执行需求并经过单独评审。

操作日志继续作为审计和排查依据，但不把日志当作用户实时状态源。写操作的主事务结果必须先落在领域资源和可查询状态上，通知、索引刷新等副作用失败时返回或投影为 `partial_success`，不能回滚已经成功的主业务结果，也不能把主结果误报为失败。

Agent、客户智能和 AI 后台任务已有独立的 job/operation 模型，本期只允许在边界上保持不互相污染，不修改其状态枚举、恢复任务和专属组件。

## 9. 可观测性

每个关键请求至少记录 `request_id`、团队 ID、操作人、资源类型/ID、操作类型、前置状态、结果状态、错误码、耗时和是否重试。高风险写操作额外记录幂等键摘要或 operation ID，但不得记录 access token、凭证文件内容或完整敏感表单数据。

建议增加以下指标：

| 指标 | 目的 | 关注信号 |
|---|---|---|
| 首次加载错误率 | 判断读取可靠性 | 按页面、接口、错误码拆分 |
| 刷新失败后恢复率 | 判断重试是否可用 | 重试后成功 / 失败 |
| 重复提交拦截数 | 判断操作锁效果 | 同一资源短时间重复请求 |
| 结果未知数 | 判断链路稳定性 | 超时/断网后的未知结果 |
| 未知结果最终收敛率 | 判断可恢复性 | 最终成功、失败、持续未知 |
| 409 冲突率 | 判断并发编辑风险 | 按资源和操作拆分 |
| 部分成功率 | 判断副作用可靠性 | 主结果成功但关联动作失败 |
| 空态误判数 | 判断静默吞错 | 失败被映射为 0 条数据 |

`outcome_unknown` 持续无法收敛、出现重复回款/重复审批实例、或关键业务状态与操作结果不一致时，应停止扩大灰度并进入人工排查。

## 10. 测试方案

### 10.1 单元与组件测试

覆盖状态机转换、错误分类、状态优先级、重试锁、请求序号、结果未知处理、空态语义和 `aria-live` 输出。测试必须通过公共 composable 或组件行为验证，不能只测试内部 ref。

### 10.2 页面集成测试

至少覆盖客户列表、客户详情、客户编辑、商机列表/详情、合同列表/详情、审批中心/审批详情、回款计划、回款记录九类入口。每类入口都应验证首次加载、刷新失败、空列表、筛选无结果、403、404、422、409、超时和恢复路径。

### 10.3 关键异常矩阵

| 场景 | 预期用户看到的状态 | 预期数据行为 | 失败门槛 |
|---|---|---|---|
| 首次读取失败 | 内容区错误 + 重试 | 不产生伪造空数据 | 只能看到空白或 Toast |
| 已有数据刷新失败 | 保留旧数据 + 顶部错误 | 筛选/分页不丢失 | 旧数据被清空 |
| 筛选无结果 | 无匹配结果 + 清除筛选 | 保留筛选上下文 | 显示成“暂无数据”且无动作 |
| 子面板失败 | 该面板错误 + 局部重试 | 其它面板正常 | 失败面板显示为空 |
| 保存 422 | 字段错误 + 保留输入 | 不跳转、不清空 | 用户需重新填写 |
| 保存 409 | 冲突提示 + 最新数据 | 不覆盖他人修改 | 静默覆盖或直接失败 |
| 审批重复点击 | 单一处理中状态 | 不重复创建实例 | 产生重复审批 |
| 回款超时 | 结果未知 + 查询 | 不重复创建记录 | 用户被引导再次登记 |
| 批量部分成功 | 成功/失败项分别列出 | 成功项不回滚 | 总 Toast 掩盖失败项 |
| 权限不足 | 权限语义 + 可执行说明 | 不伪装成系统错误 | 显示通用“加载失败” |

### 10.4 无障碍验收

使用键盘完成列表定位、详情打开、表单提交、审批同意/驳回和异常重试；验证 Dialog/Sheet 焦点进入、Escape 关闭和焦点恢复。使用至少一种桌面读屏验证对象名称、状态、错误、保存中、成功、失败和权限不足均可感知。状态徽章必须同时有文字和语义，不得只用颜色。

## 11. 发布、灰度与回滚

实施顺序为：先落地类型和错误 adapter，再迁移共享状态组件，随后按“列表 → 详情 → 表单 → 审批 → 回款”的顺序迁移真实页面。每一阶段都保留旧接口兼容层和功能开关，先在测试团队开启，再按团队灰度。

灰度期间重点观察结果未知收敛率、重复请求、409 冲突、列表失败被误判为空、审批状态与详情不一致、回款重复记录和用户主动刷新率。发现业务状态错乱、重复副作用或未知结果无法查询时，应立即关闭新反馈开关，恢复旧展示路径，但保留后端幂等和审计保护；禁止通过回滚前端展示来回滚已经成功的业务数据。

## 12. 实施拆分

1. **状态协议与错误 adapter**：新增类型、错误码映射、状态文案表和测试基座。
2. **DataTable 与列表**：先迁移 `ApprovalCenter` 验证复杂状态，再迁移客户、商机、合同、回款列表。
3. **详情与面板**：迁移 `CustomerDetailSheet`、商机详情和合同详情，消除失败吞并为空。
4. **表单保存**：迁移 `CustomerEdit` 及高频业务 Dialog，统一提交入口、字段错误、冲突和未保存输入。
5. **审批与回款**：抽取 `ApprovalProcessGeneric` 的冲突/重试能力，接入 P1-PKG-01 回款结果确认模式。
6. **跨页面和无障碍回归**：完成结果未知、部分成功、键盘、读屏、移动端和灰度门禁。

每个阶段必须有独立验收，不以“共享组件写完”视为改造完成。

## 13. 验收标准

- 列表、详情、表单、审批和回款均使用同一套状态语义，不再由页面自行定义互相冲突的 loading/error/empty 文案。
- 列表刷新失败时保留最近一次成功数据；首次加载失败、筛选无结果、真正无数据、无权查看可明确区分。
- CustomerDetailSheet 的关联面板失败不再静默显示为空，能够局部重试；核心详情和其它面板不被单个子请求拖垮。
- CustomerEdit 详情或选项加载失败时不自动返回、不只写日志；保存失败保留输入并提供字段/表单级恢复路径。
- 保存、审批、删除、回款登记等操作在处理中不会产生重复请求；审批冲突和回款结果未知均能查询或刷新到最终状态。
- 成功反馈包含对象标识和最终业务状态；受理、处理中、成功、部分成功和失败不会混用。
- 关键异常场景无需用户强制刷新页面即可恢复，或明确提供可执行的重新定位/人工处理路径。
- 状态不依赖颜色，键盘和读屏用户能够理解对象、状态、错误和下一步动作。
- Agent / AI 自动化代码和状态协议未被本期迁移或改写；原有业务规则、权限规则和正常路径操作步骤不增加无必要环节。

## 14. 待确认事项

- 需要产品和后端确认统一错误码命名空间，以及哪些接口在本期补充 `request_id`、版本字段和最终状态查询。
- 需要确认批量审批的部分成功结果是否允许逐项重试，以及失败项的权限和状态是否可能在页面停留期间变化。
- 需要根据真实接口联调确认 CustomerDetailSheet 各关联面板是否可独立请求；如不能独立请求，应由后端返回面板级 warning，而不是返回空数组。
- 需要在测试环境使用 MySQL 3307 进行并发、超时和事务结果验证；静态代码分析不能替代真实网络和数据库故障注入。
