# P1-PKG-08 列表、DataTable 与行操作可发现性收口 PRD

- **文档状态**：PRD 初稿，基于现有 P1 改造结果补充，待产品、设计、研发和业务验收
- **版本**：v0.1
- **日期**：2026-09-03
- **所属改造包**：CRMWolf 非 Agent P1 UX 改造
- **父文档**：CRMWolf 非 Agent P1 UX 改造 PRD
- **范围说明**：本 PRD 不包含 AI / Agent 自动化，不改变现有 CRM 业务规则和权限规则

> 本改造包不是重新设计列表，也不是把所有右键菜单简单搬到操作列。目标是在保留现有高效操作方式的基础上，让关键操作对普通用户可发现、对熟练用户高效、对移动端和辅助技术可用，并统一不同业务列表的滚动、行点击和操作入口行为。

## 1. 背景与问题定义

CRMWolf 的客户、客户跟进、线索、商机、合同、发票、回款计划和回款记录等页面都以列表为主要工作入口。系统已经完成了一部分 DataTable 和行交互改造，包括详情入口、键盘操作、上下文菜单、固定高度和内部滚动等能力，但当前仍需要把这些能力收敛为一套可验收的产品规则。

现阶段的主要问题不是“有没有按钮”，而是用户在不同列表中可能遇到不同的操作方式：有的页面需要点击行，有的页面依赖右键，有的页面通过操作列，有的页面在移动端通过卡片菜单；操作列又会因按钮数量、按钮文案长度不同而出现过宽或过窄。与此同时，部分页面的表格高度和滚动容器行为不一致，可能导致整页滚动、表格内部滚动或 Sheet 内部滚动相互叠加。

这些问题会直接影响客户跟进、商机推进、合同查看和财务执行等关键任务的发现效率和操作可靠性，因此需要作为现有 P1 改造的补充收口，而不是降级为纯视觉细节。

## 2. 用户与关键任务

| 用户角色 | 典型任务 | 列表中的核心诉求 |
|---|---|---|
| 销售人员 | 查找客户、查看详情、记录跟进、推进商机 | 快速找到详情和下一步动作，不误触行操作 |
| 销售管理者 | 筛选商机、查看合同、处理审批相关对象 | 在大量数据中保持筛选条件和当前对象上下文 |
| 财务人员 | 查找回款计划、登记或查看回款记录 | 清楚区分查看、编辑、提交和高风险操作 |
| 团队管理员 | 维护客户成员、联系人、部署和发票信息 | 发现对象级操作，并能理解操作影响范围 |
| 移动办公用户 | 手机查看客户和快速跟进 | 不依赖右键，不被横向溢出和嵌套滚动阻塞 |
| 键盘或读屏用户 | 浏览列表、打开详情、执行行操作 | 行、详情入口和操作菜单语义清晰且不重复 |

第一批优先覆盖 Customers、CustomerTracking、Opportunities、Contracts、PaymentPlans、PaymentRecords 和 ApprovalCenter；其他列表沿用统一规则接入。

## 3. 产品目标

### 3.1 目标

1. 用户不需要记忆“这个页面要右键、那个页面要点击操作列”，即可找到查看详情和常用操作入口。
2. 右键和键盘上下文菜单继续保留为熟练用户的快捷方式，但不再成为查看详情或高风险操作的唯一入口。
3. 行点击、详情入口和行内操作之间有明确边界，不因点击按钮触发行打开，也不因点击行误触危险操作。
4. 桌面端列表采用稳定的页面布局和表格内部滚动；移动端优先自然页面滚动和卡片操作，不强行复用桌面端固定高度。
5. 操作列根据操作数量和文案自适应，避免一列在不同页面中固定占用过多空间，也避免按钮被截断或无法触达。
6. 搜索、筛选、排序、分页、刷新和打开详情后，当前列表上下文可以预测性地保留或恢复。

### 3.2 非目标

- 不调整客户、商机、合同、回款和审批的业务规则；
- 不新增 AI / Agent 入口或自动化能力；
- 不要求所有行操作都永久显示为独立按钮；
- 不把右键菜单完全删除或把所有操作机械地复制到操作列；
- 不以本改造包替代高风险操作确认、幂等和错误恢复规则；
- 不进行全量品牌色、字体、圆角和动效重做。

## 4. 核心交互规则

### 4.1 详情入口规则

每个业务列表必须提供一个不依赖右键的详情入口。默认使用以下优先级：

- 桌面端：对象名称或明确的“查看详情”按钮可点击；
- 行点击：仅在该列表明确声明“整行打开详情”时启用；
- 移动端：卡片主体或明确详情按钮打开详情；
- 右键和键盘上下文菜单：作为快捷操作入口，不作为唯一详情入口。

如果整行打开详情，行内按钮、链接、复选框和菜单触发区域必须阻止事件继续冒泡，并通过可访问名称说明自身动作。

### 4.2 行操作分层规则

行操作分为三层：

| 操作层级 | 典型操作 | 默认呈现方式 |
|---|---|---|
| 高频低风险 | 查看详情、编辑、跟进、查看关联对象 | 名称链接、操作列按钮或卡片按钮 |
| 中频对象操作 | 查看合同、查看回款计划、转移、分配成员 | 操作列中的更多菜单或上下文菜单 |
| 低频高风险 | 删除、退回公海、标记输单、冲红、撤回 | 明确入口 + 统一确认弹窗，不得仅依赖右键 |

同一列表最多保留少量直接按钮。超过可承载数量时，将低频操作收进“更多操作”菜单；高风险操作仍需在菜单项上明确风险语义，并进入统一确认流程。

### 4.3 操作列宽度规则

操作列不使用所有页面统一的固定宽度，而根据实际操作集合计算：

- 只有一个短操作时，显示单个按钮或图标按钮，并提供可访问名称；
- 有两个至三个高频操作时，显示有限数量的直接操作，其余进入更多菜单；
- 存在四字或更长文案时，优先使用统一按钮尺寸和菜单收敛，不允许文字被截断；
- 操作列至少保证按钮完整可点击，不能因表格压缩导致按钮重叠或不可见；
- 操作列不应挤压对象名称、状态、金额、日期等主要信息列；
- 在窄屏和移动端不强行保留桌面操作列，改用卡片底部操作区或更多菜单。

### 4.4 表格高度与滚动规则

桌面端列表页采用“页面框架固定、DataTable 内容区内部滚动”的模式：

- 页面标题、筛选工具栏和分页区域保持可用；
- DataTable 在可用视口内计算高度，不使用导致整页无限增长的内容高度；
- 表头在表格内部滚动时保持可识别；
- 不在同一任务中同时引入页面、表格、Sheet、Dialog 多个无解释滚动容器；
- 详情 Sheet 和表单 Dialog 内部滚动只服务于当前层，不改变底层列表的滚动位置。

移动端采用“自然页面滚动优先”：

- 卡片内容可以自然纵向滚动；
- 只有明确需要时才使用局部滚动容器；
- 操作菜单、详情 Sheet 和软键盘打开后，当前内容和提交动作必须可达；
- 不因复用桌面端固定高度造成内容被裁切或底部操作不可见。

### 4.5 列表上下文保持规则

以下操作完成后，系统应保持或可恢复用户上下文：

- 打开详情后返回列表：恢复原筛选、排序、分页和滚动位置；
- 执行行操作后：保留当前筛选和排序，并刷新受影响行或明确提示数据已更新；
- 搜索和筛选无结果：明确显示当前条件，并提供清空或修改入口；
- 刷新失败：保留当前列表和筛选条件，提供当前上下文内重试；
- 删除或状态变更成功：说明对象和最终状态，不只依赖短时 Toast；
- 批量操作或后台处理：显示进行中、成功、失败或部分成功的结果，并提供继续处理入口。

## 5. 功能需求

### P1-08-01：统一详情和常用操作入口

所有优先覆盖列表必须完成详情入口盘点，确保详情不依赖右键。每个页面需要明确行点击策略、对象名称是否可点击、操作列直接操作和更多菜单操作。

**验收标准：**首次使用该页面的用户能够在不查看帮助的情况下找到详情入口；鼠标、触摸、键盘和读屏路径均可打开同一对象详情。

### P1-08-02：统一行点击与行内操作事件边界

建立统一事件规则，避免点击按钮、链接、复选框、菜单触发器时意外打开行详情；避免打开菜单后同时触发行操作；关闭菜单后焦点回到合理的触发元素。

**验收标准：**在客户、商机、合同和回款列表中分别验证行点击、详情按钮、编辑、更多菜单和复选框，不发生重复打开或误操作。

### P1-08-03：操作列和更多菜单自适应

复用现有行操作分组能力，根据操作数量、危险级别、文案长度和 viewport 选择直接按钮或更多菜单。菜单项必须显示完整名称、可访问名称和禁用原因；危险操作进入统一确认模型。

**验收标准：**操作数量为 1、2、3、4 个以及包含四字操作文案时，操作列均不重叠、不截断、不挤压主要数据列；移动端操作可触达。

### P1-08-04：统一桌面端 DataTable 高度与移动端滚动

统一列表页面的容器高度、内部滚动、表头和分页布局；移动端使用自然页面滚动和卡片操作。对于详情 Sheet、Dialog 嵌套列表，明确滚动责任归属。

**验收标准：**Customers、CustomerTracking、Contracts、PaymentPlans、PaymentRecords 和 Opportunities 页面在相同 viewport 下滚动行为一致；桌面端不因表格内容撑高整页，移动端不出现内容裁切或双重滚动失控。

### P1-08-05：列表上下文和状态反馈收口

列表的加载、刷新、空数据、筛选无结果、权限不足、失败、部分成功和后台处理状态沿用 P1-PKG-02 的统一状态协议。本改造包负责验证这些状态在 DataTable 和行操作场景中的落点。

**验收标准：**筛选、排序、刷新、行操作失败、网络中断和后台处理中场景下，用户无需刷新或重新设置筛选条件即可理解结果并继续操作。

### P1-08-06：键盘、读屏和触控验收

沿用 P1-PKG-06 和 P1-PKG-07 的验收基线，补充列表专属场景：Tab 进入详情入口、Enter 打开详情、Shift + F10 或 ContextMenu 键打开菜单、Escape 关闭菜单、触控打开更多操作，以及读屏正确识别行和操作。

**验收标准：**列表的行、详情入口、操作按钮和菜单不会产生重复或冲突的读屏语义；键盘用户可以完成查看详情和至少一个常用行操作；触控用户不依赖右键完成任务。

## 6. 与现有实现的关系

本改造包基于当前已经完成的改造继续收口，不代表相关能力尚未开始：

| 已有基础 | 本 PRD 的补充工作 |
|---|---|
| DataTable 已支持标准表格语义和部分键盘交互 | 统一各业务列表的入口、事件边界和验收用例 |
| 主要列表已增加详情入口 | 检查入口可发现性、移动端触达和返回上下文 |
| 右键 / 键盘上下文菜单已存在 | 明确其为快捷方式，确保不成为唯一入口 |
| 行操作分组和部分操作列能力已存在 | 统一按钮数量、文案长度、危险级别和响应式表现 |
| 部分页面已采用固定高度和内部滚动 | 统一所有目标列表并排除整页滚动和多重滚动问题 |
| 列表刷新和部分反馈已有实现 | 接入统一任务状态协议，补齐失败、部分成功和后台处理场景 |

## 7. 页面实施优先级

| 优先级 | 页面 | 首要验证点 |
|---:|---|---|
| 1 | Customers | 详情入口、退回公海/输单入口、操作列、固定高度 |
| 2 | CustomerTracking | 查看详情、跟进操作、筛选和返回上下文 |
| 3 | PaymentRecords | 财务操作分层、结果反馈、金额相关操作入口 |
| 4 | PaymentPlans | 关联合同/回款记录入口、滚动和移动端可达性 |
| 5 | Opportunities | 行点击、详情下钻、审批相关操作入口 |
| 6 | Contracts | 合同详情、回款计划入口、操作列宽度 |
| 7 | ApprovalCenter | 任务打开、状态筛选、键盘导航和结果状态 |

## 8. 验收指标

| 指标 | 验收目标 |
|---|---|
| 详情入口发现率 | 首次使用者无需右键或帮助即可找到详情入口 |
| 行操作误触率 | 点击行内按钮不意外打开详情，不触发其他行操作 |
| 关键操作完成率 | 客户查看、跟进、商机查看、合同查看、回款查看路径可完成 |
| 操作列布局通过率 | 目标页面无按钮截断、重叠、遮挡和主要字段被挤压 |
| 返回上下文恢复率 | 返回后筛选、排序、分页和列表位置按预期恢复 |
| 异常恢复率 | 刷新失败、筛选无结果和行操作失败可在当前列表恢复 |
| 键盘/读屏完成率 | 目标列表可完成详情打开和常用行操作 |
| 移动端完成率 | 不依赖右键，320px 和横屏场景主要操作可达 |

## 9. 依赖与风险

- 依赖 P1-PKG-02 的统一任务状态反馈协议；
- 依赖 P1-PKG-03 的高风险操作确认、提交和恢复模型；
- 依赖 P1-PKG-04 的详情上下文和返回规则；
- 依赖 P1-PKG-06、P1-PKG-07 的响应式、键盘和读屏验收基线；
- 不应为了统一操作列而把所有低频操作永久暴露在首屏，避免增加 Hick 定律和 Miller 定律所描述的选择负担；
- 不应为了修复桌面端滚动而破坏移动端自然滚动；
- 不应把视觉上的“按钮统一”误认为高风险操作已经具备幂等和业务恢复能力。

## 10. 交付边界

本 PRD 完成后，目标不是所有页面都拥有完全相同的按钮，而是所有目标页面遵循同一套判断规则：用户知道如何查看详情，知道常用操作在哪里，知道危险操作需要确认，知道列表是否正在处理，以及在桌面、移动端、键盘和读屏场景下都能完成关键任务。

本改造包通过后，仍需在发布前结合 P1-PKG-01 的财务风险验证、P1-PKG-02 的状态协议和 P1-PKG-03 的高风险操作验收，确认列表入口没有绕过业务安全流程。
