## 1. 技术结论

CRMWolf 目前并非「列表完全没有优化」：`DataTable` 已具备标准表格语义、行点击、详情触发器、右键/键盘上下文菜单、桌面主操作与“更多”、移动端卡片、状态反馈、分页和部分固定高度能力；主要业务列表也已经接入了 `getRowActions`。

本 TRD 的工作重点是解决以下收口问题：

1. 统一详情入口、行点击、行内按钮、右键菜单和键盘菜单的事件边界，避免一次操作触发多个动作；
2. 让桌面用户不依赖右键即可发现详情和关键行操作，同时保留右键作为熟练用户快捷入口；
3. 将操作列的按钮数量、文案长度、危险级别、禁用原因和权限可见性统一投影到同一套模型；
4. 统一 DataTable 的高度和滚动策略，短期兼容现有页面高度参数，逐步消除页面级 magic offset；
5. 保证筛选、排序、分页、滚动位置和详情返回上下文不因行操作或详情打开而丢失；
6. 用组件契约、纯函数单测、页面矩阵和响应式/无障碍验收防止后续页面重新实现一套私有列表逻辑。

**本期不把所有按钮都放到首屏，也不把所有页面强制做成完全相同的按钮集合。**统一的是入口规则和技术合同，而不是业务动作本身。

## 2. 与 PRD 的映射和非目标

### 2.1 PRD 映射

| PRD 能力 | 技术落点 | 本期处理方式 |
|---|---|---|
| 详情入口不依赖右键 | `DataTable` 行点击 + 唯一详情 trigger + 移动卡片详情入口 | 统一语义、可达性和事件互斥 |
| 行点击与行操作互斥 | `DataTable` 事件判定、嵌套交互元素识别、菜单关闭锁 | 补齐边界测试 |
| 1～2 个主操作 + 更多 | `ActionConfig`、`tableRowActionGroups`、`DesktopTableRowActions` | 统一动作投影和长文案降级 |
| 高风险操作明确可达 | `destructive` 动作进入危险分组，继续调用既有确认流程 | 不新增业务确认协议，验证入口不隐藏 |
| 桌面内部滚动 | `heightStrategy`、`scrollMode`、列表页布局 seam | 兼容旧 `height`，逐步迁移到 `fill` |
| 移动端自然滚动 | `#mobile-actions`/卡片动作区域 | 不把桌面操作列硬搬到移动端 |
| 上下文恢复 | Sheet 保持挂载、路由 query/已有视图状态、滚动容器恢复 | 不新建第二套筛选状态系统 |
| 加载/空/失败/刷新状态 | `DataViewState`、`loadError`、刷新错误、LiveRegion | 统一页面落点和验收 |
| 键盘/读屏/触控 | 原生表格语义、详情 trigger、菜单键、ARIA、触控目标 | 增加列表专属测试矩阵 |

### 2.2 非目标

- 不改变客户、商机、合同、回款、审批等业务规则和权限码；
- 不新增合同下载、回款计划下载等当前尚未实现的业务能力；
- 不将高风险业务确认、幂等、后台任务协议重复实现到 DataTable；这些能力由其他 P1 包负责；
- 不把批量操作、看板、仪表盘或非 DataTable 页面纳入本次组件改造；
- 不恢复桌面端「每行展示完整多按钮」的旧方案；
- 不以长按替代移动端明确操作入口；
- 不为了修复桌面滚动而让移动端出现固定高度和双重滚动；
- 不直接删除仍在使用的 `height` prop，先提供迁移路径。

### 3.2 需要收口

1. 页面之间仍可能存在动作定义、移动端动作和桌面操作列重复维护的风险；
2. `ActionConfig` 目前通过 `label` 判断「查看/详情」，语义不够稳定；
3. 主操作有 `max-width: 128px` 和 ellipsis 行为，长文案可能被截断；
4. 禁用动作没有统一的 `disabledReason`，用户不一定知道为什么不能操作；
5. 详情按钮在技术上存在，但需要逐页检查视觉层级、Tab 顺序、读屏名称和移动端可见性；
6. 现有页面仍显式传入 `height="calc(100vh - ...px)"`，固定高度可用但依赖页面魔法偏移；
7. 详情打开/关闭、行操作成功或失败后的筛选、分页、排序和滚动恢复缺少统一契约测试；
8. 权限或业务状态变化后，操作列宽度和菜单内容需要稳定更新且不能误触发详情。

### 3.3 需要补齐或明确

- 详情动作的显式语义或禁止把详情动作作为普通行操作传入；
- 长文案操作的「自动降级到更多菜单」策略；
- 禁用原因的展示方式和读屏描述；
- 共享 `ListPageShell`/等价布局 seam 的迁移方案；
- 七个重点页面和 Leads、Invoices 的动作契约快照/行为测试；
- 320px、200% 缩放、键盘、读屏和触控验收记录。

## 4. 总体架构

### 4.1 深模块边界

本期采用「页面声明业务，DataTable 负责交互投影」的边界：

```text
列表页面
  ├─ 字段注册表：列 / 筛选 / 排序 / 字段配置
  ├─ 数据与分页状态
  ├─ 详情打开/关闭处理器
  └─ getRowActions(row)：业务动作声明（纯函数）
          │
          ▼
DataTable
  ├─ 行点击与详情 trigger
  ├─ 嵌套控件识别与事件互斥
  ├─ 桌面动作投影：主操作 + 更多
  ├─ ContextMenu / Shift+F10 共用动作模型
  ├─ 移动端卡片动作
  ├─ 高度、滚动、固定列避让
  └─ 加载/空/失败/刷新状态
          │
          ├─ DesktopTableRowActions
          ├─ TableRowContextMenuContent
          └─ TableRowActions（mobile）
```

页面不应同时维护三份动作集合，也不应在 `#cell-actions`、桌面按钮、右键菜单、移动卡片中分别写同一业务操作。

### 4.2 模块职责

#### A. `DataTable.vue`

负责：

- 接收字段注册表、数据、分页、状态和 `getRowActions`；
- 决定行是否可交互，以及详情入口落在哪个字段；
- 统一处理行点击、详情按钮、行内交互控件、右键和键盘事件；
- 对同一行动作生成桌面、上下文菜单和移动端所需的展示投影；
- 负责操作列、固定列和滚动容器的布局边界；
- 提供空、加载、失败、刷新失败和 LiveRegion 状态。

不负责：业务接口调用、权限规则推导、危险操作确认细节、跨页面业务状态机。

#### B. `tableRowActionTypes.ts`

定义页面到组件的稳定动作合同。动作定义必须是声明式、可序列化思考的纯数据 + handler，不得在计算阶段发请求或产生副作用。

#### C. `tableRowActionGroups.ts`

负责纯函数投影：可见性过滤、主操作提升、详情动作去重、危险分组、长文案降级和操作列宽度计算。该模块不接触 Vue、DOM、路由或 API。

#### D. 展示适配器

- `DesktopTableRowActions.vue`：桌面行尾最多两个主操作和可见「更多」；
- `TableRowContextMenuContent`/现有 `ContextMenu` 内容：与桌面动作使用同一投影，不额外定义动作；
- `TableRowActions`：移动卡片底部操作；
- 三者统一使用 `ActionConfig`，差异只体现在布局和交互载体。

#### E. 共享列表布局 seam

推荐新增 `ListPageShell`（或同等职责的共享布局类），而不是让每个页面继续自行计算视口偏移：

- 桌面：页面采用 flex column，表格区域 `min-height: 0`，DataTable 使用 `heightStrategy="fill"` 和 `scrollMode="contained"`；
- 移动端：切换为 `heightStrategy="page"`/自然滚动，卡片内容不被固定高度裁切；
- 兼容期：继续支持现有 `height` prop 和 `heightStrategy="legacy"`，逐页迁移后再淘汰魔法偏移。

## 5. 动作模型与投影算法

### 5.1 `ActionConfig` 合同调整

现有字段继续兼容，建议补充以下字段：

```ts
export interface ActionConfig {
  label: string
  handler: (row: Record<string, unknown>) => void
  visible?: boolean
  disabled?: boolean
  disabledReason?: string
  icon?: Component
  destructive?: boolean
  separator?: boolean
  desktopPrimary?: boolean
  /** 推荐补充：避免通过 label 判断详情语义 */
  kind?: 'detail' | 'standard'
}
```

实现约束：

1. `label` 是用户看到的文案，不作为业务语义主键；
2. `kind="detail"` 的动作不进入桌面主操作和更多菜单，详情由行点击/详情 trigger 承担；
3. 迁移期间如果暂不增加 `kind`，必须在页面层删除普通 `查看/详情` action；不得继续扩大 `VIEW_ACTION_LABELS` 文案黑名单；
4. `visible=false` 的动作不参与菜单、宽度和无障碍树；
5. `disabled=true` 的动作仍可展示，但不能调用 handler；有 `disabledReason` 时，桌面 title/描述、菜单辅助文本和读屏名称应能表达原因；
6. `destructive=true` 只表达视觉和分组语义，不绕过统一确认流程；
7. `handler` 保持页面既有业务处理入口，组件不得根据 label 猜测业务并直接调用 API；
8. `getRowActions(row)` 必须是纯函数。权限和状态计算可作为输入，但不能在计算阶段修改数据或发起请求。

### 5.2 标准化动作集合

页面只实现一个动作声明函数：

```ts
function getRowActions(row: Record<string, unknown>): TableRowActionSet {
  return {
    primaryActions: [
      { label: '编辑', handler: () => openEdit(row), desktopPrimary: true },
    ],
    secondaryActions: [
      { label: '移交客户', handler: () => openTransfer(row) },
      { label: '删除', handler: () => confirmDelete(row), destructive: true },
    ],
  }
}
```

同一函数用于：

- 桌面主操作；
- 桌面「更多」菜单；
- 右键菜单；
- `Shift+F10`/ContextMenu 键菜单；
- 移动端卡片动作。

不得再在 `#cell-actions` 中复制一套只供桌面使用的按钮；ApprovalCenter 移动端的通过/驳回等特殊待办操作可以继续保留其既有显式移动端布局，但需明确它们是否属于同一业务动作合同，不能悄悄改变现有待办流程。

### 5.3 主操作提升

投影函数 `getDesktopTableRowActions` 遵循：

1. 过滤 `visible !== false`；
2. 过滤详情动作；
3. 显式 `desktopPrimary=true` 且非危险动作优先，最多两个；
4. 没有显式主操作时，从 `primaryActions` 中选择第一个非危险动作作为兼容兜底；
5. 其余普通动作进入「更多」；
6. 危险动作统一进入「危险」分组；
7. 若最终没有可见动作，右键/更多均不打开空菜单；
8. 不因为「有右键菜单」而隐藏所有桌面可发现入口。

主操作选择由业务状态和动作声明决定，不在组件内维护客户、商机、合同等业务 if/else。

### 5.4 长文案和按钮数量

当前桌面主操作存在 `max-width: 128px` + ellipsis。收口后规则如下：

- 主操作短文案正常显示，按钮保留不小于 44px 触控目标；
- 文案超出单按钮安全宽度时，不截断为用户无法理解的省略号，而是自动降级到「更多」菜单；
- 两个主操作加「更多」后超过操作列上限时，优先保留业务声明的第一个主操作，其余进入「更多」；危险动作不得因空间不足而消失；
- 菜单内长文案允许自然换行或使用完整 title/辅助文本，但不得破坏菜单可操作性；
- 操作列宽度按当前页所有可见行的投影取最大值，统一列宽，避免逐行跳动；
- 当前页数据或权限变化导致宽度变化时允许重新计算，但不得因为 hover 或单次点击造成布局抖动。

这里的目标不是无限扩大操作列，而是确保「首屏少量高频动作 + 可见更多入口 + 完整菜单文案」三者同时成立。

### 5.5 禁用和危险动作

- 禁用动作保留在其应有分组中，展示禁用态和原因；
- 禁用动作不可触发 handler、确认框或网络请求；
- 高风险动作（删除、输单、失效、退回等）继续进入现有确认流程；
- DataTable 只负责入口和调用原 handler，不复制确认逻辑；
- 若危险动作因权限不可见，应从动作模型中 `visible=false`，而不是展示一个无意义按钮；
- 若动作因记录状态暂不可执行但需要告知用户原因，使用 `disabled + disabledReason`。

## 6. 详情入口与事件模型

### 6.1 入口优先级

桌面和移动端都必须存在不依赖右键的详情路径：

1. 行点击（仅在 `rowInteractive=true` 且点击目标不是嵌套交互元素时）；
2. 唯一、真实可聚焦的详情 trigger，用于 Tab/Enter/读屏；
3. 移动卡片中的详情入口；
4. 右键/ContextMenu 键/Shift+F10 作为快捷方式，不是唯一方式。

页面若已有行点击详情，不应额外把「查看」作为普通行操作显示两次。若确有业务需要独立动作（例如预览附件而非打开详情），应使用不同语义和文案。

### 6.2 事件互斥规则

| 操作 | 应触发 | 不应触发 |
|---|---|---|
| 点击行识别区域 | 打开详情 | 行内 action、右键菜单 |
| 点击详情 trigger | 打开详情一次 | 再触发行点击两次 |
| 点击主操作 | 仅调用该 action | 打开详情、打开菜单 |
| 点击更多菜单项 | 仅调用该 action | 行点击、重复调用 |
| 右键行 | 打开同一套菜单 | 打开详情、浏览器 CRM 菜单覆盖 |
| `Shift+F10`/ContextMenu 键 | 打开同一套菜单 | 触发行点击 |
| Escape | 关闭菜单/浮层 | 修改行状态 |
| 链接、输入、文本选择区域右键 | 保留原生行为 | 被 DataTable 抢夺 |

实现要点：

- 继续使用 `stopPropagation`/`preventDefault` 的最小边界，不能在整个表格上无差别吞事件；
- 对 `a`、`button`、`input`、`textarea`、`select`、`[contenteditable=true]` 及其子节点执行原生优先判断；
- 右键打开菜单后，对可能紧随其后的 pointer/click 设置短时同一行锁，避免「右键开菜单又进入详情」；
- 菜单项执行 handler 后，不冒泡为行点击；
- 菜单关闭点击表格外时，不把该 pointer 重新解释为行点击；
- 键盘打开菜单时没有鼠标坐标，使用行矩形右侧/中部作为锚点；
- 事件处理逻辑集中在 `DataTable`，页面不得为每个动作另加一套行点击拦截。

### 6.3 键盘和读屏

- 行可聚焦时，读屏应能获得稳定的行名称；
- 详情 trigger 必须有稳定的 accessible name，例如「查看客户：XXX」；
- Tab 可进入详情入口和可发现的主操作；
- `Enter` 打开详情或执行当前聚焦控件的原生行为；
- ContextMenu 键和 Shift+F10 打开与右键相同的菜单；
- 菜单打开后焦点进入菜单，方向键移动，Enter 执行，Escape 关闭并恢复焦点；
- disabled action 不可聚焦或按设计保留可读的禁用原因，但绝不执行；
- 状态刷新、失败和操作结果通过 LiveRegion/既有反馈机制告知，不依赖颜色或 hover。

## 7. 操作列、固定列与宽度实现

### 7.1 宽度计算

继续由 `getDesktopTableRowActionsWidth(actionSets)` 计算当前页统一操作列宽度，原则如下：

```text
每行所需宽度 = 主操作按钮宽度之和
             + 主操作之间的间距
             + （存在菜单时的更多按钮宽度 + 间距）
             + 操作区水平内边距
当前列宽 = clamp(当前页最大所需宽度, 最小宽度, 最大宽度)
```

实现要求：

- 最小值保持当前紧凑操作列的可点击空间（当前实现约 112px）；
- 最大值保持合理上限（当前实现约 280px）；
- 文案测量采用统一估算或 CSS `min-content`/实际布局方案，不能在页面各自写一套中文字符宽度算法；
- 长文案优先改变动作投影，不简单把列无限撑宽；
- 操作列宽度应基于当前页可见动作集合，不基于不可见权限动作；
- 计算逻辑必须有纯函数单测，渲染层只消费结果。

### 7.2 固定列偏移

- `fixedRightCount` 默认维持 0；
- 仅在业务明确需要时显式配置右固定列；
- 右固定业务列必须避让操作列，不能覆盖「更多」按钮；
- 没有右固定列时不应绘制误导性的右侧固定阴影；
- 左侧识别列的固定策略保持现状，不在本 TRD 扩展；
- 禁止通过「把最后一列自动固定」来修复操作列布局。

### 7.3 空动作

某一行没有可见动作时：

- 不渲染空的操作列按钮组；
- 右键/键盘菜单不打开空菜单；
- 不为了保持列宽而显示禁用的假按钮；
- 若同一页其他行有动作，列宽仍按有动作行统一，但无动作行保持视觉空白且不拦截行点击。

## 8. 列表高度、滚动与响应式

### 8.1 当前问题的技术判断

当前 Customers、CustomerTracking、Contracts、PaymentRecords 等页面显式使用类似：

```vue
height="calc(100vh - 121px)"
```

ApprovalCenter 使用另一组页面偏移。该方案已经实现了「桌面 DataTable 内部滚动」的效果，但页面偏移依赖 header、筛选区、分页等布局高度，后续 UI 改动可能导致整页滚动、底部被遮挡或出现双重滚动。

因此本期不把现有固定高度描述为「未实现」，而是将其定义为**兼容实现，需要抽象和逐页验收**。

### 8.2 推荐布局

桌面列表页建议统一为：

```text
ListPageShell (display:flex; flex-direction:column; min-height:0)
  ├─ 页面头部/标题/主操作（flex: 0 0 auto）
  ├─ 筛选区（flex: 0 0 auto）
  ├─ DataTable 区域（flex: 1 1 auto; min-height: 0）
  │    └─ heightStrategy="fill" + scrollMode="contained"
  └─ 分页/状态区（flex: 0 0 auto）
```

要求：

- 页面外层只有一个主滚动策略；
- DataTable 的数据区在桌面内部滚动；
- 任何 flex 滚动子项必须设置 `min-height: 0`，避免内容把父容器撑高；
- 表格容器负责横向滚动，页面主体不得横向滚动；
- 筛选、表头和分页保持可见性，滚动时不被数据内容顶出；
- 短期继续允许旧页面传 `height`，迁移完成后新页面默认使用 `fill`。

### 8.3 移动端

- 断点以下使用卡片/列表自然滚动，不使用桌面固定高度；
- 行操作位于卡片底部或明确的可见菜单，不依赖右键或 hover；
- 不为了复用桌面列宽而出现横向滚动；
- 详情入口和至少一个关键操作在 320px 宽度仍可达；
- 页面只有一个自然滚动容器，避免卡片内部再嵌套固定滚动。

### 8.4 迁移策略

1. 先确认 `DataTable` 的 `heightStrategy`/`scrollMode` 在目标页行为一致；
2. 新增或复用共享 `ListPageShell`，先迁移 Customers 和 PaymentRecords 作为高频/高风险验证页；
3. 再迁移 CustomerTracking、PaymentPlans、Opportunities、Contracts、ApprovalCenter；
4. 最后迁移 Leads、Invoices；
5. 每页迁移后保留一段兼容观察期，确认无整页滚动、底部遮挡和移动端双重滚动，再删除页面 magic offset。

## 9. 状态、上下文和返回恢复

### 9.1 状态边界

筛选、排序、分页和列表滚动位置属于列表视图上下文；详情内容属于详情上下文；行操作反馈属于任务状态。三者不可互相清空。

- 筛选变化可以重新请求数据，但不得无理由清空排序规则；
- 分页切换不得清空筛选；
- 刷新/行操作成功优先只重新请求当前页或局部更新，保留筛选、排序和分页；
- 行操作失败保留原列表和上下文，显示可理解的失败反馈和重试入口；
- 详情打开采用 Sheet 时，底层列表组件保持挂载，不重建 DataTable；
- 路由详情需要恢复时，使用已有 route query 或现有视图偏好机制，不新造第二套状态存储；
- DataTable 的滚动容器在详情打开前记录 `scrollTop`，关闭后在 DOM 更新完成后恢复；
- 当记录被删除或从当前筛选结果中移除时，恢复到合法页码，不能停留在空白的非法分页。

### 9.2 详情返回流程

```text
列表当前上下文
  → 打开详情/编辑 Sheet
  → 完成查看或编辑
  → 关闭/返回
  → 保留筛选、排序、分页
  → 恢复列表滚动位置
  → 若数据变更：刷新当前页或局部更新
  → 更新状态反馈，不跳转到无关页面
```

不要求所有详情都统一成单一详情页；本期只要求入口和返回行为可预测，不改变已有业务使用方式。

### 9.3 异步处理

如果行操作交给后台任务：

- handler 立即反馈「已提交/处理中」；
- 当前列表保留可浏览状态；
- 任务完成/失败通过统一状态协议更新；
- 刷新后不应把用户带回默认筛选或第一页；
- DataTable 不实现后台任务轮询，消费已有任务状态能力。

## 10. 页面迁移矩阵

每页必须只有一个业务动作声明源；动作具体可见性沿用当前业务状态和权限，不在本 TRD 擅自新增或删除业务动作。

| 页面 | 当前基础 | 技术收口动作 | 重点验收 |
|---|---|---|---|

| PaymentRecords | 已有编辑/删除；部分 action 仍含「查看」 | 删除普通查看 action 或显式标记 detail；统一财务操作反馈 | 金额操作入口、失败保留上下文、权限变化 |

- 单个页面问题不应回滚整个 DataTable 或影响其他页面。

| 风险/疑问 | 决策 |
